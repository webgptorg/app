# @ptbk/mock-engine

A stand-in for the real engine that speaks every real contract: it registers with the dashboard, dials the relays, serves TLS inside the tunnel, serves the engine API with seeded fake data, sends signed heartbeats and, in a later task, runs the UI loader ([ADR 0004](../../docs/adr/0004-mock-engine-and-conformance.md)). No shortcuts the real engine would not have: everything goes through `@ptbk/protocol`, which makes this the reference implementation for the engine team.

## What runs today (M-01)

- A persistent Ed25519 identity in `PTBK_DATA_DIR/engine-key.pem` (PKCS#8, mode 0600, directory 0700). Startup refuses a key or directory that group or others can access, like OpenSSH. The key is generated extractable only to write it once; at runtime it is a non-extractable WebCrypto key.
- One tunnel per relay in `PTBK_RELAYS`, each independent: `idle → connecting → handshaking → ready → backoff`. The handshake is C-02's: the engine refuses to sign a challenge for a relay other than the one it dialled, signs both sides' version and feature lists, and closes with `PROTOCOL_ERROR` if `ready` is not exactly the negotiation of the signed lists.
- Reconnect with full-jitter backoff (500 ms base, factor 2, 10 s cap, reset after 60 s ready). `SHUTTING_DOWN` on a ready tunnel retries within 500 ms; `REPLACED` stops that relay's link for good (another holder of the key took the slot, and reconnecting would replace it in turn); everything else backs off.
- `HTTPS_PROXY` with `CONNECT` (basic auth from the URL) and `NO_PROXY`; the relay certificate is verified for the relay hostname through the proxy too.
- Each stream the relay opens becomes a Node `Duplex` (`TunnelDuplex`) with `WINDOW` flow control: credit flows back only as the consumer reads.

## TLS and HTTP inside the tunnel (M-02)

Browser TLS ends in the engine, never on the relay: each tunnel stream goes to a TLS server (TLS 1.3 only, ALPN `http/1.1`) that picks the certificate per SNI from a `CertificateSource`, so a renewal applies to the next connection. An unknown or missing SNI fails the handshake; there is no default certificate. Behind it, a Hono app on a `node:http` server that never listens serves the decrypted connections, and WebSocket upgrades go to `ws`. The engine holds certificates for `<engineId>.<PTBK_ENGINE_DOMAIN>` plus every hostname a relay confirmed in `ready`.

Each stream gets its own small `tls.Server` (they share the SNI contexts): a `TLSSocket` over a JS stream has no peer address and no public link back to its stream, so one shared server could not tell the HTTP layer which `OPEN` frame, and so which client IP, a request came from. HTTP/2 is not offered yet; HTTP/1.1 covers SSE, WebSockets and downloads.

Every route is declared through `defineHttpRoute` or `defineWebSocketRoute` (`src/adapters/http/route.ts`) with an auth mode (`public`, `session` or `control`), a permission where the policy needs one, a per-client-IP rate limit and strict zod schemas for path parameters, query, headers and a size-capped body; unknown or repeated query parameters and values over a cap are a 400 problem+json, an oversized body 413. The route-table test checks the public allowlist, the self-scoped session routes without a permission, the engine API against `ENGINE_API_ROUTE_LIST`, and that no `control` route can be mounted in the tunnel. Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `ENGINE_UI_CSP` from `@ptbk/engine-api` (M-05 adds the full header set).

| Route                                   | What it does                                                                                                                                                                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /`, `GET /__spike/`                | Static page naming the engine ID; no inline script or style. `/` serves it until M-05 mounts the UI                                                                                                            |
| `GET /__spike/whoami`                   | `{ engineId, hostname, clientIp, alpn, tlsVersion }`; `clientIp` is the address from the tunnel's `OPEN` frame                                                                                                 |
| `GET /__spike/sse?count=N&intervalMs=M` | `N` (1–1000, default 20) events every `M` ms (0–10000, default 1000), IDs `1..N`; resumes after `Last-Event-ID`, 204 when done                                                                                 |
| `WS /__spike/ws`                        | Echo, text and binary, up to 1 MiB per message (larger closes with 1009)                                                                                                                                       |
| `WS /__spike/screencast?fps=F&bytes=B`  | Binary frames of `B` bytes (12 B–1 MiB, default 64 KiB) at `F` fps (1–30, default 5): u32 sequence, float64 send time in ms, both big-endian; drops a frame rather than queue it behind two others (or 64 KiB) |
| `GET /__spike/download?bytes=N`         | `N` bytes (up to 1 GiB) with `Content-Length`, produced only as the connection drains                                                                                                                          |

Rate limits per client IP: 600 requests a minute, 60 for download and screencast.

## Engine API (M-04)

The engine API is not reimplemented here. `@ptbk/engine-api/in-memory`'s core holds all state and every handler (validation, permissions, audit chain, events, streamed replies), and `@ptbk/engine-api/http` serves it; the mock adds only what a separate process needs. `src/adapters/http/api-routes.ts` declares one route per entry of `ENGINE_API_ROUTE_LIST`, with the table's method, path, permission and schemas, and hands each request to the core with the request's actor. The route helper caps the body and checks the declared headers; params, query and body are parsed by the binding with the same strict schemas, after the capability and permission checks, so a caller without the permission gets 403 whatever its input (C-04's order). `GET /engine` advertises the capabilities in `MOCK_CAPABILITIES` (see M-07 below) and reports the engine ID, hostname and `mode: tunnel`, and `dashboardUrl` stays `null` until M-06 sets it. `GET /security` lists each relay as `connected`, `connecting` or `disconnected` from the tunnel links, plus the hostnames relays confirmed. `tls` reports the SHA-256 and expiry of the certificate the engine serves for its default hostname, updated on every issue and renewal (X-04). The relays' ping round trip, the hostnames' certificate status and claim, the release log entry UUIDs and the CT check are not wired yet and read as `null` or the core's placeholders.

**Data.** `MOCK_SEED`, `MOCK_SCENARIO` and `MOCK_SEED_EPOCH` fully determine the state: faker (only at seed time) and a seeded sequence for IDs, never the crypto `Random`. Every scenario has the built-in agents a Reborn engine always has: Chatter, Adam, Tasker, Router, Fixer and Teacher (`origin: core`) and Expert (`origin: system`), each with its one-line role as the Book's `PERSONA`; the simulation starts spontaneous runs only on content agents. Onboarding (`onboarding@1`) is the in-memory core's script, using every prompt kind but `upload`: the brief with attachments, the harnesses (OpenAI Codex, Claude Code or both), then per harness an install (Codex 2 s of engine time; Claude Code is already installed), its sign-in (Codex: a device code that completes after 5 s, or an API key of the form `sk-` and 20 more characters, or a link to the engine's terminal page; Claude: paste any code of 6 or more characters) and a 2 s check; then the project's name, folder and a review, and 3 s to create it. The core's levers `settleHarnessLogin` (end a sign-in with any outcome) and `failHarnessCheck` (fail a harness's check with a reason) decide the rest. Scenarios: `empty` (owner only), `small-team` (owner, admin, two members, a viewer; about 8 agents with threads: the User with one agent, Chatter bringing an agent in (`chat-chatter-brings-in`), two agents talking without the User (`chat-agents-talking`), the one-agent `Report` and an agent's `+@User` question waiting with choices (`chat-question-for-you`), secrets metadata, an `Injection demo` agent whose replies carry hostile markdown and raw HTML for engine-ui's sanitiser (an image and a raw `<img>` from `attacker.example`, a `<script>`, a `javascript:` link), and whose audit trail starts under the markup name `<img src=x onerror=alert(1)>`), `large-fleet` (about 500 agents, 40 members, long chats for paging). Seeded audit entries (agent and secret creation, the rename above) carry target names and `details` like the core's own. In a thread the core routes each User message as the engine does: to the author of the question it answers (`replyTo`), else to an agent the message brings in (`+@Name`, `+{Full Name}`, or "ask Ada", "bring in Ada", "invite Ada"; the main agent says so, the agent joins, then answers), else to the main agent; the first message retitles a thread started without a title, and a message containing "ask me" gets a reply that ends with a `+@User` question and two choices. Replies are generated per seed, chat and turn, as markdown with code blocks, tables and links, paced at about 30 tokens a second; they keep generating without a reader, and only the cancel route stops them.

**Gateway stand-in** (`src/domain/gateway/sessions.ts`, `src/adapters/http/gateway-middleware.ts`), not a port of the engine's gateway:

- Cookie `__Host-ptbk_session`: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`. Its value is a 128-bit token from the crypto `Random`, separate from the session ID that `GET /sessions` lists, and new on every sign-in.
- Sessions end after 30 minutes idle or 12 hours, or as soon as the core no longer lists them: revoking a session or removing a member through the API signs it out. The member's role is read on every request.
- A sign-in stands in for an assertion with the member's newest passkey, which becomes the session's `passkeyId`, so revoking that passkey signs the session out.
- A sign-in counts as a fresh passkey assertion for 5 minutes; after that, `stepUp` routes answer 401 `step-up-required` until the step-up form is used.
- State-changing requests need `Origin` equal to `https://<Host>` (with `Host` naming the SNI hostname) and `Sec-Fetch-Site` `same-origin` or `none`, else 403 before anything else runs. Browsers send both; non-browser clients such as the conformance suite must send them too.
- Anonymous API requests get 401 problem+json; anonymous documents are redirected to `/auth/sign-in` with their path and query as `next` when `isSafeNextPath` accepts it, so the member lands there after signing in. `POST /auth/sign-out` ends the session.
- Without dev login, `/auth/sign-in` and `/auth/step-up` are the passkey pages (M-08, below). `MOCK_DEV_LOGIN=enabled` turns `/auth/sign-in` into a page listing the members (a form per member, carrying a safe `next` through to the redirect after sign-in) and adds a dev step-up form at `/auth/step-up`; `/setup` and the passkey endpoints stay, so the dev stack can onboard with a real passkey and still use the picker.

**Policy** (`src/domain/authorization/policy.ts`, the mock's guess at engine policy until the engine team confirms it): `owner` holds every permission; `admin` all but `settings.manage`, `browser.control` and `ai-tools.manage`; `member` reads and writes agents, chats and files, reads Wallet logins and requests (never a password), members, runs, triggers and integrations, controls runs and manages triggers; `viewer` only reads agents, chats, files, members, runs, triggers and integrations. A session from `/__mock/sessions` with a permission set holds exactly that set. The one rule on top: without `members.manage`, a member changes (`agents.write`, `agents.delete`, `agents.run`) only agents they created; a refusal is the core's usual 403 and an audited `denied`.

**Faults** (`MOCK_FAULTS` or `PUT /__mock/faults`, a strict `FaultPlan`): `latencyMs { min, max }`, `errorRate` with `errorStatus` (500, 502 or 503, sent as `internal-error`, `reply-failed` or `unavailable`, the contract's problem for each status), `dropStreamRate` (an SSE response is cut after a random 1 to 20 events), `slowTunnelBytesPerS` (every tunnel stream is throttled towards the browser) and `routes` (path globs, `*` within a segment, `**` across). Decisions draw from a sequence seeded by `MOCK_SEED`, and a new plan applies from the next request. M-07 adds four that act on the engine rather than on requests (and ignore `routes`): `runFailureRate` (0–1, the share of simulated runs that fail; `null`, the default, keeps the simulation's own 12 %), `stuckQueue` (simulated runs stay `queued`, so `oldestQueuedAt` keeps ageing; turning it off lets them go), `scanInfectedRate` (0–1, the scanner finds the next uploads and run outputs infected) and `integrationErrorRate` (0–1, the next connection tests on create, enable or check end in `error`).

**Control listener** (`MOCK_CONTROL=enabled`): plain HTTP on `MOCK_CONTROL_HOST:MOCK_CONTROL_PORT` (default `127.0.0.1:4480`), never mounted in the tunnel; through the tunnel `/__mock/*` is 404 (a `GET` from an anonymous visitor is sent to sign-in first, like any page). Bodies are strict.

## Capabilities and the live simulation (M-07)

The mock serves `runs@1`, `tasks@1`, `files@1`, `triggers@1`, `integrations@1`, `test-chat@1` and `ai-tools@1` and the activity feed (with `MOCK_PROFILE=full`; the default `reborn` profile advertises only what the Reborn engine has). As for the core API, nothing is reimplemented: the in-memory core holds the state, the handlers, the capability gating (404 `capability-not-supported`), the rules (cancel, retry, pause and resume, the 409s and 422s) and every event and activity item. A `test-chat@1` reply comes from the same reply generator as chat, with the draft's name, and stores nothing; it has its own rate limit (`engine-api-test-chat-ip`, 60 a minute per client), since each one stands for a model call. `ai-tools@1` is the core's three fake tools (Claude Code signed in with an account, OpenAI Codex with an API key, Gemini CLI not installed); checks and sign-in answers have their own limit (`engine-api-ai-tools-ip`, 30 a minute per client), and the control routes below expire and renew a sign-in, fail checks and answer a device login (M-13). The mock adds the seed, the simulation, the faults and the control routes, and changes state only through the core's controller levers, which write no audit entries.

**Seed** ([capability-seed.ts](src/domain/state/capability-seed.ts), from the same seed, scenario and epoch as the rest, plus the engine hostname for email addresses). `small-team` has about 200 runs over 14 days, each with a `preview` of what started it (the chat message, an email subject, a schedule's message, else the task) and its output files named: a `web` run for every chat turn in that window, linked to its reply, and runs from API clients, members, goals, webhooks, email and schedules, with every terminal status, two still running and two queued, progress cards, tool calls in every state, usage with a USD cost, failures with believable codes (`tool-timeout`, `rate-limited`, `invalid-credentials` …), retry chains and commits with changed files and a unified diff (one generated fixture exceeds `MAX_RUN_TEXT_BYTES` and is truncated). Files: knowledge per agent (agents that commit keep a git-backed file whose versions are the commits), chat attachments, run outputs (some are 64 × 64 PNGs drawn from the seed and compressed with `CompressionStream`, see [png.ts](src/domain/state/png.ts)) and uploads; one is infected, two are pending and two failed their scan; every SHA-256 is real. Knowledge uploads take documents only (PDF, text, Markdown, CSV, JSON, HTML, DOCX, ODT, RTF) up to 10 MiB; other purposes any type up to `MAX_FILE_BYTES` (`MOCK_UPLOAD_POLICIES` in [capabilities.ts](src/domain/state/capabilities.ts)). Triggers: email triggers at `<triggerId>@<hostname>` and `once`, `interval` and `cron` schedules (several time zones) in every lifecycle and every `endedReason`, each with a fire history whose started fires link to their runs (computed with the core's own schedule). Integrations: MCP servers, calendars and GitHub repositories, engine-wide and per agent, connected, `needs-attention` (a missing and a revoked secret reference), `error` and disconnected, with scopes and tools. Activity covers every area and parses as known. `large-fleet` scales the same mix to about 20,000 runs, 3,000 files, 500 triggers, 300 integrations and 50,000 activity items, seeded in under 3 s.

**Simulation** ([src/domain/simulation/](src/domain/simulation/simulation.ts)). Engine time is a [simulation clock](src/domain/simulation/simulation-clock.ts) over the real `Clock` port: running, it moves `MOCK_SIMULATION_SPEED` times as fast as real time and starts at the real time; paused, it starts at the seed epoch and moves only by `POST /__mock/simulation/advance`, which runs everything that falls due in order. The core's timestamps come from it; chat replies stay paced in real time, so chat works while the simulation is paused. The simulators draw from a sequence seeded by (seed, scenario), so a paused engine is reproducible from seed, scenario, epoch and the `advance` calls.

- [run-simulator.ts](src/domain/simulation/run-simulator.ts) takes on every queued non-chat run (scheduled, emailed, retried, scripted or started by the simulation itself every few minutes) and the seed's open runs: `queued → running`, progress items completing one by one, tool calls `pending → partial → complete | error`, then `completed` (with usage, sometimes a commit and an output file) or `failed`. A run whose cancel was requested ends `cancelled` at its next step. Chat runs are the core's: they end with their reply.
- [schedule-simulator.ts](src/domain/simulation/schedule-simulator.ts) calls the core's `fireTrigger` at each active schedule's `nextFireAt`; the core decides the run, the fire record, the next fire and the end (`startsAt`, `endsAt`, `maxRunCount`). Paused and ended triggers have no next fire.
- The scan and the connection test are the core's `EngineChecks` port, faked in [engine-checks.ts](src/domain/faults/engine-checks.ts) from the fault plan.

Through the tunnel every `/__mock/*` route is 404, as before.

## Live browser (M-11)

`browser-tab@1` is a draft no environment advertises by accident: only `MOCK_LIVE_BROWSER=enabled` turns it on, and `NODE_ENV=production` refuses it. As for the rest of the API, the reference engine in `@ptbk/engine-api/in-memory` holds the tabs, sessions, help requests and the channel protocol; its fake browser draws small PNG frames, so no browser and no new dependency is involved. The mock adds:

- **The fake tab**: every core (at startup and after `/__mock/reset`) opens an agent tab at `https://shop.example`, in the first seeded chat when there is one, and allows `https://accounts.example` for remote sign-in. Reserved `.example` origins only.
- **The channel** at `/api/v1/live-sessions/{sessionId}/channel` ([live-channel-route.ts](src/adapters/http/live-channel-route.ts)), a WebSocket inside the tunnel's TLS like every other request. The upgrade is checked in this order: the rate limit (`live-channel-ip`), the path (a malformed or unknown session ID is 404), an empty query (no token in the URL: 400), `Origin` equal to the engine's own (403, cross-site WebSocket hijacking), the gateway session cookie (401), the route's `browser.watch` (403), the `ptbk-live` subprotocol (400, answered with it), then the core: another gateway session's session is 404, a second attachment 409, an ended session 409, without the capability 404 `capability-not-supported`. A refusal is a plain HTTP problem+json answer, never an opened socket. The core audits the attach once the handshake completed, and as `failed` when it did not. Messages above 5 KiB close it with 1009; the channel closes with 1008 once more than `MAX_LIVE_SEND_BUFFER_BYTES` (1 MiB) waits unsent (the core's ack credit keeps an honest viewer far below). Nothing a message carries is logged.
- **Timers**: the engine calls the core's `browserTick()` every 500 ms on its clock, which ends sessions past their attach deadline, time or idle limit and paces the screencast.
- **Policy**: `browser.watch` for every role (a member watches only tabs of work they can see); `browser.control` stays with the owner. The core asks the session store what each gateway session holds on every sweep, so a role change that takes `browser.control` ends a controller's session with `revoked` at once.
- **Levers** on the control listener, above: open a tab, raise a help request, move the tab, end a session early.

## Registration and heartbeat (M-06)

The engine's only conversation with the dashboard, straight over HTTPS (never through a relay), through `HTTPS_PROXY` and `NO_PROXY` like the tunnels and trusting `MOCK_EXTRA_CA_FILE` as well as the default roots.

**Startup.** The dashboard is `PTBK_DASHBOARD_URL`, else the origin of a link URL in `PTBK_LINK_CODE`, else (without `PTBK_RELAYS`) the dashboard stored in `registration.json`, so an engine that `connect` linked with a link URL restarts with no dashboard setting at all; an engine with none of them and no registration refuses to start. With a dashboard: a stored `registration.json` is loaded and checked again against the key, the engine domain and the dashboard (a mismatch stops startup); otherwise `PTBK_LINK_CODE` registers; with neither, the engine starts unlinked (`mode: local` in `GET /engine` and `status`): it dials no relay and sends no heartbeat, logs `engine.not-linked` and waits for `connect` (see "Operator commands"). With `PTBK_RELAYS` and no dashboard setting the engine runs in the M1 dev mode on `PTBK_RELAYS`, without registration or heartbeats. The engine dials the registration's relays, unless `PTBK_RELAYS` is set: then that list replaces them (an operator override from the launch contract, which the conformance harness uses to point the engine at its loopback relays), and `GET /engine` reports the dashboard URL.

**Registration** (`src/domain/registration/register.ts`): the request is built and signed with `signRegistration` (`mode: tunnel`), the answer is read tolerantly (`TolerantRegisterEngineResponse`, unknown fields stripped, known ones checked, within `REGISTER_RESPONSE_MAX_BYTES`) and then checked with `checkRegistrationResponse`: an engine ID the key does not derive, or a hostname outside the engine domain, is refused and nothing is stored. Problem codes map to `rejected` with the C-03 reason (`invalid-link-code` covers unknown, expired and used codes alike; `not-entitled` reads like `engine-limit`); `rate-limited`, no answer, a timeout, an error without a readable problem and a code this build does not know are `unavailable` with that reason, and the last two are logged with their status and code. `unavailable` is retried ([register-with-retry.ts](src/domain/registration/register-with-retry.ts)): after 5 to 10 s, doubling up to 1 to 2 min (equal jitter), for 30 minutes from the first attempt (a link code lives 30 days, so the operator can simply run `connect` again); each wait is logged as `registration.retrying` with the reason, attempt and delay, and told to the operator. An engine that already holds a registration makes no network call. Re-registering a kept key after `registration.json` is lost is idempotent on the dashboard and yields the same engine ID. The link code is taken once from the configuration (and removed from `process.env`), never stored or logged.

**Heartbeat** (`src/domain/heartbeat/`): the first beat as soon as the first tunnel is ready (after one interval if no relay takes the engine), so the dashboard's first look already shows the engine reachable, then one every `MOCK_HEARTBEAT_INTERVAL_S` (default 60). `members` counts active members with at least one passkey ([owner.ts](src/domain/onboarding/owner.ts)): 0 while the owner has none, as with `MOCK_PASSKEYS=none`. Each beat takes the next `seq` (`max(last + 1, now in ms)`, persisted in `PTBK_DATA_DIR/heartbeat-seq` with a temporary file, `fsync`, rename and a directory `fsync` before the body is built), builds the body with `buildHeartbeat`, signs those exact bytes with `signHeartbeat` and posts them. A failed send is logged with its status code only, not retried, and not backfilled; a beat still in flight when the next is due makes that one skip. When the owner's first passkey is registered, one beat goes out at once (`beatNow`; after a beat in flight, if there is one), so the dashboard's tab turns ready within seconds; the interval's schedule is unchanged. With `onboarding@1` every beat carries `setup`: `pending` until the engine-driven setup completes, then `done`. The loop looks every second, and the beat after setup completes goes out at once the same way, even when nobody has the setup page open. The body is kept verbatim as the security panel's `lastHeartbeat` (also across `/__mock/reset`), from the moment it is sent. A `stale-timestamp` answer with `serverTime` records the clock skew (local clock minus `serverTime`, with when it was measured) and logs `heartbeat.clock-skew` with the seconds only; without `serverTime` the skew is unknown, and an accepted beat clears it. The security panel reports the body with the exact `Ptbk-Signature` value sent (`lastHeartbeat`) and the skew (`clockSkew`), and `GET /__mock/heartbeat` shows both too, with the last answer (`accepted`, `refused` with its status, or `unavailable`).

Figures: disk use of the data directory's file system and memory use (rounded to tens by `buildHeartbeat`), the 1-minute load per core as `low` (< 0.5), `medium` (< 1) or `high`, agents and active members from the engine API's state, and `update: none` until the UI loader (M-05) reports one. With `MOCK_STATS=scenario` disk, memory and CPU are fixed per scenario (`empty` 10/20/low, `small-team` 40/50/medium, `large-fleet` 70/80/high), so e2e can assert exact dashboard values.

## UI loader (M-05)

The mock engine is the reference UI loader for the engine team ([ui-loader.md](../../docs/engine-integration/ui-loader.md)). With `PTBK_UI_RELEASE_URL` set it checks the release store at startup, every `MOCK_UI_CHECK_INTERVAL_S` and on `POST /__mock/ui/check`, one check at a time ([ui-update.ts](src/domain/ui/ui-update.ts)): C-06's `verifyRelease` decides on the signed release with the trust policy from `PTBK_UI_TRUST_POLICY_FILE`, the persisted `firstSeenAt` and `lastAcceptedRevocationIssuedAt` (`PTBK_DATA_DIR/ui/update-state.json`) and the Sigstore verifier from `@ptbk/release-tools` against the pinned trusted root; then the `ui` artifact's SHA-256, the unpacked files against the manifest and the manifest's `engineApi` range against `ENGINE_API_VERSION`. A bundle that passes is unpacked into `PTBK_DATA_DIR/ui/<version>-<sha256 prefix>/` (read-only) and becomes active atomically; anything else is logged as `ui.refused` (reason and version only) and the previous bundle keeps being served. Every check's outcome, with the refusal and revocation reasons and, for `delay-not-elapsed`, when the release becomes eligible (`eligibleAt`, rounded up to the second), is the security panel's `ui.lastUpdateCheck`.

A revoked bundle stops being served at once: when a check accepts a revocation list (verified, fresh, not rolled back) that names the active bundle, the previous bundle comes back unless the list names it too, and otherwise no bundle is active and the app answers the plain 503 page. The withdrawn bundles are deleted and `active.json` is rewritten, so a restart does not bring them back. The check reports `refused` with reason `revoked` and the revoked version (logged as `ui.revoked-active` at error level), unless it goes on to install a newer release. A list that cannot be accepted never withdraws anything.

`/` and every other path no route takes serve the active bundle behind the gateway session: only files its verified manifest lists, content-hashed assets cached as immutable, `index.html` as the fallback for documents outside those paths and `/assets/`. The engine's own paths (`/api/`, `/auth/`, `/setup`, `/.well-known/`, `/__spike/`, `/__mock/`) are never served from a bundle, and a manifest listing a file there is refused at install. While no bundle is active (before the first install, or after a revocation withdrew every one) the answer is a plain 503 page, and the security panel shows the same placeholder bundle as before the first install. Every in-tunnel response carries the engine's headers ([security-headers.ts](src/domain/http/security-headers.ts)): `ENGINE_UI_CSP`, HSTS, COOP and CORP `same-origin`, `Referrer-Policy: no-referrer`, `nosniff`, `X-Frame-Options: DENY` and a `Permissions-Policy` that disables camera, microphone, geolocation, payment and USB (the microphone is allowed for the engine's own origin only with `MOCK_VOICE=enabled`). They are engine code; the bundle's manifest `csp` is never read. The security panel's `ui` shows the active bundle's version, archive SHA-256 and Rekor log index.

`verifyRelease` refuses every release without a fresh revocation list, so against a release store that has none the loader installs nothing. Staging's list is issued with `release:revocations` and uploaded by hand ([development.md](../../docs/development.md#revocation-list)); production has none yet ([open points](../../docs/engine-integration/README.md#open-points)). Tests and the e2e stack sign their own lists at run time.

## ACME TLS-ALPN-01 (M-03)

With `MOCK_CERT_SOURCE=acme` the engine obtains its certificate from an ACME CA (`PTBK_ACME_DIRECTORY_URL`) with TLS-ALPN-01 (RFC 8737), validated through the relay it is reachable by: no DNS record is ever touched. The relay routes the CA's validation connection by SNI exactly like a browser (it never looks at ALPN), so telling the two apart is the engine's job:

- A ClientHello router (`client-hello-router.ts`) sits in front of every TLS server inside the tunnel. It reads each stream's ClientHello with `@ptbk/protocol`'s parser (SNI and ALPN; never a local one), puts the bytes back (`unshift`) and decides (`domain/tls/alpn-dispatch.ts`): a hello offering exactly `acme-tls/1` for a hostname with a challenge pending goes to the responder; any other `acme-tls/1` hello (no challenge pending, mixed with other protocols, no SNI) is closed before a byte is written, as is anything that is not a ClientHello or does not complete within 10 s. Everything else goes to the normal TLS server. In `dev-ca` mode no challenge is ever pending, so every `acme-tls/1` hello is refused.
- The responder (`tls-alpn-responder.ts`) is a TLS 1.3 server offering only `acme-tls/1` that presents the challenge certificate (`acme-client`'s `createAlpnCertificate`, with the critical `acmeIdentifier` extension) and closes after the handshake. Challenge certificates live only in memory (`domain/tls/acme-challenges.ts`), registered just before the CA is asked to validate and removed as soon as the authorization settles, valid or not.
- The source (`acme-certificate-source.ts`) holds one certificate for every engine hostname, in `PTBK_DATA_DIR/tls/` (`certificate.pem`, `key.pem`, 0600; directory 0700), so a restart serves the same one. It starts ordering only once a relay reports the tunnel ready (the CA validates through it), renews once a third of the lifetime remains (`domain/tls/renewal-policy.ts`; looked at every 12 h and when due), retries failures after 5 s doubling to an hour while the current certificate keeps being served, and gives up on an issuance after 120 s. A renewal reaches new connections through `onChange`; open ones carry on with the old certificate.
- The issuer (`acme-client-issuer.ts`, `acme-client` 5.4.0) runs one order: account (created once per process), order for every hostname, the `tls-alpn-01` challenge per authorization, then a CSR from a fresh local ECDSA P-256 key (SANs only, no common name: an engine hostname can exceed its 64 characters) and the chain. It sits behind the `CertificateIssuer` port, so the production client, the engine team's choice (ADR 0014: `acme-client` is unmaintained and only for this Pebble spike), replaces this one file.
- The ACME account key is `PTBK_DATA_DIR/acme/account-key.pem` (ECDSA P-256, 0600, created once). It is not the engine key: the engine's Ed25519 identity signs only our own protocol, and the account is a separate identity at the CA.
- The ACME server's own TLS trust comes from the process (`NODE_EXTRA_CA_CERTS`), never from changing `acme-client`'s global axios instance. `acme-client`'s axios also honours `HTTPS_PROXY`.
- Logged: `acme.order-created` (identifier count), `acme.challenge-served` and `acme.challenge-valid` (hostname), `acme.certificate-issued` and `acme.certificate-loaded` (`notAfter`), `acme.issue-failed` (error name, stage, failures, retry delay, whether a certificate is still served), `tls.hello-rejected` (reason). Never a key, a key authorization, a token, an account URL or a CA response text.

The e2e `acme` scenario runs it against Pebble through the relays; the result and the Let's Encrypt staging runbook are in [docs/spike/acme-tls-alpn-01.md](../../docs/spike/acme-tls-alpn-01.md).

## Dev CA

For development and e2e the engine's certificates come by default from a local dev CA (`MOCK_CERT_SOURCE=dev-ca`). It must never be trusted outside development, so it is built to be harmless if it leaks:

- ECDSA P-256, valid one year, `basicConstraints` CA with `pathLen 0`, key usage `keyCertSign` and `cRLSign` only.
- A **critical name constraints** extension: it permits only `PTBK_ENGINE_DOMAIN` and the domains in `MOCK_DEV_CA_DOMAINS` (and their subdomains), and excludes every IP address (`0.0.0.0/0` and `::/0`). A browser that trusts it still refuses it for any other site.
- Leaves last 7 days (SANs for every engine hostname, `digitalSignature`, EKU `serverAuth`) and are re-issued when a third of their lifetime remains.
- No key is committed, printed or logged. With `MOCK_DEV_CA_CERT_FILE` and `MOCK_DEV_CA_KEY_FILE` set (X-01 generates them so Playwright and curl can trust the CA before the engine starts), the engine uses those and refuses a CA without the constraints above or a key file readable by group or others. Otherwise it generates the CA into `PTBK_DATA_DIR/dev-ca/` (`ca-cert.pem` and `ca-key.pem`, mode 0600, directory 0700) and reuses it, generating a new one when the permitted domains change or it is within 7 days of expiry.

To trust it locally, add `PTBK_DATA_DIR/dev-ca/ca-cert.pem` to the browser's or the system's trust store, or pass it to curl with `--cacert`. Remove it again when you are done.

## Operator commands and first-start output (M-08)

The host's commands reach the running engine over the **operator channel**: HTTP on the Unix socket `/tmp/ptbk-<hash>/op.sock` (mode 0600, in a 0700 directory named after the first 16 hex digits of the SHA-256 of the data directory's real path), never on the network. Not in the data directory itself: a socket path holds at most 103 bytes, and data directories under macOS's `/var/folders` temporary directory are longer. The engine and the commands both refuse that directory unless it is the engine user's own, 0700, and not a symbolic link, since a socket someone else planted there would answer the operator in the engine's name ([operator-socket.ts](src/adapters/operator-socket.ts), [operator-api.ts](src/domain/onboarding/operator-api.ts)). Shell access to the host is the trust level these commands need, so there is no API or UI route to them. The channel is always on and is not the dev-only control listener. At startup a socket left by a crashed engine is replaced, and one that still answers stops startup ("another engine is running from this data directory"): two engines from one data directory would hold the same key.

- `status [--json]`: engine ID, address, fingerprint, version, link (`local` until linked), each relay's state, certificate expiry, UI bundle version, update policy, whether the owner is set up, the last heartbeat (sent time, answer, clock skew) and what the address still lacks (a relay, a certificate). No key, secret, token or content, so it may be pasted into a ticket. Exits 1 when no engine answers.
- `connect --link <code>` against an engine that runs unlinked: after registering, it tells the engine over the socket to load `registration.json`, and the engine goes online without a restart (`mode: tunnel`, relays, heartbeat). On a terminal (and without `--json`) it then shows the first setup link: see "The first setup link" below.

The engine itself narrates installation.md's first-start steps ([startup-progress.ts](src/app/startup-progress.ts)): log events `engine.identity` (engine ID, hostname, fingerprint), `relays.connected` (counts), `owner.none` or `owner.set-up`, and `engine.ready` (the URL) once a relay routes the engine and a valid certificate is in place; registration, certificate and UI bundle keep their own events. When stdout is a terminal it also writes the same steps as human lines (`✓ Engine key ready` with the identity block, `✓ Linked to your Promptbook account`, `✓ Connected to 1 of 2 relays`, `✓ Certificate for …`, `✓ Engine UI … verified`, `Ready: https://…/`, then the setup link while there is no owner); a service whose stdout is a log stream gets only the events.

## Owner setup and passkeys (M-08)

The engine onboards its owner as installation.md's "The setup link" asks, on the MIT reference pages from [`packages/gateway-pages`](../../packages/gateway-pages/README.md) (copied next to the bundle by the build, `dist/gateway-pages/`).

- **Setup secret** ([setup-secret.ts](src/domain/onboarding/setup-secret.ts)): issued only while no active owner holds a passkey; 128 bits from the crypto `Random`, base64url, valid once and for 30 minutes, kept only as its SHA-256 in `PTBK_DATA_DIR/setup-secret.json` (0600) and compared in constant time. Each `setup-link` replaces it. A wrong, malformed, replaced or expired secret gets one answer, 403 `setup-link-invalid`; an owner who exists gets 409 `owner-exists` (public: the sign-in page says so too).
- **`/setup`**: the page reads `#<secret>` once and removes it with `history.replaceState`; it sends the secret only in the bodies of `POST /setup/options` (checks it, returns WebAuthn creation options) and `POST /setup/verify` (verifies the passkey, then spends the secret, so a cancelled prompt keeps the link usable). A query string on `/setup` is refused unread, and validation errors never echo a parameter name. Both endpoints allow 10 requests a minute per client IP. A verified registration makes the existing owner member the passkey's holder (an engine without one gets a new owner), signs them in, and audits `passkey.register` and `auth.sign-in` with the client IP from the tunnel.
- **Passkeys** ([passkey-gateway.ts](src/domain/gateway/passkey-gateway.ts), [simplewebauthn-ceremonies.ts](src/adapters/simplewebauthn-ceremonies.ts) on `@simplewebauthn/server`): discoverable credentials with user verification required and no attestation; the relying party is the hostname the browser reached. Challenges are the engine's own (32 bytes), single use, five minutes, bound to their ceremony (and a step-up to its session), at most 1,000 pending. Sign-in (`POST /auth/sign-in/options` and `/verify`) is usernameless; step-up (`/auth/step-up/options` and `/verify`) accepts only the session member's passkeys. Public keys and counters live in `PTBK_DATA_DIR/passkeys.json` (0600) and are put back into the in-memory state at start and after `/__mock/reset`. The engine API's lists decide: a passkey revoked through the API, or a member removed, no longer signs in.
- **`members`** in the heartbeat counts active members with a passkey, so it is 0 until setup and after `owner --reset`; by default (`MOCK_PASSKEYS=none`) the scenario starts without passkeys, a fresh engine waiting for its owner.

**The first setup link** ([setup-link-delivery.ts](src/domain/onboarding/setup-link-delivery.ts)). Onboarding is one command and a passkey: whichever foreground process is on a terminal when the engine first becomes reachable (a relay routes it, a valid certificate is in place, `/setup` is served) without an owner prints the setup link and, in a local desktop session, opens it in the default browser, then says "Opened in your browser. Create your passkey there." That is `connect --link` when it brings a running engine online (it waits for the address like `setup-link`, up to 10 minutes, with progress), or the engine itself run in the foreground (`node dist/main.mjs`, after `Ready:`). Only one setup secret is live at a time, so exactly one of them issues it: `connect` on a terminal tells the engine so with the link request (`POST /v1/link?setup-link=caller` on the operator socket), and the engine then only says that `connect` shows the link; a `connect` without a terminal or with `--json` leaves it to the engine. Nothing is printed or opened when stdout is not a terminal (the log gets only `setup-link.issued` with the expiry, never the link), when the engine has an owner, or after the first time (`owner --reset` prints its own link). A local desktop is macOS, or Linux with `DISPLAY` or `WAYLAND_DISPLAY`, and never a session with `SSH_CONNECTION` or `SSH_TTY`; `--no-open` or `PTBK_NO_OPEN=1` keep the browser closed. The browser is opened with `open` or `xdg-open` and the URL as their one argument, no shell ([browser-opener.ts](src/adapters/browser-opener.ts)); when that fails the link stays on the screen with a one-line note. Where the terminal renders OSC 8 hyperlinks (iTerm2, WezTerm, kitty, Ghostty, VS Code, VTE terminals, Windows Terminal; never through tmux or screen; `FORCE_HYPERLINK=1` or `0` overrides), the printed URL is one, with the URL as its visible text. `setup-link` stays the fallback: it makes a fresh link, which replaces the previous one.

Commands over the operator socket (exit codes: 0, 1 not running, 2 usage, 8 owner exists, 9 not ready):

- `setup-link [--no-wait] [--no-open] [--json]`: a fresh link `https://<hostname>/setup#<secret>` with its expiry, once a relay routes the engine, a valid certificate is in place and `/setup` is served; until then it waits up to 10 minutes and says what is missing (or, with `--no-wait`, says it and exits 9). It prints the link only to an interactive terminal, unless `--json` asks for it; never to the log stream, which logs only `setup-link.issued` with the expiry. On a local desktop it also opens the link in the browser, as above (never with `--json`). No QR code (it would need a dependency).
- `owner --reset [--yes] [--no-wait] [--no-open] [--json]`: after typing the first 8 characters of the engine ID (or `--yes`), every passkey and session ends, gateway tokens and stored credentials are dropped, the agents and data stay, both revocations are audited as the system, and a fresh setup link is printed under `setup-link`'s rules.

`bun run --filter @ptbk/mock-engine test:browser` runs [onboarding.spec.ts](test/browser/onboarding.spec.ts): Chromium with a virtual authenticator, through the in-test relay's SNI passthrough, registers the owner through `/setup#<secret>`, checks that the link is dead afterwards, follows a deep link from another site through the sign-in page's session check to its path, signs in with the passkey from a deep link and lands on it, finds no CSP or Trusted Types violation, and scans every log line of the run for the setup secret, the link code and keys.

## Commands

- `bun run --filter @ptbk/mock-engine dev`: run from source with `tsx watch`.
- `bun run --filter @ptbk/mock-engine build` then `start`: one bundled file, `dist/main.mjs`, for Node 24. `node dist/main.mjs [--no-open]` runs the engine; in the foreground on a terminal it shows (and opens) the first setup link itself.
- `node dist/main.mjs connect --link <link URL or code> [--no-open] [--json]`: creates the engine key if there is none, registers and exits. A link URL (`https://<dashboard>/link#<code>`, `@ptbk/protocol`'s `parseLinkUrl`) names the dashboard; if `PTBK_DASHBOARD_URL` names another one, it refuses before sending anything. A bare code goes to `PTBK_DASHBOARD_URL`, else to the dashboard of the stored registration. It prints the dashboard origin before registering (never the code or the URL), and `registration.json` keeps that origin, which later starts use without `PTBK_DASHBOARD_URL`. A stored registration makes no call. It prints the identity (engine ID, address, the fingerprint the dashboard shows) and the outcome as human lines, the outcome's next step on a failure and each retry's wait; with `--json` those go to stderr and stdout holds one report, `{ outcome, engineId, hostname, relays }` or `{ outcome, reason }`. Exit codes per class ([exit-codes.ts](src/app/exit-codes.ts), installation.md): 0 linked, 1 another failure, 2 usage, 3 link code refused, 4 identity refused (`engine-exists`, `engine-suspended`), 5 plan (`engine-limit`, `not-entitled`), 6 platform unreachable for the whole 30-minute retry window, 7 answer refused (`bad-signature`, a mismatched identity). A startup with `PTBK_LINK_CODE` that cannot register exits with the same codes. When it brings a running engine online from a terminal, it then waits for the address and shows the first setup link (see "The first setup link"); that does not change its exit code.
- `node dist/main.mjs status [--json]`: the running engine's one screen over the operator socket (above); exit 1 when no engine answers.
- `node dist/main.mjs setup-link [--no-wait] [--no-open] [--json]` and `node dist/main.mjs owner --reset [--yes]`: see "Owner setup and passkeys".
- `bun run --filter @ptbk/mock-engine register --link <link URL or code>` (or `node dist/main.mjs register --link <link URL or code>`): the same as `connect --json`, under the name X-05's dev stack and the dashboard e2e use.
- `bun run --filter @ptbk/mock-engine identity`: prints `{ engineId, enginePublicKey, hostname }` as JSON, creating the identity if missing (X-01 writes the relay's static registry from it). Needs `PTBK_DATA_DIR` and `PTBK_ENGINE_DOMAIN`.
- `bun run --filter @ptbk/mock-engine dev-ca`: creates the dev CA in `PTBK_DATA_DIR/dev-ca/` exactly as startup would (or reuses it) and prints its file paths and permitted domains as JSON, so tools can trust it before the engine runs (X-01). Reads `PTBK_DATA_DIR`, `PTBK_ENGINE_DOMAIN` and `MOCK_DEV_CA_DOMAINS`.
- `bun run --filter @ptbk/mock-engine dev-ca issue <cert-file> <key-file> <hostname>...`: also issues a 7-day leaf from that CA for another dev service, such as X-01's relays (key 0600). Only names under `MOCK_DEV_CA_DOMAINS` are accepted; engine hostnames are refused, so their certificates come from the engine alone.

## Layout

- `src/domain/`: the tunnel state machine (`tunnel/relay-link.ts`), the per-tunnel stream state (`tunnel/stream-mux.ts`), backoff, the rate limiter, the seed, scenarios and engine runtime (`state/`), the role policy (`authorization/`), gateway sessions (`gateway/`), the reply generator (`chat/`), fault plans and the faked scan and connection test (`faults/`), the simulation clock and the run and schedule simulators (`simulation/`), registration (`registration/`), the heartbeat (`heartbeat/`), the ClientHello dispatch, renewal policy and pending challenges (`tls/`), and the ports (`RelayDialer`, `IdentityStore`, `CertificateSource`, `CertificateIssuer`, `DashboardApi`, `RegistrationStore`, `SeqStore`, `SystemStats`, `EngineStatsSource`, `SetupSecretStore`, `PasskeyStore`, `PasskeyCeremonies`, `OperatorApi`, `BrowserOpener`, `Clock`, `Logger`, `Random`). No Node APIs; tested with fakes only.
- `src/adapters/`: `ws` dialer with TLS verification and pings, the `CONNECT` proxy client, the `Duplex` per stream, the file identity store, the dev CA (`dev-ca.ts` on a small DER writer in `x509/`), the ClientHello router, the TLS server (`tls-stream-server.ts`), the ACME side (`acme-*.ts`, `tls-alpn-responder.ts`), the tunnel throttle, the HTTP app with the spike, gateway and engine API routes and the fault middleware (`http/`), the control listener (`control-server.ts`), and the dashboard side: the HTTPS `fetch` (`https-fetch.ts`), the dashboard client (`fetch-dashboard-api.ts`), the registration and `seq` files and the host's figures, and the browser opener for the setup link.
- `src/app/`: config parsing, the commands (`connect`, `status`), their sentences and exit codes, the first-start narration, and the composition root, `startMockEngine(config, deps)`: tunnel streams → ClientHello router → TLS server → HTTP app (or the TLS-ALPN-01 responder) when given `certificates`; `onStream(handler)` replaces that handler in tests.
- `src/testing/`: fakes, a test PKI, a fake ACME issuer and a minimal in-process ACME server for `acme-client` (`test/acme-issuance.test.ts` runs the real client through the router and responder), an in-test relay with an SNI passthrough, a `CONNECT` proxy, an in-process engine harness (TLS server and HTTP app over linked duplexes), the engine API harness with a `fetch` over those connections, and a recorder that checks every engine API response against its strict schema. `test/`: integration tests across real sockets, including engine-api's shared client suite run through the in-test relay.

The DER writer is hand-rolled: the catalog's `@peculiar/asn1-*` packages resolve to two copies whose schema registries do not see each other, and `@peculiar/x509` needs a global `reflect-metadata` polyfill. Signing is `node:crypto` (OpenSSL), and the tests verify every certificate through `node:tls`.
