# @ptbk/dashboard

app.ptbk.io: account sign-up with passkeys, engine list, billing (Stripe), engine status, and links to engines. Also the HTTP API engines and relays talk to:

- `POST /v1/engines/register`: engine registration (spec, Interfaces 1; D-03)
- `GET /internal/v1/engines/{engineId}`: registry lookup for relays, relay-key authenticated (Interfaces 2; D-04)
- `POST /v1/engines/{engineId}/heartbeat`: signed heartbeat (Interfaces 4; D-05)
- `GET /v1/health`: `{ "ok": true, "environment": "<env>" }`, never cached

It stores no engine content, not even encrypted (AGENTS.md rule 2), and no page of it loads anything from an engine hostname: the CSP's `connect-src 'self'` and `frame-src 'none'` enforce that in the browser.

## Stack

One Cloudflare Worker serves a Vite single-page app and a Hono API ([ADR 0007](../../docs/adr/0007-frontend-stack.md), [ADR 0008](../../docs/adr/0008-hono-for-http-apis.md)). React with TanStack Router (file routes, code-split) and Query, Tailwind 4 with `@ptbk/ui` (tokens, components, forms, `DataTable`), Paraglide JS 2 for English and Czech. D1 through Drizzle with generated, guarded migrations ([ADR 0009](../../docs/adr/0009-drizzle-and-migrations.md)). Stripe through the official `stripe` package on its fetch client. Durable Objects for hourly rate limits (D-02), engine status (D-05), the ops monitor (I-04) and Web Risk's threat lists (I-08); Cron Triggers for monitoring (I-04) and abuse jobs (I-05).

The Worker renders nothing on the server. Every request except Vite's fingerprinted `/assets/*` runs the Worker first (`run_worker_first`), so the security headers (strict CSP with Trusted Types, HSTS, `no-referrer`, `nosniff`, COOP) are set on the HTML shell too. Under `vite dev` only, and only in `dev`, the CSP allows React Refresh's inline preamble and HSTS is left out; builds, the dev container and every test use the production policy. The SPA sets zod to `jitless` before any schema exists, because zod's `new Function` probe is a reported Trusted Types violation even though it is caught.

## Layout

```
src/
  worker.ts     Workers entry: default export { fetch }; the HourlyRateLimiter and EngineStatus Durable Object classes
  domain/       Pure logic, types and ports (Clock, Random, Logger, Authorizer). No I/O, no platform imports
  adapters/     Port implementations and in-memory fakes; adapters/db/ is the only place that imports drizzle-orm
  app/          Composition root (create-dashboard.ts), config, i18n for what the Worker renders, Hono app in app/http/
  shared/api/   The UI API: a zod route table used by both the Hono routes and the SPA client
  testing/      Fakes, the software WebAuthn authenticator and shared contract suites; never shipped
  client/       The SPA: main.tsx, routes/ (TanStack Router file routes), features/, core/ (shell plumbing), api/, i18n/
messages/       en.json and cs.json, the only place user-facing text lives
migrations/     drizzle-kit output, committed
scripts/        Migration guards, bundle budget check, dev container entry point
test/           Build output, catalogues, lint rules; test/http/ runs the HTTP app with real adapters (route table, auth flows)
```

ESLint keeps the boundaries: the SPA imports only `src/client`, `src/shared`, the generated messages, `@ptbk/ui` and `@ptbk/protocol`; Worker code never imports the SPA; `drizzle-orm` only inside `src/adapters/db/`, where Drizzle's relational query API (`db.query`, `relations`) is banned until Drizzle 1.0.

The Hono app mounts four routers: `/api` (the SPA's own API), `/v1` (engines), `/internal` (relays) and `/webhooks` (Stripe). Machine routes bind contracts from `@ptbk/protocol`; the UI API's contracts live in `src/shared/api/routes.ts`. Every error is RFC 9457 `application/problem+json` with a stable `code`, never a stack trace or an echo of the input; a 500 carries a `correlationId` that is also logged. An unknown path under one of the four prefixes is a 404 problem, never the SPA shell.

### Routes

Every route is a `defineRoute` contract (`src/shared/api/contract.ts`) mounted with the route binder (`src/app/http/bind-route.ts`), which refuses anything without a safeguard ([engineering.md](../../docs/engineering.md#request-handling-every-http-endpoint)). A contract declares `auth` (`public`, `session`, `stripe-signature`, `engine-signature` or `relay-token`, no default), a `permission` from `DASHBOARD_POLICY` for session routes, a per-IP `rateLimit` for every other non-session route and a per-relay one for `relay-token` routes, optionally an `engineRateLimit` keyed by the `:engineId` path segment, strict `input` schemas (params, query, the headers it reads, body) with a body size cap, and a strict `output`. Per request the binder applies, in order: the per-IP rate limit (429, also when the limiter cannot decide), the per-engine one if declared (429), for `relay-token` routes the relay key (401) and then the relay's own budget (429), the body cap (413), input validation (400), the session (401), then `Authorizer.can` on the actor's own scope (404 for what is not theirs, 403 with `step-up-required` or `recovery-cooldown`, else 403). `test/http/route-table.test.ts` enumerates the mounted Hono routes, fails on any route that bypassed the binder, and holds the allowlist of `public` routes. State-changing `/api` requests also pass the Fetch Metadata check (`Sec-Fetch-Site: same-origin`, else `Origin` equal to `DASHBOARD_ORIGIN`); machine routes never read cookies.

### Accounts, sessions, passkeys (D-02)

- **Signup is email first:** `signup/start` always answers 202 with the same body and mails a 15-minute link (`/signup#<token>`) or, for a known address, an "account exists" note; the lookup and the mail run after the response (`waitUntil`). `signup/options` and `signup/verify` register a passkey and create user, personal org, owner membership, passkey and session in one D1 batch.
- **Sign-in** is usernameless with discoverable passkeys; the returned `userHandle` must be the credential owner's random `webauthn_user_id`. User verification is always required; rpID and origin come from `DASHBOARD_ORIGIN`. A signature counter that does not grow from a non-zero value sets `counter_regressed_at`, logs `auth.passkey-counter-regression` with the user ID only, and fails the sign-in.
- **Challenges** are single use (deleted in the statement that reads them), live 5 minutes, are bound to the browser by `__Host-ptbk_chal` and, in token flows, to the email token's hash.
- **Sessions:** `__Host-ptbk_session` (`Secure`, `HttpOnly`, `Path=/`, `SameSite=Lax` so links from emails arrive signed in), 256-bit random, stored as SHA-256, new ID on every sign-in, idle 7 days, absolute 30 days, read on every request. A sign-in counts as a 5-minute step-up; `step-up/options` and `step-up/verify` renew it for actions with `requiresStepUp`.
- **Recovery:** `recovery/request` answers like `signup/start`; the link only allows `recovery/options` and `recovery/verify`, which add a passkey, revoke every session, set `recovered_at` (72-hour cooldown for `sensitive` actions) and mail a notice. Email tokens are 256-bit, stored as SHA-256, single use, 15 minutes, and a newer one replaces older ones.
- **Rate limits** (`RATE_LIMITS` in `src/domain/ports/rate-limiter.ts`, the one block of values; see [Rate limits](#rate-limits-i-05) for every anonymous endpoint): per-minute rules run on the Workers Rate Limiting binding (one binding per rule in `wrangler.jsonc`, checked against the code by a test); the hourly signup and recovery rules run on the `HourlyRateLimiter` Durable Object, because the binding only has 10 s and 60 s periods. Production keys are `HMAC-SHA-256(RATE_LIMIT_HMAC_KEY, rule ‖ IP or email)`, so no raw IP or address is stored; a counter is deleted when its window ends; a limiter error fails closed.
- **Email** goes through the `EmailSender` port: Cloudflare Email Service (`send_email` binding `EMAIL`, sender `EMAIL_FROM`), or in dev the fake outbox: `GET /api/__dev/emails?to=` returns one address's messages for e2e, without `to` every message, and the SPA page `/__dev/mailbox` lists them with their dashboard links clickable (X-06). Both exist only with the fake adapter: elsewhere the API is not mounted and the page answers not found. Templates are plain text in `messages/*.json`.
- **Platform admins:** `platform_role = 'admin'` is set by hand ([scripts/make-admin.md](scripts/make-admin.md)); admin actions need a fresh step-up and write `admin_audit_log`.

Config is parsed once in `src/app/config.ts` into a frozen `DashboardConfig`; nothing else reads `env`. It fails closed on a missing var, an unknown var or an unknown value, and refuses `fake` or `memory` adapters outside `dev`. Runtime objects in `env` (D1, ASSETS, service bindings) are wired by the composition root, not parsed as config.

### Billing (D-07)

Stripe sits behind the `BillingProvider` port (`src/domain/billing/billing-provider.ts`); everything else asks the `Entitlements` port (`allows(orgId, feature)`, `limit(orgId, quota)`, `null` = unlimited) and never a plan, a price or a Stripe object ([ADR 0017](../../docs/adr/0017-billing-entitlements.md)). `test/billing-boundaries.test.ts` fails if a module outside `src/domain/billing/`, `src/adapters/billing/`, `src/testing/` and the composition root imports `BillingProvider` or the stripe package, or if any module outside billing compares a plan or price ID.

- **Plans are configuration:** the `BILLING_PLANS` var holds the `none` plan (what an organization without a live subscription gets) and the paid plans (`id`, `name` in every locale, `stripeProductId`, `stripePriceId`, `features`, `quotas`, an optional display `price` of `amount` as a decimal string, `currency` and `interval`, and an optional `trialDays`, 1 to 30). The price is shown on `/billing` only; Checkout charges the Stripe price, so `price` must be copied from the price `stripePriceId` names (a Stripe price never changes), and without it the plan says the price shows on Stripe. Config parsing rejects duplicate plan or price IDs, unknown features or quotas, a missing quota and a missing `none` plan. Features and quotas are the closed lists in `src/shared/billing.ts`. Every value in `wrangler.jsonc` is a placeholder until pricing is decided; `none` follows the spec's "card on file before an engine".
- **Which plan applies:** `active`, `trialing` and `past_due` use the subscribed plan (no automatic downgrade, no automatic suspension); `unpaid`, `canceled`, no subscription and a price the catalogue does not know fall to `none`. Stripe statuses outside our list (`incomplete`, `paused`, anything new) map to `none`. Entitlements are computed from the stored row on every call, so a webhook changes them at once.
- **Trial with a card (D-10):** a plan with `trialDays` starts with a trial for an organization that never had one: Checkout gets `subscription_data.trial_period_days` and `payment_method_collection: 'always'`, so the card is on file before any engine. `organizations.trial_started_at` is set, once, by the first webhook that finds the subscription `trialing`; until then `GET /api/billing` says `trialAvailable` and the plan card offers "Start your {n}-day trial". An abandoned Checkout spends no trial. Stopping one person from opening many organizations for many trials is I-05's (card fingerprints in Stripe Radar).
- **Checkout and portal:** `POST /api/billing/checkout { planId, returnTo? }` and `POST /api/billing/portal` (`billing.manage`, owners) create the organization's Stripe customer on first use (the acting owner's email, metadata `org_id` only, an idempotency key per organization), then a Checkout session in subscription mode or a portal session, and return `{ url }` for a top-level navigation. Checkout returns to `/billing`, or to `/engines/new` with `returnTo: 'engines-new'`: an allowlist of pages, never a URL from the request. The organization is always the session's; no request names one. No Stripe.js on our pages, so the CSP stays `script-src 'self'`. `GET /api/billing` (`billing.read`) returns state, plan and its name, entitlements and the plans on offer with their names and any configured price; `GET /api/admin/billing` (platform admins) lists organizations that are `past_due`, `unpaid` or `canceled` for manual follow-up (suspension is I-05).
- **Webhooks:** `POST /webhooks/stripe` is a `stripe-signature` route: the route binder reads the raw body (capped at 512 KiB) and verifies it with `stripe.webhooks.constructEventAsync` on WebCrypto, 300-second tolerance, before anything parses it; failure is 400 `invalid-signature`. Handled types (`checkout.session.completed`, `customer.subscription.created|updated|deleted`, `invoice.paid`, `invoice.payment_failed`) fetch the subscription from Stripe again, so late or out-of-order delivery cannot apply stale data; other types answer 200 and change nothing. Event IDs go to `stripe_events` once handled (a repeat is skipped) and are pruned after 30 days. The upsert keeps an organization's open subscription over a late event about an older, ended one, and never overwrites a newer fetch with an older one. Logs carry event ID and type only.
- **Fake provider** (`adapters.billing = 'fake'`, dev and the e2e stack only): Checkout completes at once through the webhook's own handler, `trialing` until the trial's end when it grants one, and returns the `returnTo` page with `?checkout=success`; the portal returns `/billing`. Without `STRIPE_WEBHOOK_SECRET` it refuses every webhook; with one, it verifies like Stripe.
- **`/billing`:** without a plan, only the offers (Checkout with `returnTo: 'billing'`); with one, a single card with plan, status, period and entitlements. `GET /api/billing` counts the organization's active engines as `engines.max`'s `used`; custom domains are not counted yet. Back from Checkout it thanks once and drops `?checkout` from the URL, and while the webhook's plan has not arrived it says so and asks again every 3 s.
- **Stored:** `billing_customers` (org → Stripe customer ID), `subscriptions` (status, price ID, quantity, period end, cancel at period end) and `stripe_events` (ID, type, time). No cards, addresses or invoice contents; Stripe is the system of record.

### Engine registration (D-03)

- **Link codes:** `POST /api/engines/link-codes` (`engine.link`, owners) issues C-03's `LinkCode` (128 bits from `Random`, lowercase base32) for the session's active organization and answers `{ linkCodeId, linkCode, installCommands: [{ id, labelKey, command, docsAnchor }], installGuideUrl, expiresAt }` once, with the code filled into each configured install path; `/engines/new` shows the paths as tabs (D-11), each command as text in a code block with its own copy button, the requirement line and a link to its heading in the install guide, plus a 30-minute countdown. Switching tabs asks the API nothing. `link_codes` keeps only `SHA-256(code)`, looked up by hash for registration, and a random `id` that names the code for its status; no endpoint returns the code again and nothing logs it. Before issuing, the `EngineCreationPolicy` asks `Entitlements` for `engines.create` (else 403 `not-entitled`) and `engines.max` against the organization's active engines (else 403 `engine-limit`), then enforces at most 5 active codes and 10 per hour per organization (429 `rate-limited`); the SPA links the first two to `/billing`.
- **Link progress (D-10):** `GET /api/engines/link-eligibility` (`engine.link`) answers `allowed`, `not-entitled` or `engine-limit` through the same `EngineCreationPolicy` (the link-code limits stay issuance's) and the configured `linkCodeTtlS`, so `/engines/new` shows the plan step or the limit before any code. `GET /api/engines/link-codes/:linkCodeId` (`engine.link`) answers `pending { expiresAt }`, `expired` or `linked { engineId, hostname }`, never the code or its hash; another organization's ID is the same 404 as an unknown one. A redeemed code stays `linked` for good, so the page turns to linked even when the engine lost the registration's answer and its retry with the spent code got `invalid-link-code`. The `linkCodeId` grants nothing and may sit in the page's URL. The eligibility answer also carries `installGuideUrl`, for the troubleshooting links after a reload.
- **`/engines/new` (D-10):** asks `link-eligibility` on load: the plan step (the plans inline, Checkout with `returnTo: 'engines-new'`) or the limit banner, else it issues the code without a click and replaces the URL with `?link=<linkCodeId>`. Back from Checkout (`?checkout=success`) it polls eligibility every 3 s until the webhook's plan arrives. Below the command, the live checklist (`link-progress.tsx`) polls the code's status and then `GET /api/engines/:engineId` every 3 s while the tab is visible, and stops at ready or expiry: waiting (a troubleshooting hint after 2 minutes), linked with engine ID, address and fingerprint (a no-heartbeat hint after 3 minutes), online with the version, reachable through n relays (only while relays report, R-07), waiting for the owner (`members` 0), ready with "Open engine". One `aria-live="polite"` sentence names the current state. After a reload the progress resumes from `?link=`; the command is never shown again. Nothing is fetched from the engine's hostname.
- **Registration:** `POST /v1/engines/register` binds C-03's contract as an `engine-signature` route: per-IP limit (`registration-ip`, 20 per hour, on the Durable Object) → 4 KiB cap (413) → strict `RegisterEngineRequest` (400) → `registerEngine` (`src/domain/registration/`), which first checks `verifyRegistration` (401 `bad-signature`), derives the engine ID and hostname with the protocol, resolves the organization from the code (401 `invalid-link-code` for unknown, expired and used alike), then: a suspended or owner-revoked engine is 403 `engine-suspended`; one in another organization is 409 `engine-exists` with the code unused; one already active in the code's organization re-links idempotently (200, code consumed, `engineVersion` and `mode` updated); a new one passes the entitlement half of the policy (the link-code limits counted the code when it was issued) and is inserted. The code is consumed and the engine written in one D1 batch whose second statement depends on the first, so a lost race changes nothing and is retried once against fresh state. The answer is `{ engineId, hostname: <engineId>.<ENGINE_DOMAIN>, relays: RELAYS' relayIds }` with `Cache-Control: no-store`; logs carry the engine ID and the outcome only.
- **Stored:** `link_codes` (hash, organization, issuer, created, expires, used, redeeming engine) and `engines` (engine ID, organization, public key, hostname, mode, version, status and reason, timestamps). Suspension and revocation (D-06, I-05) set `status = 'suspended'` with a reason.

### Registry for relays (D-04)

- **Endpoint:** `GET /internal/v1/engines/{engineId}` (C-03's `registryPath`) is a `relay-token` route. `Authorization: Bearer <relay key>` is checked for its format first (`ptbk_rt_` and 43 base64url characters, else 401 without a query), then looked up by its SHA-256 among rows that are neither revoked nor expired (else 401); `last_used_at` is written at most once a minute, after the response (`waitUntil`). Then the relay's budget (`registry-relay`, 600 per minute per relay ID, Workers binding `RATE_LIMIT_REGISTRY`), the engine ID (400), and 404 for an unknown engine. The answer is C-03's strict `RegistryEntry`: the engine key, its default hostname plus every custom hostname whose claim passes `resolveRoutableHostnames` (others are dropped and counted in `registry.claims-dropped`), the claims, and `active` or `suspended`; nothing about the organization, its users or billing, and `Cache-Control: no-store`. A session cookie never authenticates it.
- **Ports:** `RegistryReader` (an unscoped read of an engine's key and status, for platform actors only), `EngineHostnameStore` (the active custom hostnames and their claims, from `engine_hostnames`; D-08) and `RelayTokenStore`.
- **Relay keys:** `relay_tokens` holds one row per key (ID, relay ID, SHA-256, created, expires, last used, revoked), so two live keys of one relay overlap during rotation. Logs name the row ID and relay ID, never the key.
- **Minting and rotation:** from `apps/dashboard`, `node scripts/mint-relay-key.ts --relay <relay hostname> (--local | --env staging | --env production) [--days <1-730>]` (default 365 days) writes the row through `wrangler d1 execute` and prints the key once; only its hash reaches wrangler and D1. Set it as the relay's `RELAY_REGISTRY_TOKEN`. To rotate: mint a new key, deploy it to the relay (I-01), then `node scripts/mint-relay-key.ts --revoke <row id> --env <env>` for the old row.

### Relay tunnel presence (R-07)

- **Endpoint:** `PUT /internal/v1/relays/presence` is a `relay-token` route like the registry read: the key is authenticated first (401 for a missing, malformed, unknown, revoked or expired key), then the relay's budget (`presence-relay`, 30 per minute per relay ID, binding `RATE_LIMIT_PRESENCE`), then a body cap that fits exactly `MAX_PRESENCE_ENGINE_IDS` (10,000) engine IDs as compact JSON (413 above it), then the strict body `{ v: 1, engineIds: EngineId[] }` from `src/shared/api/relay-presence.ts` (400 for an unknown field, another `v`, a malformed or repeated ID). The relay is the key's relay ID, never a body field; one not in `RELAYS` is 403 `unknown-relay`, since engines never dial it. Answers 204. Relays send their full list of ready tunnels every 60 s and within 5 s of a change ([relay README](../relay/README.md#tunnel-presence-r-07)).
- **Stored** in D1, not in the engines' `EngineStatus` objects: a report is one batch of four statements whatever its size (the IDs travel as one JSON parameter through `json_each`), writing only the relay's report time and the rows that changed, where per-engine objects would take one call per engine per relay per minute. `relay_presence_reports` (relay ID, reported at) and `relay_presence` (relay ID, engine ID). Each report replaces its relay's rows; a relay whose last report is 3 minutes old stops counting (`PRESENCE_EXPIRY_MS`), and the next report from any relay deletes it with its rows. No history, no addresses, no connect times.
- **Read:** `GET /api/engines` asks once for the whole list and `GET /api/engines/:engineId` once for its engine, beside the status reads, so the D-06 fan-out is unchanged. `EngineView.reachableRelays` is the number of live relays whose last report lists the engine, or `null` when no relay report is live or presence could not be read (logged as `presence.read-failed`): then nothing is known, and an engine is never called unreachable on missing data. The SPA shows "Reachable through {n} relays" or "Not reachable: no relay connection" for an online engine only, under its status in the list and as "Reachability" on the engine page.

### Enterprise custom domains (D-08)

- **Flow:** set up by hand with each Enterprise customer ([runbooks/custom-domain.md](runbooks/custom-domain.md)). A platform admin opens `/admin/engines/$engineId/hostnames` (or enters the engine ID on `/admin`), adds the hostname with the engine's claim, hands the customer the CNAME target shown next to it, then runs "Check DNS". Only `active` rows reach the registry.
- **Endpoints** (session, platform admins only): `GET /api/admin/engines/{engineId}/hostnames` (`admin.hostnames.read`) lists the rows with `expectedTarget`, C-03's `expectedCnameTarget` (`<engineId>.<ENGINE_DOMAIN>`, never a relay name). `POST …/hostnames { hostname, claimSig }`, `POST …/hostnames/{hostname}/check` and `POST …/hostnames/{hostname}/remove` need `admin.hostnames.manage`, which requires a passkey step-up within 5 minutes. An unknown engine or hostname is 404.
- **Add** (`addCustomHostname`, `src/domain/custom-hostnames/`), in order: normalise (lowercase, one trailing dot dropped, IDNs to A-labels through the URL parser, then the protocol `Hostname` rules, which refuse IP literals, wildcards and names over 253 characters; 400 `invalid-hostname`); not `ptbk.io`, the engine domain or a relay hostname from `RELAYS`, nor under one (400 `reserved-domain`); the engine exists (404); not assigned to any engine (409 `taken`); the claim passes C-03's `resolveRoutableHostnames` against the engine's key (400 `bad-claim`); at most 31 per engine, what a registry entry can carry (409 `limit-reached`). Stored as `pending-dns`.
- **Check DNS** (`checkCustomHostname`): a `DnsResolver` port answers like the relay's (exactly one CNAME is `cname`, none or NXDOMAIN is `none`, anything else `error`). The production adapter is DNS over HTTPS with the JSON API (`https://cloudflare-dns.com/dns-query`, 3-second timeout). The row becomes `active` exactly when the target is `expectedTarget`, and goes back to `pending-dns` on any other definite answer; `error` changes nothing. The response carries what DNS found, which the page shows on a mismatch. The dashboard never re-checks on its own: relays do, every registry refresh.
- **Audit:** every change (add, activate, deactivate, remove) writes `admin_audit_log` in the same D1 batch, with `target_type` `engine-hostname` and `target_id` `<engineId>/<hostname>`.
- **Stored:** `engine_hostnames` (hostname, engine, organization, the claim signature, status, last DNS check, created, the admin who added it). Organization owners see the active ones on the engine page (D-06) through `EngineHostnameStore`; the org-facing `engine.hostnames.manage` action has no route in v0.

### Heartbeats and engine status (D-05)

- **Endpoint:** `POST /v1/engines/{engineId}/heartbeat` (C-03's `heartbeatPath`) is an `engine-signature` route whose body is `RAW_BODY`: the handler gets the exact bytes, and no JSON middleware parses them first. In order: per-IP limit (`heartbeat-ip`, 600 per minute, binding `RATE_LIMIT_HEARTBEAT`), per-engine limit (`heartbeat-engine`, `HEARTBEAT.perEngineLimit` per minute, on the `HourlyRateLimiter` Durable Object because a binding's limit is fixed in wrangler.jsonc), 4 KiB cap (413), engine ID (400), the engine's D1 row (404 unknown, 403 `engine-suspended`), then the engine's `EngineStatus` Durable Object runs C-03's `verifyHeartbeat` against its stored `lastSeq`, with the Worker's clock at receipt as `now`. Answers: 204; 401 `bad-signature-header` (missing, malformed or another scheme) or `bad-signature`; 400 `invalid-body` or `engine-mismatch`; 409 `replayed-seq`; 401 `stale-timestamp` with `serverTime` (RFC 3339 UTC). Errors are C-03 `ProblemDetails`. Only refusals are logged, with the engine ID and the outcome kind.
- **`EngineStatus`:** one SQLite-backed Durable Object per engine, `idFromName(engineId)`, binding `ENGINE_STATUS`, migration tag `v2`. Its storage is its own, not D1's. It keeps C-03's numbers and enums (`version`, `uptimeS`, `diskPct`, `ramPct`, `cpuLoad`, `update`, `agents`, `members`) with `seq`, `ts` and the time received, plus the engine's organization from D1; never the signature, the address or a header. RPC: `recordHeartbeat`, `getStatus` (`never-seen`, or `online`/`offline` with `lastSeenAt`, `lastSeq`, `payload`, `offlineSince`), `reset`. The behaviour is `src/domain/status/` (pure transitions in `engine-status.ts`, the service in `engine-status-service.ts`); the class only adapts storage.
- **Offline alerts:** every accepted heartbeat moves the alarm to `missedLimit × intervalS + graceS` later (3 × 60 s + 15 s by default; `HEARTBEAT` var). When it fires, the engine is `offline` and the organization's owners with a verified email (`AlertRecipients`, D1) get one `engine-offline` email in their locale: engine ID, hostname, last seen (UTC), link to the engine page. A send that fails is retried for whom it failed after 1, 5 and 15 minutes, then given up; the next heartbeat brings the engine `online` and arms the next outage. Thirty days after the last heartbeat the alarm deletes everything but the state and `lastSeenAt`.
- **Online and back-online emails (D-12):** the first accepted heartbeat of an engine whose `members` is 0 owes the same recipients one `engine-online` email ("finish setup on the engine's terminal", never a setup link); the first heartbeat after an outage whose offline email went out (or after the retention purge) owes one `engine-back-online` email with the last heartbeat before the outage and the first after it. The heartbeat only stores what is owed and moves the alarm to now; the alarm sends it with the offline alert's retries. A new outage drops a notice still owed. Before every send the alarm reads the engine's row in D1: an engine revoked, suspended or removed since is told about to nobody, and its outage stays unalerted, so it owes no back-online email either. The engine page of an offline engine shows when it was last seen, `promptbook-engine status` to copy and a link to the guide's troubleshooting; the link is `INSTALL_GUIDE_URL` (D-11) from `GET /api/install-guide` (session, `engine.read`), and the command's name lives in `src/client/features/engines/engine-guide.ts`.
- **Ports:** `HeartbeatEngineReader` (an unscoped read of an engine's organization, key and status), `EngineStatusDirectory` (the objects, by engine ID), `EngineStatusStorage` (one object's storage and alarm), `AlertRecipients`. In-memory versions in `src/testing/memory-engine-status.ts`; `heartbeat-flow-suite.ts` runs on them and on D1, and `engine-status-object.workers.test.ts` runs the real object through the built Worker.

### Engine list and status (D-06)

- **Endpoints:** `GET /api/engines` and `GET /api/engines/:engineId` (`engine.read`, owners) read the session's organization's engines through the org-scoped `EngineStore` (another organization's engine is the same 404 as a missing one), then ask each engine's `EngineStatus` object for `getStatus()` and D-04's `EngineHostnameStore` for its active custom hostnames, at most 10 engines at once and 2 seconds per status call (`src/domain/engines/engine-overview.ts`); a status object that times out or fails shows that engine as `unknown` and logs only its ID. The answer is registry data and heartbeat numbers only: engine ID, default and custom hostnames, mode, registered version, `deriveEngineDisplayStatus` (`suspended` wins, then `never-seen`, `owner-pending` for an online engine whose heartbeat counts no member yet, `online`, `offline`, or `unknown`), who suspended it, last seen, and the last heartbeat field by field as D-05 stores it.
- **Revocation:** `POST /api/engines/:engineId/revoke` (`engine.revoke`: owners, `sensitive` so the 72-hour recovery cooldown denies it, `requiresStepUp`) sets `status = 'suspended'`, `status_reason = 'owner-revoked'` and appends one `org_audit_log` row (`engine.revoke`, the acting user, the engine) in one D1 batch; revoking an engine already revoked changes nothing and logs nothing. Relays drop it at their next registry refresh, heartbeats and re-registration answer 403 `engine-suspended`. There is no undo.
- **Active organization:** `POST /api/session/active-org { orgId }` (`session.manage`) moves the session only to an organization the user is a member of (404 otherwise) and answers the new `GET /api/session` view. The header's organization switcher uses it.
- **Timer port:** deadlines go through `Timer.wait(ms, signal)` (`systemTimer` in the Worker, a manual timer in tests), so the status timeout is tested without sleeping.

### Monitoring and scheduled jobs (I-04)

- **Scheduled dispatcher:** the Worker's one `scheduled` handler (`src/app/scheduled.ts`) runs, for the cron expression that fired, every job in `scheduledJobs` (`src/app/scheduled-jobs.ts`), side by side, each with 50 s and an abort signal (`src/domain/scheduled/scheduled-dispatcher.ts`). A failed or timed-out job is logged (`cron.job-failed`), counted, and recorded in the `OpsMonitor` object, where three failures in a row raise `cron-job-failing`; it never stops the other jobs. After every job, the alerts queued in `OpsMonitor` are delivered; a failed send stays queued for the next run, 5 attempts in all. Outside dev a run without valid config, `MONITORING` or the email binding, or for a cron without jobs, fails instead of passing quietly. To add a job (I-05): implement `ScheduledJob` (`name`, `cron`, `run({ scheduledTime, signal })`), add it to `scheduledJobs`, and put its cron into `triggers.crons` of every environment; `scheduled-jobs.test.ts` fails if they disagree.
- **`relay-monitor`:** with `MONITORING` set, every minute: each relay's `/healthz` and `/metrics` over HTTPS on its own hostname with its metrics token (`RELAY_METRICS_TOKENS`), the Worker's own `/v1/health`, and the dashboard's counters of the last 10 minutes; then the alert rules (`src/domain/monitoring/alert-rules.ts`) on the state in the `OpsMonitor` Durable Object (binding `OPS_MONITOR`, one instance `ops`, migration `v3`), and alerts by email to `MONITORING.opsEmail` (`ops-alert`, English only). Without `MONITORING` (dev, the local stack) no job runs.
- **Metrics:** `DashboardMetrics` writes to Workers Analytics Engine (`OPS_METRICS`, dataset `ptbk_ops_<env>`) outside dev and to memory in dev, where the monitoring job reads them back; elsewhere it reads them with Analytics Engine's SQL API (`ANALYTICS`, `ANALYTICS_API_TOKEN`). Requests are counted by route template, never by path.
- Rules, thresholds, retention, credentials and queries: [docs/runbooks/observability.md](../../docs/runbooks/observability.md).

### Abuse controls (I-05)

- **Suspension:** `/admin/engines/$engineId` (reached by engine ID from `/admin`) shows any organization's engine (`GET /api/admin/engines/:engineId`, `admin.engine.read`) and suspends it or lifts a platform suspension (`POST …/suspend`, `POST …/unsuspend { reason }`, `admin.engine.suspend`: platform admins with a step-up within 5 minutes). The reason (1–500 characters) goes to `admin_audit_log` (`admin.engine.suspend` / `admin.engine.unsuspend`, target `engine`), written in the same D1 batch as the change and only when the engine changes; `engines.status_reason` is the fixed `platform-suspended`, so the owner sees "suspended by Promptbook" with the abuse address, never the reason. Unsuspend lifts only `platform-suspended`: an engine its owner revoked (`owner-revoked`, D-06) answers 409 `owner-revoked` and stays revoked, also when the owner revoked it while it was suspended. A suspended engine's registry entry is `suspended` with its default hostname only (custom hostnames withheld), so relays close its tunnel within one registry TTL and refuse new ones; registration and heartbeats answer 403 `engine-suspended`.
- **Abuse contact:** `ABUSE_EMAIL` is shown on the public `/abuse` page (English and Czech: how to report, what we can and cannot see, what a suspension does), by `GET /api/abuse-contact` (public, `public-read-ip`), on a suspended engine's page, and as the `Contact` of `GET /.well-known/security.txt` (RFC 9116, plain text: `Contact`, `Expires` 180 days after the current UTC day, `Policy` = `/abuse`, `Preferred-Languages: en, cs`, `Canonical`). The file is rendered from the live config, so its `Expires` rolls forward and it cannot outlive what it states. Abuse alerts go to the same address.
- **Monitoring jobs** (with `MONITORING`, every 15 minutes, `*/15 * * * *`, in their own invocation): `ct-watch` reads crt.sh and Cert Spotter for the engine domain (`src/adapters/abuse/`), keeps every certificate once in `ct_certs` (keyed by issuer, validity start and names, so a precertificate and its certificate, or one issuance in both sources, count once) with each source's cursor in `ct_cursors`, and raises `ct-wildcard`, `ct-foreign-issuer` (issuer `O=` not in `allowedIssuers`), `ct-unknown-hostname` (a name under the engine domain that is no engine's default hostname) once per certificate, and `ct-issuance-spike` once when an engine passes `issuanceSpike.limit` certificates within `issuanceSpike.days`; one source failing or timing out (20 s) only degrades the run, both failing fails it. `public-face` visits the default hostnames of the active engines checked longest ago (`perRun` per run, 6 at a time, 8 s each), as an anonymous visitor (no cookie, same-host redirects only, the first 64 KiB read for the title), compares status, final path, media type and title with the known sign-in fingerprints (`public_face_checks` keeps the result and the fingerprint 30 days, never the page) and tracks `public-face-mismatch` per engine: it fires on a mismatch, resolves on a match, and an unreachable engine changes nothing. It never suspends anything. `abuse-feeds` (with `WEB_RISK_API_KEY`; outside dev a missing key logs `abuse-feed.unconfigured` every run) checks every active engine's default hostname against Google Web Risk through its Update API (I-08, `src/adapters/abuse/web-risk-*.ts`): the `MALWARE`, `SOCIAL_ENGINEERING` and `UNWANTED_SOFTWARE` hash-prefix lists (at most 2^20 prefixes each) live in the `WebRiskLists` Durable Object and are diffed when Google's `recommendedNextDiff` has passed; a hostname's expressions (the host and its parent suffixes, path `/`) are canonicalised and hashed as Web Risk specifies and matched locally, and only a prefix hit costs a `hashes.search` (billed per call, at most 50 per run, answers cached in the object until Google's positive and negative expiry). Google sees hash prefixes, never hostnames, and the key travels only in `X-Goog-Api-Key`. A list that is missing or more than 2 h past its due diff fails the feed, which leaves the alerts as they are. Alerts of all three go through I-04's `AlertSink` to `ABUSE_EMAIL` (`[ptbk abuse]`, `src/domain/monitoring/alert-routes.ts`); a failing job alerts ops. Runbook: [docs/runbooks/abuse-takedown.md](../../docs/runbooks/abuse-takedown.md).

### Tenancy and authorization

An organization owns engines and billing; users join through a membership with a role ([ADR 0006](../../docs/adr/0006-organizations-and-roles.md)). Every authorization decision goes through `Authorizer.can(actor, action, resource)` in `src/domain/authz/`, deny by default, with one policy table in `policy.ts`. Rules for every later task:

- Add the action to `DASHBOARD_POLICY`; handlers and components check actions, never role names.
- Org-owned repositories take `orgId` as the first argument and put it in every `where`. Each org-scoped adapter test includes "org B cannot read or change org A's rows".
- Timestamps are integers in milliseconds since the Unix epoch.

### SPA: screens, guards, passkeys (D-09)

- **Routes.** `_app` is the signed-in layout (`/` redirects to `/engines`, `/engines/$engineId`, `/engines/new`, `/billing`, `/account`, `/admin`, `/admin/billing`, `/admin/engines/$engineId/hostnames`): its guard reads `GET /api/session` through TanStack Query and sends anyone without a session to `/signin?returnTo=…`; `returnTo` only ever holds a same-origin path (`safeReturnTo`). `_auth` is the signed-out frame; under it `_guest` (`/signin`, `/signup`) sends a signed-in person home, while `/recover` stays open. `/admin` and everything under it answer "not found" unless `platformRole` is `admin`. A 401 on any later call clears the cache and returns to sign-in.
- **Shell** from `@ptbk/ui`: skip link, org name (a switcher menu only with more than one membership), navigation by the session's org permissions (`features/shell/navigation.ts`, never role names; `/admin` by the platform role; the current page has a background, not only a colour), a language switch (`LanguageSwitch`), the user menu (theme, sign out, confirmed by a toast), route-level error, pending and not-found states. An unknown URL, and `/admin` for anyone else, renders "not found" inside the frame of whoever asks: the signed-in shell or the signed-out one.
- **Emailed tokens** (`/signup#…`, `/recover#…`): the route's `beforeLoad` moves the fragment into an in-memory holder and replaces the URL without it before anything renders; the page takes it into its state. It is never in history, storage or a later URL (`test:csp` checks).
- **Passkeys** go through the `PasskeyAuthenticator` port (`features/passkeys/`): `@simplewebauthn/browser` in the app, a fake in tests. Its output is narrowed to the API's schemas, so an unrequested extension result never makes a strict server refuse it. `classifyPasskeyError` is the one table from browser errors to reasons (cancelled, not allowed, no authenticator, already registered, unsupported), and `ceremony-messages.ts` the one place they become words; every screen shows them with a retry.
- **Mutations** use `useAppMutation`: a `step-up-required` answer opens the step-up dialog (passkey assertion in place) and retries; an action already confirmed in a dialog (revoking an engine) passes `stepUp: 'in-place'` instead, so the passkey check runs from that dialog's own button (labelled for it while the session's `steppedUpUntil` has passed) and a failed check is shown there, never as a second modal; failures become toasts (`recovery-cooldown` with its end), nothing is optimistic (adding a passkey needs the authenticator; removal and "sign out everywhere" must not pretend).
- **Engines (D-06).** `/engines` is the landing page: a `DataTable` (virtualised past 50 rows) of one line per engine, ordered by what needs attention (offline, unknown, owner setup pending, online, never seen, suspended); revoked engines sit behind a "Show revoked engines (n)" toggle unless nothing else is left. Each row has the `TrustMark` fingerprint (`deriveEngineFingerprint` from `@ptbk/protocol`, the same function and vectors as engine-ui's security page and the engine's terminal; its code in the accessible name) with the engine's label (`engineLabel()`), status in words and an icon with when it was last seen, the hostname on one line (cut off with an ellipsis when narrow, in full in its tooltip and copy button), and the version with any pending update; for an engine that is not reporting, the version is muted and no update is claimed. `/engines/$engineId` opens with a summary (name, status, last seen, version, "Open engine"), then a warning banner for an offline engine (what to run, troubleshooting), the identity card (large fingerprint with its code, engine ID, address that breaks only after a dot, connection, version at linking, when linked), the last heartbeat as received behind a disclosure, and "Revoke engine" behind a confirmation that states the consequence and asks for the engine ID's first 8 characters. An unknown engine ID answers "Engine not found" with a way back to the list. Both refetch every 60 seconds while visible and on window focus. The only reference to an engine hostname is the "Open" link: `https://<hostname>/`, `target="_blank"`, `rel="noopener noreferrer"`, `referrerpolicy="no-referrer"`; nothing is fetched, framed or prefetched from it (client tests check the DOM and that the client calls only `/api/*`).
- `/account` names a passkey by its provider: registration stores the authenticator's AAGUID (the model, not the device; null when it is all zeros), and `GET /api/passkeys` maps it to a name from `src/domain/auth/passkey-providers.ts`, a short list of AAGUIDs each vendor publishes itself (the community AAGUID list has no licence, so it is not copied). An unknown or absent AAGUID reads "Passkey". Each row also shows its creation date, last use (a passkey created at sign-up or recovery has signed in, so it counts as used) and where it lives from `backedUp` (synced or one device).

### API client

The SPA calls `/api/*` only through `src/client/api/api-client.ts`, a small fetch client over the shared route table, wrapped in TanStack Query hooks; components never call `fetch`. It parses every response with the contract's schema, tolerantly: fields the contract does not know are dropped at any depth, known ones are fully validated (AGENTS.md rule 5). It returns an outcome union (`ok`, `problem` with a declared code, `invalid-response`, `network-error`). Output schemas stay strict, and the HTTP tests parse every response with them, so the server never sends an undeclared field.

We chose this over Hono's RPC client `hc`: each HTTP contract stays explicit as data (method, path, schemas, error codes), the same style as `engine-api`'s `EngineApiClient`; responses are validated at runtime, not just typed; and the SPA does not depend on the inferred type of the whole Hono app, which slows type-checking as the API grows and lets a server refactor change the client silently. The cost is writing the route table by hand, which is the point.

### i18n

Paraglide compiles `messages/*.json` into typed functions at build time (no runtime parser, no eval); its message-format plugin is loaded from `node_modules`, never from a CDN. The SPA picks the locale from the `ptbk_locale` cookie, then the browser's languages, then English; signing in or signing up applies the account's saved locale and writes it to the cookie (recovery keeps the language it was done in). `<html lang>` follows the locale; every header has a `LanguageSwitch` (the code, "EN ▾"); the theme sits in the user menu when signed in and in its own menu on the signed-out pages. `@ptbk/ui`'s strings come from the same catalogues (`core/ui-messages.ts`). What the Worker renders itself (emails from D-02) uses `resolveRequestLocale`: user locale, cookie, `Accept-Language`, English. ESLint rejects literal text in `src/client/**/*.tsx`, and any HTML sink or string `style` attribute in `src/client` (the CSP has `trusted-types 'none'`).

## Migrations

The schema is TypeScript in `src/adapters/db/schema.ts`. After changing it, run `bun run db:generate --name <what>` and commit the SQL and `migrations/meta/`. Nobody runs `drizzle-kit push` or `migrate`, and nobody writes schema SQL by hand; a data backfill is its own reviewed migration from `drizzle-kit generate --custom`. Migrations are applied with `wrangler d1 migrations apply DB` (`--local` here; staging and production through I-03).

**Expand, deploy, contract.** Migration and deploy are not atomic and `wrangler rollback` does not undo a migration, so every migration must work with the Worker that is live: add the new shape (expand), deploy code that uses it, and remove the old one (contract) in a later PR once nothing reads it.

`db:check` enforces:

- **Layout:** `migrations/` holds only files drizzle-kit journaled.
- **Drift:** `drizzle-kit check` and `drizzle-kit generate` on a copy of `migrations/` must produce nothing, so a schema change without its migration fails.
- **Destructive changes:** a migration with `DROP TABLE`, `DROP COLUMN`, any `RENAME` or a table rebuild (`__new_` tables, `PRAGMA foreign_keys=OFF`) fails unless its first line is `-- contract: <what is removed>; unused since <migration or PR>`. That marker is the only hand edit allowed in a generated file; reviewers check the contract step follows the rule above. If drizzle-kit rebuilds a table for what looks like a small change (a new CHECK, a changed default), prefer a different schema change over the marker.

`src/adapters/db/schema-allowlist.test.ts` compares every table and column after all migrations with a checked-in allowlist, so each new column is a visible review point for "no engine content".

## HTTPS development and the dev container

Passkeys need a secure context on a real hostname. Both modes take a certificate and key by path; for a local pair:

```sh
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 30 \
  -subj "/CN=app.ptbk.test" -addext "subjectAltName=DNS:app.ptbk.test" -keyout key.pem -out cert.pem
```

`dev:https` runs `vite dev --mode https`; the Worker's `DASHBOARD_ORIGIN` (and so the WebAuthn rpID) follows the served origin:

```sh
DASHBOARD_ORIGIN=https://app.ptbk.test:5173 DASHBOARD_TLS_CERT=cert.pem DASHBOARD_TLS_KEY=key.pem bun run dev:https
```

`Dockerfile.dev` builds the app and runs the built SPA and Worker in workerd (`vite preview` through the Cloudflare plugin), with the committed migrations applied to a local D1 at start and the production CSP. The origin is set at start, so one image serves any dev hostname; `DASHBOARD_VARS`, a JSON object of vars, overrides others the same way (`scripts/dev-container-vars.ts` writes them into the built Worker config, since `.dev.vars` holds only strings). X-05 runs it in the e2e stack (`e2e/compose.dashboard.yaml`):

```sh
docker build -f apps/dashboard/Dockerfile.dev -t ptbk-dashboard-dev .
docker run --rm -p 443:443 -v "$PWD/tls:/tls:ro" \
  -e DASHBOARD_ORIGIN=https://app.ptbk.test -e DASHBOARD_TLS_CERT=/tls/cert.pem -e DASHBOARD_TLS_KEY=/tls/key.pem \
  ptbk-dashboard-dev
```

## Bundle budgets

`bundle-budgets.json` caps the gzipped JavaScript of the entry (with its static imports) and of each route chunk; `scripts/check-bundle-budgets.ts` reads Vite's build manifest and fails the test run when one is over. A route that needs more gets its own entry under `routes`, keyed by its source file.
