# Apply checklist

The code for every task lands before the cloud accounts exist ([local-first](README.md#current-priority-local-first)). What is left needs a credential, an account, a domain or a person: these are the **Apply** steps. Each brief lists its own under "Apply (needs credentials)"; this page collects them and every credential they need, in the order to run them.

Each Apply step is a PR or a runbook run with `Refs: <task>`. Secrets go into the place named below (a password manager, a GitHub environment secret, `wrangler secret put` or a host credential file), never into the repo, a PR, a log or this page.

## Apply steps, in order

| #   | Task | Step                                                                                                                                                                       | Needs                                                                |
| --- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | I-02 | Apply the staging stack; set NS and DS at the registrar; write the D1 IDs into `wrangler.jsonc`; verify the deploy token; then production once the engine domain is chosen | Cloudflare accounts, domains, IaC token, state bucket and passphrase |
| 2   | D-02 | Enable Email Service, set `EMAIL_FROM`, send a test email and check SPF, DKIM and DMARC, then set `dmarc_policy = "reject"`; set `RATE_LIMIT_HMAC_KEY`                     | Step 1                                                               |
| 3   | D-07 | Manual Stripe test-mode check: Checkout completes, webhook arrives, portal opens (`stripe listen --forward-to` against `wrangler dev`; no staging needed)                  | Stripe test account                                                  |
| 4   | X-03 | First `ui-release.yml` dry run (`ui-v0.0.0-dryrun.<n>`), verified with `release:verify`                                                                                    | GitHub plan decision, `UI_STAGING_RELEASE_KEY`, release bucket       |
| 5   | I-01 | Create, verify, destroy and recreate the staging relay; run the e2e suite against it; later the production hosts                                                           | Hetzner, SSH keys, step 1, a relay token from D-04                   |
| 6   | I-03 | Staging deploys of the dashboard and the relay; rolling deploy with a broken image; approvals for production and the UI release                                            | GitHub environments, deploy token, deploy key, steps 1 and 5         |
| 7   | I-04 | Staging dashboards and the relay-down alert; journald retention on the hosts                                                                                               | Steps 5 and 6, ops mailbox, monitoring backend                       |
| 8   | I-05 | `/abuse` live on staging; PSL request; Let's Encrypt rate-limit request; abuse-feed keys; Search Console and Safe Browsing setup                                           | Engine domain, `abuse@`, feed vendor                                 |
| 9   | I-07 | Health checker against the staging relays                                                                                                                                  | I-07 decision, step 5                                                |
| 10  | M-03 | One manual run against Let's Encrypt staging through a staging relay (no account needed: ACME keys are self-generated)                                                     | Steps 1 and 5                                                        |
| 11  | I-06 | Internal security review on a staging that matches production, after the key ceremony                                                                                      | Everything above, the reviewers                                      |
