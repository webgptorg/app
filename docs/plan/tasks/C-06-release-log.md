# C-06. Release log entry and verification (engine and UI artifacts)

- **Lane:** Contracts · **Module:** `packages/protocol` · **Milestone:** M2
- **Depends on:** C-01
- **Status:** todo
- **Spec:** Interfaces (draft) 5. Release log entry, Residual risks: certificates and engine updates (2. Engine updates, Release keys), Transparency and verifiability, Security hardening 9 and 10; ADRs: [0003](../../adr/0003-ui-as-signed-bundle.md), [0014](../../adr/0014-cryptography.md)

## Goal

`@ptbk/protocol` exports the release entry, revocation list and UI bundle manifest schemas, the DSSE envelope encoding they travel in, and one pure `verifyRelease` function that decides whether an engine may install or serve a release.

## Context

Updates are the main remaining path to customer data, so this check is the core of the update and UI-loader trust story. The same function is used by the mock engine's UI loader (M-05, reference implementation for the engine team), by the UI bundle pipeline to self-check what it publishes (X-03), and later by the real engine's updater and loader. It must be pure and deterministic: time, first-seen time, provenance verification and keys are inputs.

Decided 2026-10-19 (ADR 0014): no JSON canonicalisation. Signed documents are DSSE envelopes carrying the exact payload bytes; every signature (release key, maintainer keys, CI provenance via `sigstore.attest()`) covers the same DSSE PAE.

## Scope

- `src/release/dsse.ts`: `DsseEnvelope { payloadType, payload (standard base64 of the exact bytes), signatures: [{ keyid, sig }] (1–16) }` (strict schema; `sig` exactly 64 bytes). Base64 inside DSSE (the one exception to ADR 0010's base64url rule, as DSSE and Sigstore require): `payload` and `sig` are RFC 4648 §4 standard base64 with `=` padding required; the decoder rejects `-`, `_`, whitespace, missing padding and non-zero trailing bits, so each byte string has exactly one accepted encoding. `keyid` stays base64url without padding, like every other byte string on the wire. Add `encodeBase64Std` / `decodeBase64Std` next to C-01's base64url functions; `pae(payloadType, payload: Bytes)` = `"DSSEv1" SP len(type) SP type SP len(body) SP body` (lengths as ASCII decimal); `RELEASE_PAYLOAD_TYPE = 'application/vnd.ptbk.release+json; v=1'`, `REVOCATION_PAYLOAD_TYPE = 'application/vnd.ptbk.revocation+json; v=1'`; `dsseKeyId(publicKey: Bytes)` = base64url(SHA-256(raw public key)); `signDsse(signer, payloadType, payload)` and `verifyDsseSignatures(envelope, keys)` returning the set of key IDs with a valid signature (C-01's strict `verifyEd25519`).
- `src/release/entry.ts`: the release payload `ReleaseEntry { v: 1, version: EngineVersion, gitTag, commit (40 hex), artifacts: Artifact[] (1–32, unique names), kind: 'regular' | 'security', advisory: url | null, publishedAt: Timestamp }`, `Artifact { name, sha256 (64 hex), kind: 'engine' | 'ui' }`; refinements: `security` requires a non-null `advisory`; at most one `ui` artifact. The published record is `SignedRelease { v: 1, envelope: DsseEnvelope, provenance: string }`, where `provenance` is the Sigstore bundle JSON (≤ 64 KiB) from `sigstore.attest()` over the same payload and payload type.
- `src/release/revocation.ts`: the revocation payload `RevocationList { v: 1, issuedAt: Timestamp, expiresAt: Timestamp, revoked: [{ version: EngineVersion, reason (≤ 500 chars) }] (0–1,000, unique versions) }`, published as a DSSE envelope with `REVOCATION_PAYLOAD_TYPE`. One list replaces individual revocation entries so freshness can be checked. Rollback protection (decided 2026-10-19) is part of `verifyRelease`, not a separate call callers could skip: it takes `lastAcceptedRevocationIssuedAt` and treats a list whose `issuedAt` is older than that as `revocations-unverifiable` with reason `rolled-back`; the caller persists the `issuedAt` of each list it accepts.
- `src/release/manifest.ts`: `UiBundleManifest { v: 1, version: EngineVersion, commit (40 hex), engineApi (SemVer range of the `ENGINE_API_VERSION`values the bundle supports, e.g.`>=1.0.0 <2.0.0`), entry: 'index.html', files: [{ path, sha256 (64 hex), size (bytes, safe integer ≥ 0) }], csp: string }`. `csp` records the `ENGINE_UI_CSP` the bundle was tested against and is informational only: the loader never reads it, because the engine's headers are engine code. Because `protocol` cannot import `engine-api`, `engineApi` is validated here only as a range string (a small range grammar: `>=`, `<`, `^` on full versions); the loader checks it against `ENGINE_API_VERSION`. Paths are safe relative paths (1–1,024 chars, no `..` or empty segment, no leading `/`, no backslash, no duplicates). Per the spec the `ui` artifact's SHA-256 pins the tarball; the manifest inside it lets the loader re-check every unpacked file, so an unpacker bug cannot serve a file the release did not contain.
- `src/clock.ts`: `Clock` port (`now(): Date`) and `createFixedClock(date)` for tests, if no earlier task added it.
- `src/release/trust.ts`: `TrustPolicy { releaseKeys: KeyRef[], maintainerKeys: KeyRef[] (3), securityThreshold: 2, workflowIdentity: WorkflowIdentity, revocationRule, delays: { regularMs: 72 h, securityMs: 24 h } }`, `KeyRef { publicKey: Ed25519PublicKey }` (the key ID is always derived, never stored beside it), `WorkflowIdentity { issuer: 'https://token.actions.githubusercontent.com', repository, repositoryId, workflowPath }`. The `TrustPolicy` schema rejects a key listed both in `releaseKeys` and `maintainerKeys`, and requires the 3 maintainer keys to be distinct, so one person's key can never count twice toward a threshold.
- `src/release/provenance.ts`: `expectedWorkflowClaims(identity, entry)` (pure) returning the exact certificate SAN `https://github.com/<repository>/<workflowPath>@refs/tags/<entry.gitTag>` (plus its anchored, regex-escaped form for APIs that only take a pattern), the issuer, and the required Fulcio extensions: `1.3.6.1.4.1.57264.1.13` (source repository digest) = `entry.commit`, `…1.14` (ref) = `refs/tags/<gitTag>`, `…1.15` (repository ID) = `repositoryId`, `…1.11` (runner environment) = `github-hosted`. `ProvenanceVerifier` port: `verifyProvenance(bundle: string, envelope: { payloadType, payload: Bytes }, expected: ExpectedWorkflowClaims, signal): Promise<{ kind: 'verified', logIndex, trustedTime: Date | null } | { kind: 'invalid', reason } | { kind: 'not-in-log', reason }>`. Contract for every adapter: the bundle's DSSE payload and type equal `envelope` byte for byte; the certificate matches `expected` exactly (never a caller-supplied pattern); `tlogThreshold >= 1`; verification against a pinned `trusted_root.json` (no live TUF fetch required); `trustedTime` is the **latest** verified timestamp in the bundle (RFC 3161 TSA timestamps and Rekor v1 integrated time), `null` when none exists. The real adapter is built on `@sigstore/verify@4.1.2` directly, not on `sigstore.verify()` (whose identity match is an unanchored regex and whose OID comparison uses raw DER): `toTrustMaterial(TrustedRoot.fromJSON(pinnedRoot))`, `new Verifier(trustMaterial, { tlogThreshold: 1, ctlogThreshold: 1 })`, `verifier.verify(toSignedEntity(bundle))`; then it compares `signer.identity.subjectAlternativeName` to the expected SAN exactly, decodes each required extension's DER UTF8String and compares the string exactly, and reads the verified TSA or Rekor times and `logIndex`. Pinned exactly in the workspace catalog: `@sigstore/verify@4.1.2`, `@sigstore/bundle@5.0.0`, `@sigstore/protobuf-specs@0.5.2`. `createFakeProvenanceVerifier()` takes test certificate claims and applies the same exact matching (tests and e2e only).
- `src/release/verify.ts`: `verifyRelease(input, deps)` (below), and `verifyArtifact(artifact, bytes)` / `verifyManifestFiles(manifest, files)` for hash checks.
- No `canonical.ts` (JCS) and no separate `TransparencyLog` port: log inclusion and trusted time come from the Sigstore bundle through `ProvenanceVerifier`.

## Out of scope

- The real Sigstore adapter (`@sigstore/verify@4.1.2` as above, Node ^24.15, Node-only): it lives where it is used, `apps/mock-engine/src/adapters/` in M-05 and the engine's own code, and implements the port contract above. CI signing may still use `sigstore@5.0.0` (`attest()` with `tsaServerURL`, X-03). Signing, building and publishing to R2 (X-03, I-03). Downloading, unpacking and persisting `firstSeenAt` (M-05, engine).

## Design notes

- **Protocol design:** follows [ADR 0010](../../adr/0010-protocol-design-principles.md) and [ADR 0014](../../adr/0014-cryptography.md).
- `verifyRelease({ release: SignedRelease, revocations: DsseEnvelope | null, lastAcceptedRevocationIssuedAt: Date | null, policy, mode: 'auto' | 'manual', installedVersion | null, firstSeenAt: Date }, { provenance: ProvenanceVerifier, clock: Clock })` checks in this order and returns the first failure: `invalid-entry` (envelope schema or payload type; payload not matching the strict schema), `signature-threshold-not-met`, `not-in-log`, `revocations-unverifiable { reason: 'missing' | 'invalid' | 'expired' | 'rolled-back' }`, `revoked`, `not-newer` (version ≤ installed; the updater's downgrade refusal), `delay-not-elapsed { eligibleAt }`; otherwise `{ kind: 'ok', eligibleAt }`. `mode: 'manual'` skips only the delay (spec: manual approval may install early); no mode skips signatures, log or revocation.
- Parse after verify: the payload JSON is parsed with the strict zod schema only after a trusted key's signature over the PAE verifies; provenance is checked after that, because the expected SAN needs `entry.gitTag` and `entry.commit`.
- Threshold (decided 2026-10-19): `regular` needs **both** valid provenance (the release workflow's keyless Sigstore attestation over the same envelope, matched exactly per `expectedWorkflowClaims`) **and** a valid signature from a release key held by a human on a hardware key, so a compromised CI alone cannot ship. `security` needs all of that **and additionally** valid signatures from 2 of the 3 distinct maintainer keys (provenance + release key + 2 maintainers), as the spec says. Signatures from unknown key IDs are ignored, duplicates count once, a malformed signature never throws. Invalid provenance is `signature-threshold-not-met`; valid provenance without log inclusion or trusted time is `not-in-log`.
- **Delay with trusted time:** `eligibleAt = max(publishedAt, trustedTime, firstSeenAt) + delay`. `publishedAt` is self-asserted, so it can only lengthen the delay; `firstSeenAt` is persisted by the engine the first time it sees the envelope (keyed by payload SHA-256) and passed in, so a release withheld and shown late still waits the full delay.
- **Revocation freshness:** the revocation list counts only if it verifies under `policy.revocationRule`, `clock.now() < expiresAt` (else reason `expired`) and `issuedAt` is not older than `lastAcceptedRevocationIssuedAt` (else reason `rolled-back`). A missing, invalid, expired or rolled-back list is `revocations-unverifiable`: the caller keeps the current version and alerts (it never installs without a fresh list).
- Artifact hashes compared with `bytesEqual` on decoded digests (public values), after streaming SHA-256 over the bytes; a mismatch is `{ kind: 'hash-mismatch', name }`.

## Acceptance criteria

- [ ] One test per outcome, plus: regular release with a valid release-key signature but invalid or missing provenance fails, and valid provenance without a release-key signature fails; security release with 1 valid and 1 invalid maintainer signature fails; same maintainer twice fails; regular release signed only by maintainers fails (unless policy says otherwise); a revoked version is refused; a list with a bad signature is `revocations-unverifiable`; delay boundary at exactly `eligibleAt` passes and 1 ms before fails.
- [ ] Trusted time: a backdated `publishedAt` does not shorten the delay (`trustedTime` or `firstSeenAt` wins); a later `firstSeenAt` moves `eligibleAt`; provenance without a trusted time is `not-in-log`.
- [ ] Identity pinning (fake verifier, same `expectedWorkflowClaims`): wrong repository, repository ID, workflow path, commit, ref (e.g. a branch instead of the tag) or runner environment (`self-hosted`) is rejected; a SAN that only matches as a prefix or with regex metacharacters is rejected.
- [ ] Revocation list: an expired list returns `revocations-unverifiable` with reason `expired` (keep current version); a list older than `lastAcceptedRevocationIssuedAt` returns reason `rolled-back`; a list with the same `issuedAt` and a fresh list without the version pass.
- [ ] `TrustPolicy`: a key in both `releaseKeys` and `maintainerKeys`, and two identical maintainer keys, are rejected by the schema. A security release with provenance and 2 maintainer signatures but no release-key signature fails.
- [ ] DSSE: PAE golden vector; a signature over the raw payload instead of the PAE fails; changing one payload byte or the payload type fails; `payload` or `sig` in base64url, without padding, with whitespace or with non-zero trailing bits is rejected; an envelope with a different payload type is `invalid-entry`; `dsseKeyId` matches a checked-in value. Golden vectors (payload bytes, PAE hex, envelope with fixed test keys) checked in.
- [ ] Manifest: unknown field, missing `commit`, malformed `engineApi` and negative `size` are rejected. Path tests: `../x`, `/x`, `a\b`, `a//b`, empty, duplicate, and a 1,025-char path are rejected.
- [ ] Property test: arbitrary JSON never makes envelope or payload parsing or `verifyRelease` throw.
- [ ] `bun run check` passes.
- [ ] **Status** line above set to `done (#<PR>)`.

## Risks and open points

- Revocation threshold is not in the spec. Default proposal: release key or any one maintainer (stopping a release is the safe direction), configurable in `TrustPolicy`. Rekor search by payload hash as a second revocation channel is open.
- Open (ADR 0014 follow-ups): who signs the revocation list and how often it is re-signed, and the maximum validity `expiresAt − issuedAt` the verifier accepts; an optional pin of Fulcio OID `1.3.6.1.4.1.57264.1.20` (build trigger, e.g. `push` only) in `expectedWorkflowClaims`, since X-03 also allows `workflow_dispatch`; an optional torsion-free engine-key check at registration (C-03, D-03), beyond noble's small-order check.
- M-05 (loader) and the engine must persist `firstSeenAt` and gain the `revocations-unverifiable` refusal; `SignedRelease` replaces `ReleaseEntry.provenance`.
- Staged rollout (random install moment within 24 h after the delay) is the updater's job, not this function's.
