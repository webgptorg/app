# X-05. E2E: sign up, link engine, see it online, open it

- **Lane:** X · **Module:** `e2e/` · **Milestone:** M3
- **Depends on:** D-04, D-06, D-09, M-06 · **Unblocks:** — (closes M3)
- **Status:** todo
- **Spec:** Pairing and identity (First setup), Interfaces (1 registration, 2 registry lookup, 4 heartbeat), What our platform can and cannot do, One address for users; ADRs: [0004](../../adr/0004-mock-engine-and-conformance.md)

## Goal

A browser test signs up on the dashboard with a passkey, links a fresh mock engine with the link code, sees the engine online, and opens it through a relay that read its registry from the dashboard, with no static registry anywhere in the stack.

## Context

This is the M3 done criterion and the first test where all three of our components cooperate over their real interfaces: registration (engine to dashboard), registry lookup (relay to dashboard), heartbeat (engine to dashboard) and the tunnel. It also guards rule 3 in [AGENTS.md](../../../AGENTS.md): no code on our domains loads engine data.

## Scope

- Compose overlay `e2e/compose.dashboard.yaml` on X-01's stack:
  - `dashboard`: the dashboard app run locally from D-01's dev container (built SPA and Worker in workerd, local D1 with the generated migrations applied, so the production CSP is in force), with fake adapters for email and billing, served at `https://app.ptbk.test` with a dev-CA certificate (TLS in the dev server or a pinned Caddy in front). Relay authentication key for the internal registry API generated by `init`.
  - `relay-a`, `relay-b`: switched to D-04's HTTP registry adapter pointing at the dashboard; the static registry file from X-01 is not mounted.
  - `mock-engine`: not started by `up`; started by the test with the link code (`docker compose run -d` or a control script), configured with the dashboard URL, the relay list returned at registration, a fresh key, and a short heartbeat interval for e2e (e.g. 2 s).
  - DNS resolves `app.ptbk.test` to the dashboard; `*.engine.test` stays on both relays.
- Test `e2e/tests/dashboard/link-engine.spec.ts`:
  1. Enable a virtual authenticator (CDP `WebAuthn.addVirtualAuthenticator`, `ctap2`, internal transport, resident key, user verification).
  2. Sign up at `https://app.ptbk.test` with a random email; follow D-02's email-first signup (the signup link from the fake outbox via D-02's dev-only `GET /api/__dev/emails`); a passkey is created.
  3. Read the install command and link code from the page.
  4. Start the mock engine with that link code; it registers, receives its engine ID, hostname and relays, opens tunnels and sends heartbeats.
  5. The engine list shows the engine as online within 60 s (`expect.poll` on the UI, no sleeps), with the hostname derived from the engine key (assert against the engine's public key reported by the mock engine).
  6. Click "Open"; the browser navigates to `https://<engineId>.engine.test`, the page loads through the relay, and the peer certificate is the engine's (fingerprint check from X-01's fixtures).
  7. Sign out and sign back in with the same passkey (assertion path).
- Negative tests in the same folder:
  - before linking, `https://<engineId>.engine.test` does not connect (unknown SNI at the relay);
  - reusing a link code, or using an expired one (dashboard clock advanced through its test hook or a short TTL in e2e config), is rejected at registration;
  - while on `app.ptbk.test`, the browser makes no request to any `*.engine.test` host (request log fixture);
  - stopping the mock engine makes the engine list show offline after the missed-heartbeat threshold (shortened in e2e config).
- CI: part of the existing `e2e` job.

## Out of scope

- Stripe flows (D-07 is covered by its own tests; here billing uses the fake adapter).
- Custom domains (D-08), offline alert emails beyond the status change (D-05), engine-ui flows (X-04).

## Design notes

- Short intervals (heartbeat, offline threshold, link code TTL) are configuration of the dashboard and mock engine for e2e, not test-only code paths.
- The engine's setup secret and owner passkey on the engine are not part of this flow; opening the engine shows its sign-in or setup page, which is enough to prove routing.
- Assert that the relays' registry came from the dashboard by checking relay logs for registry lookups, or by suspending the engine in the dashboard and seeing the tunnel refused (optional, if D-04 exposes suspension).

## Acceptance criteria

- [ ] The happy-path test and all four negative tests pass in the CI `e2e` job.
- [ ] No static registry file is mounted in the dashboard overlay (assert in the test setup).
- [ ] The test fails if the dashboard page fetches from an engine hostname (verified once with a temporary change, noted in the PR).
- [ ] [development.md](../../development.md) explains how to run the dashboard flow locally.
- [ ] `bun run check` passes.
- [ ] **Status** line above set to `done (#<PR>)`.

## Risks and open points

- Running the dashboard (Vite SPA and Hono Worker in workerd) in a container with TLS for `app.ptbk.test` relies on D-01's dev container; if it falls short, fix it there. WebAuthn needs a secure context, so plain HTTP is not an option.
- The spec requires a card on file before an engine can be linked; the fake billing adapter must let the test pass that gate without Stripe.
- `/api/__dev/emails` exists only with the fake email adapter, which D-01's config allows only in dev; staging and production cannot expose it.
