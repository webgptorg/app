# M-05. UI loader in the mock engine (reference implementation)

- **Lane:** Mock engine · **Module:** `apps/mock-engine` · **Milestone:** M2
- **Depends on:** C-06, X-01, X-03, M-02, M-04
- **Status:** done (#39)
- **Spec:** Architecture (UI delivery); Interfaces (draft) 5 and 6; Engine security baseline (Browser headers); Security hardening (1, 5); ADRs: [0003](../../adr/0003-ui-as-signed-bundle.md), [0004](../../adr/0004-mock-engine-and-conformance.md), [0014](../../adr/0014-cryptography.md)

## Goal

The mock engine downloads the signed engine-ui bundle, verifies it like a release, keeps the previous bundle when anything fails, and serves it from its own origin under the engine's strict security headers. It is the reference the engine team ports to the real engine (about 100 lines of core logic there).

## Context

ADR 0003: we never serve UI to browsers. X-03 builds, signs and publishes the bundle with a manifest; C-06 provides the release-log types, the `UiBundleManifest` schema and `verifyRelease`; X-01 provides the e2e stack the smoke test runs in; M-04 provides the gateway session and control server. This task is where both meet a running engine, and where engine-ui first runs under the real CSP. The security headers are engine code, not part of the bundle, so the bundle can never loosen them.

## Scope

- Ports in `src/domain/ui/`: `ReleaseSource { latest(signal); release(version, signal); revocations(signal); artifact(name, signal): Promise<ReadableStream<Uint8Array>> }` (`release` returns C-06's `SignedRelease { envelope, provenance }` as fetched, `revocations` the `RevocationList` DSSE envelope or `null`), `BundleStore { active(): InstalledBundle | undefined; stage(...); activate(id); previous(): InstalledBundle | undefined }` and `UpdateStateStore { firstSeenAt(payloadSha256, now): Promise<Date>; lastAcceptedRevocationIssuedAt(): Promise<Date | null>; acceptRevocations(issuedAt): Promise<void> }` (`firstSeenAt` stores `now` on the first call per entry and returns the stored value after; `acceptRevocations` never moves backwards). In-memory adapters for all three.
- `src/domain/ui/ui-update.ts`: `checkForUiUpdate(deps): Promise<UiUpdateOutcome>` with `UiUpdateOutcome = { kind: 'up-to-date' } | { kind: 'installed'; version; sha256 } | { kind: 'refused'; reason: 'invalid-entry' | 'signature-threshold-not-met' | 'not-in-log' | 'revoked' | 'not-newer' | 'delay-not-elapsed' | 'hash-mismatch' | 'manifest' | 'engine-api' | 'unpack' | 'revocations-unverifiable'; revocationReason?: 'missing' | 'invalid' | 'expired' | 'rolled-back' } | { kind: 'unavailable' }`. The release decision is C-06's `verifyRelease` only (its first failure becomes the refusal reason, with C-06's revocation reason carried as `revocationReason`), called with the `SignedRelease` and revocation envelope as fetched, `lastAcceptedRevocationIssuedAt` from `UpdateStateStore`, `firstSeenAt` and the injected `Clock`. The release is a DSSE envelope over the `ReleaseEntry` payload (`payloadType: "application/vnd.ptbk.release+json; v=1"`): every signature is verified over the DSSE PAE and the payload is parsed with C-06's strict schema only after that, so the loader never reads a field of an unverified entry. A regular release needs both the CI workflow's keyless provenance (`sigstore.attest()` over the same envelope; the Sigstore bundle carries the Rekor entry and the TSA timestamp, checked by C-06's `ProvenanceVerifier`) and the human-held release key; a `security` release additionally needs 2 of 3 maintainer keys; then log inclusion, revocations and the delay. Trusted time: the loader records `firstSeenAt` in `UpdateStateStore` (keyed by SHA-256 of the envelope payload) the first time it sees an entry and passes it in; `verifyRelease` computes `eligibleAt = max(publishedAt, trustedTime, firstSeenAt) + delay`, where `trustedTime` is the latest verified timestamp in the bundle (RFC 3161 TSA timestamp or Rekor v1 integrated time), and refuses with `not-in-log` when neither verifies. The artifact with `"kind": "ui"` is hashed while streaming and compared with the entry (`verifyArtifact`); the unpacked files are checked against the bundle's C-06 `UiBundleManifest` (`verifyManifestFiles`); the manifest's `engineApi` range must include `ENGINE_API_VERSION` from `@ptbk/engine-api`, else `engine-api`. The manifest's `csp` field is informational and never read by the loader.
- `src/adapters/ui/fs-update-state-store.ts`: `PTBK_DATA_DIR/ui/update-state.json` (0600, temp file, `fsync` and rename, strict zod on load). A lost or unreadable file restarts the delay rather than shortening it, and is logged as an error because it also resets revocation rollback protection.
- `src/adapters/ui/sigstore-provenance-verifier.ts`: the real C-06 `ProvenanceVerifier`, built on `@sigstore/verify@4.1.2` directly with `@sigstore/bundle@5.0.0` and `@sigstore/protobuf-specs@0.5.2` (all exact, from the workspace catalog; Node ^24.15), never `sigstore.verify()` (its identity match is an unanchored regex and its OID comparison uses raw DER). Steps: `toTrustMaterial(TrustedRoot.fromJSON(pinnedRoot))` from the pinned `trusted_root.json` shipped with the release (no live TUF fetch), `new Verifier(trustMaterial, { tlogThreshold: 1, ctlogThreshold: 1 })`, `verifier.verify(toSignedEntity(bundle))`. Then, per the port contract: the bundle's DSSE payload and type equal the release envelope byte for byte; `signer.identity.subjectAlternativeName` equals C-06's `expectedWorkflowClaims` SAN exactly (string equality; ADR 0014: `TrustPolicy.workflowIdentity = { issuer: 'https://token.actions.githubusercontent.com', repository, repositoryId, workflowPath }`, SAN `https://github.com/<repository>/<workflowPath>@refs/tags/<entry.gitTag>`); the issuer matches; each required extension (…1.13 = `entry.commit`, …1.14 = `refs/tags/<gitTag>`, …1.15 = `repositoryId`, …1.11 = `github-hosted`) is DER-decoded as a UTF8String and compared exactly; `logIndex` and `trustedTime` are read from the verified TSA and Rekor times, `trustedTime` being the latest verified timestamp, else `null`. It never accepts a caller-supplied pattern.
- Revocations: the `RevocationList` is a DSSE envelope (`application/vnd.ptbk.revocation+json; v=1`) with `issuedAt` and `expiresAt`. Rollback protection is inside `verifyRelease` (C-06), so the loader cannot skip it: it always passes `lastAcceptedRevocationIssuedAt` from `UpdateStateStore`, and a list older than that is `revocations-unverifiable` with reason `rolled-back`; an expired list has reason `expired`, a missing or badly signed one `missing` or `invalid`. When `verifyRelease` got past the revocation check, the loader persists that list's `issuedAt` with `acceptRevocations`. On `revocations-unverifiable` the current bundle stays and the loader alerts (`ui.revocations-unverifiable` with the reason at error level, shown in the security panel).
- `src/adapters/ui/http-release-source.ts`: `fetch` against `PTBK_UI_RELEASE_URL` (a local file server in tests, MinIO or a static server in e2e), timeouts and size caps on every request.
- `src/adapters/ui/bundle-unpacker.ts`: `tar.zst` via Node 24's `zlib` zstd decompressor and a minimal ustar reader (or `tar` 7.x if a dependency is justified). Rejects absolute paths, `..`, symlinks, hard links, devices, duplicate paths, more than 10,000 files or more than 200 MB unpacked.
- `src/adapters/ui/fs-bundle-store.ts`: unpacks into `PTBK_DATA_DIR/ui/staging-<random>/`, verifies, renames to `ui/<version>-<sha256 prefix>/`, makes it read-only, and switches `ui/active.json` atomically (write temp, rename). Keeps the previous bundle; deletes older ones and failed staging dirs.
- `src/domain/http/security-headers.ts`: one function returning the engine's headers, applied by a Hono middleware to every in-tunnel response (UI, API, sign-in, errors): `Content-Security-Policy` always set to `ENGINE_UI_CSP` imported from `@ptbk/engine-api` (C-04; the one string the bundle, the mock engine, conformance and the real engine share; never a local copy, never the manifest's `csp`), `Strict-Transport-Security: max-age=31536000`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and a `Permissions-Policy` that disables camera, microphone, geolocation, payment and USB.
- `src/domain/ui/static-route.ts`: pure `resolveStatic(path, method, accept, manifest)` returning `{ kind: 'asset'; file; cache: 'immutable' | 'no-cache' } | { kind: 'spa-fallback' } | { kind: 'not-found' }`. Hashed assets get `Cache-Control: public, max-age=31536000, immutable`; `index.html` and unhashed files get `no-cache`. SPA fallback only for `GET`/`HEAD` with `Accept` containing `text/html`, outside the API base path, `/assets/` and `/__spike/`. Only files listed in the manifest are served; correct `Content-Type` from a fixed extension map.
- `src/adapters/http/ui-routes.ts`: serves the active bundle behind the gateway session (anonymous visitors get only the sign-in page: open code). If no bundle has ever installed, answers 503 with a plain engine page.
- Update triggers: at startup and every `MOCK_UI_CHECK_INTERVAL_S` (default 3600); also `POST /__mock/ui/check` on the control server when M-04's control server exists. Exposes the active bundle version, SHA-256 and log entry for the security panel endpoint.
- Config: `PTBK_UI_RELEASE_URL`, `PTBK_UPDATE_POLICY` (`auto` | `manual` | `pinned`), `PTBK_PINNED_VERSION`, `MOCK_UI_TRUST_POLICY_FILE` (C-06 `TrustPolicy`: release keys, maintainer keys, workflow identity), `MOCK_UI_TRUSTED_ROOT_FILE` (defaults to the pinned `trusted_root.json`), `MOCK_UI_CHECK_INTERVAL_S`, `MOCK_UI_FAKE_PROVENANCE` (`enabled` swaps the Sigstore verifier for C-06's `createFakeProvenanceVerifier()` with test certificate claims; for unit tests and the e2e stack only, never a default, and startup fails with it under `NODE_ENV=production`).

## Out of scope

- Building, signing and publishing the bundle (X-03). Engine binary updates. The UI flows themselves (X-04). Staged-rollout randomisation (engine updater).

## Design notes

- Fail closed and keep serving: any refusal or error leaves the active bundle untouched and logs `ui.refused` with the reason and version, never file contents.
- Delay: `auto` enforces C-06's delay with the injected clock; `manual` and `pinned` may install before the delay ends (spec, Updates), still requiring signatures, log inclusion and no revocation. E2E uses `pinned`.

## Acceptance criteria

- [ ] `ui-update` tests with in-memory adapters, a test release key generated at test time and a fake provenance verifier: valid install with both signatures; release-key signature only (no provenance) and provenance only (no release-key signature) are each refused; each other refusal reason (no log entry in the bundle, delay not passed under `auto`, revoked, not newer, artifact hash mismatch, manifest mismatch, `engineApi` range excluding `ENGINE_API_VERSION`); network failure mid-download yields `unavailable`; an envelope whose payload or `payloadType` changed after signing is refused; no TSA timestamp or integrated time → `not-in-log`; under `auto` an entry first seen today waits the full delay even with an old `publishedAt` and trusted time, and `firstSeenAt` survives a restart; a missing, expired or badly signed revocation list → `revocations-unverifiable` with reason `missing`, `expired` or `invalid` and an alert; a validly signed list older than the last accepted one → `revocations-unverifiable` with reason `rolled-back`, also after a restart (`lastAcceptedRevocationIssuedAt` is always passed to `verifyRelease`); in every failure case the previous bundle stays active.
- [ ] Sigstore verifier tests against recorded bundle fixtures (signed with the real workflow, or a local Sigstore stack): the expected identity verifies; another repository, workflow path, tag, commit, repository ID, a self-hosted runner, another issuer or a bundle without a log entry are each refused; a SAN that merely contains the expected one (extra prefix or suffix) and a required extension that is not a DER UTF8String are refused; with both a TSA timestamp and a Rekor integrated time, `trustedTime` is the later one; the adapter does not import `sigstore` (lint or test asserts it).
- [ ] Unpacker tests: path traversal, absolute path, symlink, hard link, oversize and too many files are rejected; staging dirs are cleaned up.
- [ ] `static-route` tests: hashed asset immutable, `index.html` no-cache, `/agents/123` with `Accept: text/html` falls back, `/assets/missing.js` is 404, `POST` to an unknown path is 404, API paths never fall back.
- [ ] Every in-tunnel response, including 404, 401 and 503, carries the full header set (snapshot test of the header map); a bundle whose manifest `csp` differs from `ENGINE_UI_CSP` installs and is still served with `ENGINE_UI_CSP`.
- [ ] E2E smoke (X-01 stack): the mock engine installs X-03's test-signed bundle from the local store with the fake provenance verifier, a signed-in Playwright session loads the UI through the relay with zero CSP or Trusted Types violations reported, and a tampered bundle published next is refused while the old one keeps loading.
- [ ] `bun run check` and the e2e suite pass.
- [ ] **Status** line above set to `done (#<PR>)`.

## Risks and open points

- The allowed Trusted Types policy names (`ptbk-html`) are part of `ENGINE_UI_CSP` and therefore engine-defined, never read from the bundle.
- Revocation lookup through Rekor search by payload hash, in addition to the signed list, is an open point (ADR 0014).
- Whether `Cross-Origin-Embedder-Policy: require-corp` should be added is open; leave it out until the UI is tested with it.
