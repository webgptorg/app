# C-07. Engine capabilities: runs, files, triggers, integrations, activity

- **Lane:** Contracts · **Module:** `packages/engine-api` · **Milestone:** M2
- **Depends on:** C-04
- **Status:** done (#10)
- **Spec:** Security hardening (preamble, 5, 7), Enterprise-ready engine architecture (API, Authorisation, Audit), Interfaces (draft) 6; ADRs: [0010](../../adr/0010-protocol-design-principles.md), [0016](../../adr/0016-engine-capabilities.md), [0006](../../adr/0006-organizations-and-roles.md)

## Goal

`@ptbk/engine-api` advertises optional engine capabilities through `GET /engine` and defines one contract module per capability (`runs@1`, `files@1`, `triggers@1`, `integrations@1`) plus a typed, forward-compatible activity union, with routes, permissions, events and in-memory client support.

## Context

Besides chat, the UI must show what agents do (ADR 0016). The real engine's shapes are still being decided, so the v1 models follow what the predecessor already has: one durable job per chat turn with status, progress card, tool calls, usage and a run report with git changes; files with purposes and virus-scan results; planned messages with recurrence and lifecycle; inbound email; MCP, calendar and GitHub integrations with secrets referenced from a wallet. Model the concepts, not the predecessor's code. engine-ui feature modules (U-08 to U-12) and the mock engine (M-07) build on this task; the core contract from C-04 (agents, chats, members, secrets, security, audit) stays as it is, except where noted below. The package stays MIT-licensed and portable (no `node:*`, `bun:*`, `cloudflare:*`), and contracts are not frozen until E-02, so moving C-04's file routes under a capability is allowed.

## Scope

- **Tolerant reader for responses (ADR 0010 §3, decided 2026-10-20):** C-04 shipped response schemas as `z.strictObject`, so a UI built against API 1.0 would reject the new `GET /engine` fields. Request schemas stay strict (servers reject unknown fields). The client parses responses with unknown keys stripped at every depth (derive tolerant variants of the response schemas, e.g. a `toTolerant(schema)` helper, or define response schemas with `z.object` and keep a strict check for servers). Known fields are still fully validated. Server-side tests (mock engine, conformance) assert that responses contain no undeclared fields, so drift is still caught. Test: a 1.0 client parses a 1.1 `GET /engine` response.
- Core addition needed by the member home (U-08): `GET /chats?agentId&q&cursor&limit` lists every chat the member can see across agents (`chats.read`, paged, newest activity first).

- **Discovery** (`src/capabilities/capability.ts`): C-04's `EngineInfo` has no capability list yet; add `capabilities: [{ id: CapabilityId, version: int ≥ 1 }]` (`CapabilityId` matches `^[a-z][a-z0-9-]{0,31}$`) and `engineId` (opaque lowercase DNS label of the default hostname, own schema with C-01's rule, like `Hostname`; the UI's TrustMark fingerprint is derived from it, U-02). Export `KNOWN_CAPABILITIES` (`runs@1`, `files@1`, `triggers@1`, `integrations@1`), `CapabilityRef` and `supports(engineInfo, ref)`. An engine may advertise two versions of one capability side by side; unknown IDs and versions are ignored. A response without `capabilities` (an engine on API 1.0) parses as `[]`. `ENGINE_API_VERSION` becomes `1.1.0`.
- `RouteDefinition` gains `capability?: CapabilityRef`; every capability route carries it. An engine that does not advertise a capability answers its routes with 404 problem code `capability-not-supported`.
- **Permissions** (append to `PERMISSIONS`, C-04 naming style): `runs.read`, `runs.control` (cancel and retry), `triggers.read`, `triggers.manage`, `integrations.read`, `integrations.manage`. `files.read` and `files.write` already exist. New branded IDs in `common.ts`: `RunId`, `ToolCallId`, `TriggerId`, `TriggerFireId`, `IntegrationId`, `ActivityId`, `FileVersionId`. New problem codes: `capability-not-supported`, `run-finished`, `run-not-retryable`, `trigger-ended`, `invalid-schedule`, `file-infected`.
- **`src/capabilities/runs.ts`** (`runs@1`):
  - `Run { id, agentId, source: 'web' | 'api' | 'email' | 'schedule' | 'member' | 'goal' | 'webhook', status: 'queued' | 'running' | 'completed' | 'failed' | 'cancelled', chatId | null, messageId | null, triggerId | null, retryOf: RunId | null, createdBy: MemberId | null, queuedAt, startedAt | null, completedAt | null, cancelRequestedAt | null, attemptCount, runner | null, model | null, progress: { title, now | null, next | null, items: [{ id, text, status: 'pending' | 'completed' }] } | null, usage: { inputTokens | null, outputTokens | null, durationMs | null, cost: { amount: decimal string, currency: ISO 4217 } | null } | null, error: { code, summary } | null }`. Added in API 1.5.0 for U-09: `agentName` (string ≤ 256 | null), the agent's name when the engine answers, and `preview` (string ≤ 200 | null), the text that started the run (the chat message, an email's subject, a schedule's message, an API or member request), whitespace collapsed; both untrusted text. The client reads an unknown `status` or `source` as `unknown` (`RunReader`, also for `run.changed`); the engine-side schemas stay closed.
  - `RunDetail` adds `toolCalls: [{ id, name, state: 'pending' | 'partial' | 'complete' | 'error', startedAt | null, durationMs | null, logs: string, logsTruncated }]` and `outputs { messages: [{ chatId, messageId }], files: FileId[], fileNames: string[] (API 1.5.0: the name of each entry of `files`, same length and order, so outputs read without `files@1`), projectChanges: [{ projectName, commitHash, changedFiles: [{ path, insertions, deletions }], diff: string, diffTruncated }] }`, plus `report { touchedProjects: string[], externalSources: string[] }`. Logs and diffs are plain text with a contract byte limit (`MAX_RUN_TEXT_BYTES`, 256 KiB); the engine truncates and sets the flag.
  - Routes: `GET /runs?agentId&status&source&triggerId&createdBy&from&to&sort&cursor&limit` (`status` accepts a comma-separated set; `sort` `queuedAt` | `-queuedAt`, default newest first), `GET /runs/{runId}`, `GET /runs/stats?agentId` → `{ running, queued, failedLast24h, oldestQueuedAt | null, lastFinished: { status: 'completed' | 'failed' | 'cancelled', at } | null }` (`lastFinished` added in API 1.5.0: the run that finished last, so the UI can tell a failure nothing has finished after) (all `runs.read`); `POST /runs/{runId}/cancel` → 202 `Run` with `cancelRequestedAt` set (idempotent; 409 `run-finished` once terminal) and `POST /runs/{runId}/retry` → 201 new `Run` with `retryOf` (only from `failed`, else 409 `run-not-retryable`), both `runs.control`. Starting a run stays a chat message or a trigger.
- **`src/capabilities/files.ts`** (`files@1`): C-04's four file routes move here unchanged in path and operation ID. `FileMetadata` gains `purpose: 'knowledge' | 'attachment' | 'output' | 'upload'`, `agentId | null`, `chatId | null`, `runId | null`, `scan: { status: 'pending' | 'clean' | 'infected' | 'failed', checkedAt | null }`, `versionCount`. Upload adds `purpose` and optional `agentId`. New: `GET /files?agentId&purpose&scan&q&sort&cursor&limit` filters, `GET /files/{fileId}`, `GET /files/{fileId}/versions` (paged `FileVersion { id, createdAt, sizeBytes, sha256, commitHash | null, runId | null }`; agent project files are git-backed, so a version is a commit) and `?version=` on the content route. Content is always served as an attachment with `X-Content-Type-Options: nosniff`; infected files are not downloadable (409 `file-infected`). Added in API 1.6.0 for U-10: `purpose` and `scan` take comma-separated sets, `GET /files/stats?agentId` → `{ byPurpose, byScan }`, and `GET /files/upload-policy?purpose` → `{ purpose, maxBytes, accept }`, enforced on upload (413, 415); the client's `files.upload` takes `{ onProgress }`.
- **`src/capabilities/triggers.ts`** (`triggers@1`): `Trigger { id, agentId, name, kind, lifecycle: 'active' | 'paused' | 'ended' | 'failed', endedReason: 'completed' | 'cancelled' | 'max-runs' | null, lastFiredAt | null, nextFireAt | null, createdBy, createdAt, updatedAt }` with a discriminated `config`: `email { address }` (engine-assigned; each inbound email starts an `email`-source run), `schedule { recurrence: { kind: 'once', at } | { kind: 'interval', everySeconds } | { kind: 'cron', expression, timeZone }, startsAt, endsAt | null, maxRunCount | null, runCount, message }`, `webhook` (shape only, `draft`). `TriggerFire { id, at, outcome: 'started' | 'skipped' | 'failed', runId | null, error | null }`. Routes: `GET /triggers?agentId&kind&lifecycle&cursor&limit`, `GET /triggers/{id}`, `GET /triggers/{id}/fires` (`triggers.read`); `POST /triggers` (schedule or email), `PATCH /triggers/{id}`, `POST /triggers/{id}/pause`, `POST /triggers/{id}/resume`, `DELETE /triggers/{id}` (`triggers.manage`). Pause and resume are idempotent; resuming an ended trigger is 409 `trigger-ended`; a bad cron, time zone or range is 422 `invalid-schedule`. Added in API 1.7.0 for U-11: `agentName` (string ≤ 256 | null) like `Run.agentName`, `GET /triggers/stats?agentId` → `{ active, paused, failed, ended, nextFireAt | null }`, `invalid-schedule` names the field at fault in `errors[].path`, and the client reads an unknown trigger kind, recurrence, lifecycle, ended reason or fire outcome as `unknown`, keeping the raw kind and lifecycle (`TriggerReader`, `TriggerFireReader`); the engine-side schemas stay closed.
- **`src/capabilities/integrations.ts`** (`integrations@1`): `Integration { id, agentId | null (engine-wide), name, kind, status: 'connected' | 'needs-attention' | 'disconnected' | 'error', statusDetail | null, scopes: string[], secretRefs: [{ name, secretId | null, state: 'resolved' | 'missing' | 'revoked' }], tools: [{ name, description | null }], lastActivityAt | null, createdBy, createdAt, updatedAt }` with discriminated `config`: `mcp-server { url }`, `calendar { provider, account }`, `repository { provider: 'github', repository }`. Routes: `GET /integrations?agentId&kind&status&cursor&limit`, `GET /integrations/{id}` (`integrations.read`); `POST /integrations` (MCP server and repository; calendar connection is an engine-side OAuth flow, `draft`), `PATCH /integrations/{id}`, `POST /integrations/{id}/enable|disable`, `POST /integrations/{id}/check` (re-tests the connection), `DELETE /integrations/{id}` (`integrations.manage`). Secrets are referenced by name only; no schema has a value field. Added in API 1.8.0 for U-12: `status` takes a comma-separated set, `includeEngineWide=true` with `agentId` also lists the engine-wide integrations, `GET /integrations/stats?agentId` → `{ connected, needsAttention, disconnected, error }`, and the client reads an unknown `status` or secret reference `state` as `unknown` (`IntegrationReader`); the engine-side schemas stay closed.
- **Activity** (`src/capabilities/activity.ts`): `ActivityBase { kind, v, id, at, agentId | null, actor: { kind: 'member', memberId } | { kind: 'system' } | { kind: 'trigger', triggerId } }`, discriminated on `kind` and `v`. v1 kinds: `run.queued`, `run.started`, `run.completed`, `run.failed`, `run.cancelled` (`runId`, `source`, `usage` or `error` summary); `file.created`, `file.deleted`, `file.scan-failed`; `trigger.fired`, `trigger.failed`, `trigger.paused`, `trigger.resumed`; `integration.connected`, `integration.error`, `integration.used` (`toolName`); `member.joined`, `member.role-changed`, `member.removed`; `engine.update-available`, `engine.updated`, `engine.relay-disconnected`. Activity carries IDs and short names, never message or file content. Each prefix is visible only with its read permission (`runs.read`, `files.read`, `triggers.read`, `integrations.read`, `members.read`; `engine.*` needs `security.read`) and only for agents the member may read. `GET /activity?agentId&kind&runId&triggerId&integrationId&from&to&cursor&limit` (`kind` exact or a prefix such as `run.`; route permission `agents.read`, items filtered as above), newest first.
- **Events:** `EngineEvent` gains `{ type: 'activity', activity }` and change hints `{ type: 'run.changed', runId, agentId, status }`, `{ type: 'trigger.changed', triggerId, agentId }`, `{ type: 'file.changed', fileId, agentId | null }`, `{ type: 'integration.changed', integrationId, agentId | null }`, filtered like activity. The client ignores event types it does not know.
- **Unknown-kind fallback:** `parseActivity(input)` → `{ kind: 'known', activity } | { kind: 'unknown', base, raw } | { kind: 'invalid', base, issues }`. `ActivityBase` must always parse (else the item is dropped and counted). Unknown `kind` or a higher `v` gives `unknown`; a known kind and version that fails its strict schema gives `invalid` (conformance fails it). The page envelope stays strict, and one bad item never fails a page or the stream. Same rule for open sets inside models: an unknown integration `kind` parses as `{ kind: 'unknown', rawKind }` with `config` omitted; closed enums (statuses) change only with a new capability version.
- **Client and in-memory client:** `EngineApiClient` gains groups `runs`, `files` (moved), `triggers`, `integrations`, `activity`. `createInMemoryEngineApiClient` takes `capabilities?` (default all four) and seeds believable data for each; its controller (test-only) can append activity, advance a run, fire a schedule and emit events, driven by the injected clock, so UI tests are deterministic.
- `openapi.json` regenerated; capability routes carry `x-capability`.

## Out of scope

- Serving it with seeded data and simulation (M-07); conformance checks (M-07 extends C-05); UI (U-08 to U-12).
- Generic webhooks, per-tool approvals, starting runs outside chat and triggers (later capability versions).

## Design notes

- File layout: `src/capabilities/{capability,runs,files,triggers,integrations,activity}.ts`, each exporting its schemas, `*_ROUTES` and event schemas; `ENGINE_API_ROUTES` spreads them. Re-export through `src/index.ts`.
- Predecessor mapping (for E-01): sources `WEB_UI → web`, `OPENAI_API → api`, `TEAM_MEMBER → member`, `EMAIL → email`, `AGENT_GOAL → goal`, planned messages → `schedule`; tool states lowercased; trigger lifecycles `ONGOING | SCHEDULED | NOT_STARTED → active` (future `startsAt` means not started yet), `PAUSED → paused`, `CANCELLED | ENDED → ended` with `endedReason`, `FAILED → failed`; usage `price → cost`. Agent idle or running state is not stored: the UI derives it from runs.
- Money as a decimal string plus currency, never a float. Timestamps are C-04's `Timestamp`.
- Versioning per ADR 0010: additive within `@1`; a breaking change is `runs@2` with new schemas and routes next to the old ones.

## Acceptance criteria

- [ ] Schema tests: every new schema rejects unknown fields; no schema in the capability modules contains a `value`, `secret` or `token` field (extends C-04's test).
- [ ] Route-table test: every capability route declares `capability` and a permission; every mutating one a non-`.read` permission; OpenAPI lists `x-capability` and `x-required-permission`.
- [ ] `parseActivity` tests: unknown kind, higher `v` and a known kind with a broken payload each give their result; property test that arbitrary JSON never throws; a page with one unknown item still parses.
- [ ] `GET /engine` without `capabilities` parses as `[]`; `supports` handles two versions side by side and ignores unknown IDs.
- [ ] Shared client suite (in-memory and fetch over the in-process handler): paging and filters for runs, files, triggers, integrations and activity; cancel idempotent and 409 after completion; retry only from `failed`; pause and resume idempotent, 409 on ended; 422 `invalid-schedule`; a member without `runs.read` gets 403 on runs and sees no `run.*` activity or events; an unadvertised capability's routes return 404 `capability-not-supported`.
- [ ] `ENGINE_API_VERSION` is `1.1.0`; `openapi.json` regenerated; coverage stays at or above 90%.
- [ ] `bun run check` passes.
- [ ] **Status** line above set to `done (#<PR>)`.

## Risks and open points

- All four models are modelled on the predecessor; review them with the engine team before E-01. Field names may move; capability versions keep that cheap.
- C-04's strict response parsing means a UI built against 1.0 rejects a 1.1 `GET /engine`; the bundle manifest's `engineApi` range (X-03) must express that, or the client must tolerate extra fields there. Decide with X-03 instead of loosening schemas silently.
- `GET /activity` uses `agents.read` as the route permission because every item is filtered by its own read permission; an `activity.read` permission is an alternative if the engine team prefers it.
