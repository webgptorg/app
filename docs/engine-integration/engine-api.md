# Engine API

The engine API is the typed HTTP API our UI bundle uses, and the only thing it uses. Every engine implements it behind the [gateway](gateway.md). The contract is `@ptbk/engine-api`: zod schemas, one route table and an OpenAPI document generated from it.

Spec: [Engine security baseline](../spec/zero-trust-spec.md#engine-security-baseline), [Security hardening](../spec/zero-trust-spec.md#security-hardening) (preamble, 1, 5, 7, 8), [Enterprise-ready engine architecture](../spec/zero-trust-spec.md#enterprise-ready-engine-architecture), [Transparency and verifiability](../spec/zero-trust-spec.md#transparency-and-verifiability). ADRs: [0003](../adr/0003-ui-as-signed-bundle.md), [0010](../adr/0010-protocol-design-principles.md), [0016](../adr/0016-engine-capabilities.md). Package: [README](../../packages/engine-api/README.md).

## The contract

- **Route table:** `ENGINE_API_ROUTES` (and `ENGINE_API_ROUTE_LIST`) in [routes.ts](../../packages/engine-api/src/routes.ts) is the single source for the client, the OpenAPI document, the conformance suite and your server. Each `RouteDefinition` ([route.ts](../../packages/engine-api/src/route.ts)) has a method, a path, the required `permission`, strict params, query and body schemas, exactly one success response, its route-specific problems and the `stepUp`, `draft` and `capability` flags. Drive your server from it rather than re-typing paths.
- **OpenAPI:** [openapi.json](../../packages/engine-api/openapi.json) (OpenAPI 3.1, `servers` `/api/v1`) is generated by `buildOpenApiDocument` and committed. Each operation lists `x-required-permission`, `x-capability`, `x-step-up`, `x-draft` and its problem codes (`x-problem-codes`). Framework-agnostic: Hono, Fastify or anything else.
- **Version:** `ENGINE_API_VERSION` (`1.15.0`), SemVer. Additive changes bump the minor; until the contracts freeze (E-02), breaking changes are made in place and bump the minor too, listed under "What changed" in [AGENT_BRIEF.md](AGENT_BRIEF.md). 2.0 is reserved for the freeze. The UI bundle's manifest names the range it supports, and the [UI loader](ui-loader.md) refuses a bundle the engine's API version does not satisfy.
- **Base path:** `ENGINE_API_PREFIX` (`/api/v1`). A breaking change ships as `/api/v2` next to it.

## Requests and responses

The engine must:

- Parse every request strictly: unknown fields, unknown or repeated query parameters and out-of-range values answer 400 `validation-failed` (with `errors: [{ path, message }]`). JSON bodies require `application/json` (415 `unsupported-media-type` otherwise); uploads are `multipart/form-data`. Size limits are constants in [constants.ts](../../packages/engine-api/src/constants.ts) (`MAX_BOOK_SOURCE_LENGTH`, `MAX_MESSAGE_LENGTH`, `MAX_TEST_CHAT_MESSAGES`, `MAX_TEST_CHAT_TRANSCRIPT_LENGTH`, `MAX_FILE_BYTES`, `MAX_RUN_TEXT_BYTES`); larger bodies answer 413 `payload-too-large`.
- Send responses that match the strict response schema exactly: no undeclared fields. The UI reads responses tolerantly (`toTolerant`, `stripUnknownFields`), so an older UI keeps working when a newer engine adds an optional field within a version, but conformance fails an engine that sends fields the contract does not declare.
- Answer every error as RFC 9457 `application/problem+json` (`ProblemDetails` in [common.ts](../../packages/engine-api/src/common.ts), built like `createProblem` in [problem.ts](../../packages/engine-api/src/problem.ts)) with a `code` from the closed `PROBLEM_CODES` and its fixed status in `PROBLEM_STATUS` ([problem-codes.ts](../../packages/engine-api/src/problem-codes.ts)). The problem's `status` must equal the HTTP status. Clients branch on `code`, never on `type` or `title`. No stack traces, SQL or upstream messages; an unexpected error is 500 `internal-error`.
- Should send `Cache-Control: no-store` on API responses, as the HTTP binding `serveEngineApiRoute` does.

### Pagination

- Lists take `PageQuery` (`cursor`, `limit` 1–`MAX_PAGE_LIMIT` 100, default 50) and return a page `{ items, nextCursor }`, where `nextCursor` is `null` on the last page.
- Cursors are opaque strings of at most `MAX_CURSOR_LENGTH`. A malformed or expired cursor, or one from another sort order, is 400 `invalid-cursor`.
- Order must be stable under inserts: walking all pages gives no duplicates and no gaps. The in-memory engine uses keyset paging ([paging.ts](../../packages/engine-api/src/in-memory/paging.ts)); the format is the engine's choice.

### Server-sent events

- Three routes stream `text/event-stream`: `GET /events`, `GET /chats/{chatId}/messages/{messageId}/stream` and, with `test-chat@1`, `POST /agents/{agentId}/test-chat`. Each event's `type` is also its SSE `event` field, and `data` is the event as JSON (`encodeSseMessage` in [sse.ts](../../packages/engine-api/src/sse.ts)).
- **Message stream** (`ReplyStreamEvent` in [chats.ts](../../packages/engine-api/src/chats.ts)): any agent message still `streaming` streams its partial text as `delta { seq, text }` with `seq` (1, 2, …) as the SSE id, then exactly one `completed { message }` or `failed { problem }`. A reconnect with `Last-Event-ID: <seq>` continues after that delta with no duplicates. `POST …/cancel` stops a reply in progress; the stream then ends with `failed` and code `cancelled`. Cancel is idempotent, and 409 `reply-finished` once the reply completed. Sending a message answers 202 `{ message }`: replies are entries of their own, which `chat.changed` announces.
- **Engine events** (`EngineEvent` in [events.ts](../../packages/engine-api/src/events.ts)): change hints with IDs only, never content, each sent only to members holding the matching read permission. Every event has an SSE id, and the stream resumes after `Last-Event-ID`. The engine keeps a bounded buffer of recent events: a `Last-Event-ID` that is unknown or no longer buffered resumes from the oldest buffered event. IDs keep increasing across dropped events and gaps are not signalled, so the UI refetches what it shows on every reconnect. Clients ignore event types they do not know, so an engine may add types within a version.
- Wallet passwords and field values never appear in any stream.

### Chats

A chat is the engine's thread, its `CHAT` Book (Reborn `specs/cli/chats.md`): members join over time, every message has its real author, and the title and status change. Nobody owns a thread; every member with `chats.write` writes in any of them.

- **IDs are the engine's.** `ChatId` is the thread's normalized `CHAT` name and `MessageId` is `<chat>#<position>` today; both are opaque, printable, up to 512 characters, so they may hold spaces, `—` and `#`. Clients percent-encode them in paths.
- **`Chat`**: `title` (the latest `CHAT TITLE`), `status` (`CHAT STATUS`: `open`, `waiting-for-user`, `resolved`), `members` (`{ kind, key, name }` in join order; an agent's key is its `AgentId`, the User's is `user`; the first agent is the main agent), `messageCount`, `lastMessageAt`, `preview` (the newest message as plain text, whitespace collapsed, cut to `MAX_CHAT_PREVIEW_LENGTH`), `unread` (agent messages since the calling member last marked the thread read) and `questions` (outstanding `+@User` questions: `{ id, messageId, author, seen }`). A thread may have no User: agents talking, or the one-agent `Report`.
- **Entries**: `GET /chats/{chatId}/entries` lists the thread newest first as `message`, `joined`, `titled`, `status` and `linked` entries, in the order the engine recorded them. A participant's `joined` comes before its first message. Every `Message` has `author: { kind, key }`, `createdBy` (the member who sent a User message, else `null`) and `choices` (answers an agent offers). Clients skip entry types they do not know.
- **Starting**: `POST /chats` with no `agentId` starts the thread with Chatter (409 `chatter-missing` when the engine has none; never another agent silently), or with the agent named. The User and the agent join at once.
- **Sending**: `POST /chats/{chatId}/messages` writes as the User; the User joins first if it was not a member. `replyTo` names the question the message answers; saving it clears that question at once. Without `replyTo`, the message answers a question only when exactly one waits, and the engine routes it as Reborn does (the question's author, an agent the message brings in, else the main agent).
- **Idempotency**: `createChat` and `sendChatMessage` take an optional `requestKey` (`[A-Za-z0-9_-]{8,128}`), scoped to the member (and the thread, for sends). A repeat with the same key and the same request answers the original result and creates nothing; the same key with a different request is 409 `request-key-reused`. The UI sends a key with every message and resends under it when an answer was lost.
- **Read and seen**: `POST /chats/{chatId}/read` sets the caller's `unread` to 0. `POST /chats/{chatId}/seen` with `{ messageIds }` marks the questions in those displayed messages seen for everyone; it answers nothing, resolves nothing and is idempotent. Both need only `chats.read`.
- **Attention**: `unread` is not a demand; `questions` is. A thread needs the User while it has questions, and an unseen one is the stronger signal. Seen and answered are separate: a seen question keeps waiting until a saved answer (or its agent withdrawing it) removes it.

#### What agents do in a thread

Added 2026-11-13 (C-14). A thread shows what its agents are doing, not only what they wrote. Every field below is required in what the engine sends; the UI's readers default each one (`null`, `[]`) for an engine that predates them.

- **A turn.** An agent's turn is everything it does to answer, from the moment the engine decides it will answer until its reply is saved, fails or is cancelled. A turn that takes a while is saved as one or more `progress` messages followed by one `final` reply. A quick turn with no saved progress is one ordinary message.
- **`Message.phase`** (`MESSAGE_PHASES`):
  - `progress`: an interim update saved during the turn.
  - `final`: the reply that ends a turn that saved progress.
  - `null`: every other message, every User message among them.
  - A `progress` message with no `final` after it from the same agent is a turn that never finished (interrupted or failed).
- **`Message.steps`** (`ReplyStep[]`, at most `MAX_REPLY_STEPS` = 200, oldest first): what the agent did in this turn. It is empty unless `phase` is `progress`. When a turn has more steps, it spans several `progress` messages. A `ReplyStep` is:
  - `kind`: `reasoning` (the model thinking), `tool` (a tool call the harness made) or `note` (anything else the engine reports, such as a warning or the reason a turn stopped).
  - `tool`: the tool's name exactly as the harness reports it (`Read`, `Glob`, `mcp__ptbk__create_task`), 1 to 128 characters. It is set for a `tool` step and `null` for every other kind; the schema refuses both mismatches.
  - `text`: one line, at most `MAX_REPLY_STEP_TEXT_LENGTH` = 500 characters, whitespace runs collapsed: the tool's main argument, a reasoning excerpt or the note. It may be empty (a reasoning step with nothing to show).
  - `level`: `info`, `warning` or `error`.
- **A `progress` message's `content`** stays a readable rendering of its steps, so a client that ignores `steps` still shows something sensible. One line per step: `- thinking: <text>`, `- <tool> <text>`, `- <text>` for an `info` note and `- <level>: <text>` for any other note. Streamed partial text and an unfinished note may follow after a blank line. Reborn's `ReplyProgress.render()` already writes reasoning and tool lines this way.
- **`Chat.working`** (`ChatWorking[]`, in the order the turns started; empty when nobody works) lists the agents writing a reply now:
  - `author`: the agent, already a member of the thread.
  - `startedAt`: when the turn started, before the agent has done or written anything. This is what lets the UI show "Chatter is working" at once instead of nothing.
  - `steps`: its latest steps, at most `MAX_WORKING_STEPS` = 20, oldest first.
  - `messageId`: the `streaming` message this turn writes, once the thread lists one; `null` while the agent only works.

  The entry disappears when the reply is saved, fails or is cancelled.

- **`Chat.tasks`** (`ChatTask[]`, at most `MAX_CHAT_TASKS` = 100, in the order they came in): the tasks this thread created or links, with their live state.
  - `name`: the task's Book name, 1 to 512 characters. This is what `{name}` refers to in message text and what a `linked` entry names.
  - `taskId`: the same task's ID in `tasks@1`. `null` when the engine does not advertise `tasks@1` or the name does not resolve.
  - `state` (`CHAT_TASK_STATES`): `queued`, `running`, `waiting`, `blocked`, `completed`, `failed`, `cancelled`, `retired`. It is the engine's own task state, never a guess from the thread.
  - `detail`: its phase, waiting reason, blocker or result summary, in plain words, at most 500 characters, or `null`.
  - `agentId`: the agent working on it or the one that finished it, or `null`.
  - `commit`: the result commit of a `completed` task (7 to 64 lowercase hex), else `null`.
  - `reopened`: it was reopened after an earlier completion or cancellation.
  - `startedAt`: when it first ran. `endedAt`: when it reached `completed`, `failed`, `cancelled` or `retired`. Both are `null` before that, or when the engine no longer knows. An unfinished task never has an `endedAt`.
- **The `linked` entry** `{ type: 'linked', id, chatId, createdAt, task }` marks where in the thread a task came in (the Book's `LINK {name}`). `task` is a name in `Chat.tasks`, and every task in `Chat.tasks` has one `linked` entry.
- **`Chat.recheck`** (`ChatRecheck`, or `null`): a failed reply that the engine attempts again by itself.
  - `cause`: the last failure, in plain words, 1 to 500 characters (never empty).
  - `nextAt`: when the engine attempts it.
  - `rounds`: attempts scheduled so far, at least 1.

  While an attempt runs, `recheck` is `null` and the agent is in `working`. If the attempt fails, `recheck` returns with `rounds` one higher. Once it succeeds, `recheck` stays `null`.

- **`POST /chats/{chatId}/retry`** (`retryChatReply`, permission `chats.write`, no body) attempts the thread's recheck now instead of at `nextAt`, and answers 200 with the `Chat`:
  - A second call while that attempt runs changes nothing and answers 200 too.
  - Without a recheck, and with no attempt running, it answers 409 `nothing-to-retry`.
  - Audit it as `chat.reply.retry` (target the `chat`), like `chat.reply.cancel`; a 409 is audited `failed` and a missing permission `denied`.
- **`chat.changed`** fires on every change to a thread's fields or entries, including:
  - a turn starting or ending;
  - a progress message saved or updated in place;
  - a task's state or `detail` changing, or a new `linked` entry;
  - a recheck appearing, disappearing or moving.

  Step updates are the exception: they fire at most once a second per thread. The first one fires at once, and the latest one fires within a second, so a busy agent does not make every client refetch the thread many times a second.

- **Untrusted text.** Step text, task names, `detail` and `cause` are agent or tool output. The UI renders them as text and never makes them links or controls. The engine applies the redaction it applies to harness output (bridge secrets) before a step leaves it.

### Wallet secrets are write-only

- Passwords and additional field values are accepted in `POST /wallet/records` and `PUT /wallet/records/{recordId}` and returned by no response, stream, log, error or audit entry. `WalletRecord` has neither; its `fields` carry labels only. See [Wallet](#wallet).
- Clients read tolerantly and drop unknown fields, so a `password` an engine wrongly sent would be dropped before the UI sees it. That is a safety net, not the check: conformance's `engine-api.secrets.never-returned` is what proves an engine never returns them.
- The only response that carries a credential is `POST /api-tokens` (`CreateApiTokenResult`, shown once; the engine stores tokens hashed). The invite URL from `POST /invites` is likewise returned once.
- Integrations reference the engine's named tool secrets (`SecretRef`), never by value. No route lists or sets those; the engine manages them itself.

## Permissions

The contract is multi-member from day one, even though v0 has only the owner. Nothing may assume a single user.

- `GET /me` returns `{ memberId, orgId, displayName, role, permissions }` (`Me` in [me.ts](../../packages/engine-api/src/me.ts)) with the member's explicit permissions. The UI renders by `permissions`, never by `role`.
- `Permission` ([permissions.ts](../../packages/engine-api/src/permissions.ts)) is a closed list; `Role` is `owner`, `admin`, `member` or `viewer`. Which role holds which permission is engine policy. The contract guarantees only that `owner` holds every permission (`OWNER_PERMISSIONS`).
- Every route except `/me`, `/me/**` and `/engine` declares a permission, and every mutating route a non-`.read` one. Without it the engine answers 403 `forbidden` with the extension `requiredPermission`, changes nothing, and audits the attempt with outcome `denied`.
- The own-credential routes under `/me` (`permission: null`) act only on the caller's own passkeys and sessions. Another member's ID or an unknown ID answers 404 `not-found`, never 403, so IDs cannot be probed. `DELETE /me/passkeys/{passkeyId}` refuses the caller's last passkey with 409 `last-passkey`. `POST /me/sessions/revoke-others` keeps the current session.
- Record which passkey signed each session in (`Session.passkeyId`). Revoking a passkey, under `/me` or `/passkeys`, ends every session it signed in, the caller's own included; the UI warns before revoking the current session's passkey. Report each passkey's authenticator (`Passkey.authenticator`: WebAuthn `authenticatorAttachment` from registration and the backup state flag from the last assertion) and each member's `passkeyCount`.
- Authorisation runs in one policy module, deny by default, against the resource's owner (resources carry `createdBy`), never only in middleware. A resource the member may not see answers 404. The in-memory engine models this as an `Authorizer` port, `can(actor, permission, resource)`, whose default `PERMISSION_AUTHORIZER` allows exactly the actor's permissions; a denial keeps the 403 `forbidden` answer and the `denied` audit entry.
- A role change or a removed member applies on the next request; a revoked session fails within one request.
- Since API 1.12.0, removing or demoting the last active owner answers 409 `last-owner`, so an engine always keeps someone who can manage it. Removing a member also deletes their passkeys and ends their sessions.

## Wallet

Capability `wallet@1`: the engine's Wallet, its secret manager (Reborn `specs/cli/wallet.md`, `specs/app/integration.md` "Wallet and in-App attention"). It maps one-to-one onto the engine's `wallet`, `wallet-save`, `wallet-remove`, `wallet-seen` and `wallet-reject` operations. Setup, the 12 words for recovery, restore, rotation, reset, import and credential tests are not in this API: they stay on the engine's own owner surfaces, as the engine already refuses them to API clients.

- `GET /wallet` (`wallet.read`) answers `WalletOverview`: `state` (`ready`, `empty`, `setup`, `locked`, `unavailable`), the saved logins (`records`, only while `ready`), `lockedRecords` while `locked`, and the pending agent requests (`pending`, oldest first). A login carries its editable `label`, `origin`, `username` (the nonsecret account metadata the engine already gives agents), additional field labels, `lastUse` and the latest credential test (`verification`, `null` when never tested).
- A request (`WalletRequest`) is one per unresolved origin, account and step: `problem` (`missing`, `rejected`, `locked`, `code`, `field`), the requested field labels, the saved login it is about (`recordId`), the engine's nonsecret `reason`, the waiting `tasks` and requesting `agents` by name (the responsible one first; empty for system work, which Fixer owns), `requests` (how often work asked), `seenAt` and `step`.
- `POST /wallet/records` and `PUT /wallet/records/{recordId}` (`wallet.manage`) take `{ origin, username, password, label?, fields?, requestId? }` and answer `{ record, resolvedRequestIds }`. A login for the same origin and username is updated, not duplicated. Fields change only the labels named; an empty value removes one; at most `MAX_WALLET_FIELDS` (12). A save resolves the pending requests for that origin (and `requestId`), except `code` requests, and leaves the login unverified (`verification: null`) until the engine tests it. `DELETE /wallet/records/{recordId}` removes one login. All three answer 409 `wallet-not-ready` unless the Wallet is `ready`.
- `POST /wallet/requests/{requestId}/seen` (Mark as seen) and `…/reject` (Reject request) take `{ step }`, the step the member saw. Seen sets `seenAt` and keeps the request waiting (idempotent for the same step); reject ends it and tells the waiting work nothing was provided (204). Another step answers 409 `wallet-request-moved`; a request that is no longer pending answers 404.
- Adding, updating and removing a login need step-up (401 `step-up-required` without a fresh passkey assertion): a stolen session must not point an agent at an account it chose. Mark as seen and Reject request do not. Audit `wallet.record.save`, `wallet.record.update`, `wallet.record.delete`, `wallet.request.seen` and `wallet.request.reject` (targets `wallet-record`, `wallet-request`), with field names only in `details`.

## Access requests

Capability `access-requests@1`, since API 1.12.0. People an organization invites in the dashboard ask for access on the engine, and someone already on it approves them ([teams spec](../spec/teams.md#adding-a-person), [ADR 0018](../adr/0018-teams-and-member-access.md)). The dashboard never adds a member itself.

- The gateway's join page (`/auth/join`, [gateway.md](gateway.md#access-requests)) turns a valid dashboard ticket and a new passkey into a pending request, shown to the person with a 6-digit code. At most `MAX_PENDING_ACCESS_REQUESTS` (20) wait at once; each expires after `ACCESS_REQUEST_TTL_MS` (7 days); a second ticket for the same `dashboardUserId` replaces the earlier request.
- `GET /access-requests` (`members.read`) lists them oldest first: `displayName`, `email` and `proposedRole` from the ticket, which are untrusted hints. The code is never returned.
- `POST /access-requests/{accessRequestId}/approve` (`members.manage`, step-up) takes `{ code, role }`. A wrong code is 422 `access-code-mismatch` and leaves the request pending, except the fifth wrong code for a request (`MAX_ACCESS_CODE_ATTEMPTS`), which also deletes it; the join page then reports the request declined and the person needs a new ticket. Count per request, not per approver. On a match the request becomes a member with the role, the request's passkey and `Member.dashboardUserId`; answer 201 with the member. `DELETE` declines and discards the passkey.
- `PUT /settings/dashboard-removals` (`settings.manage`, step-up) takes `{ enabled }`; `Settings.dashboardRemovals` reports it, `true` by default and `null` from engines without the capability. When it is off the engine refuses the dashboard's signed member revocations (protocol, C-13), but still deletes a pending request from the person the revocation names: a request is not access.
- Audit `access-request.approve` (target the new member), `access-request.decline` (target `access-request`), `settings.dashboard-removals`, and `member.revoke` with a `system` actor when a dashboard revocation disables a member.

## Step-up

- Routes flagged `stepUp` (`x-step-up` in OpenAPI) need a fresh passkey assertion. Without one, the engine answers 401 `step-up-required`; the UI sends the member to `STEP_UP_PATH` and retries. The in-memory engine audits a refused step-up as `denied`; the engine should too.
- Flagged today: `PUT /settings/update-policy`, `PUT /settings/dashboard-removals`, `POST /api-tokens`, `DELETE /passkeys/{passkeyId}`, `DELETE /me/passkeys/{passkeyId}`, `PATCH /members/{memberId}`, `DELETE /members/{memberId}`, `POST /invites` and `POST /access-requests/{accessRequestId}/approve`. Which further routes need it is an open point.

## Audit

- Every mutation, and every denied attempt, appends an `AuditEntry` ([audit.ts](../../packages/engine-api/src/audit.ts)): `seq`, `at`, `actor` (`member` with `memberId`, `api-token` with `apiTokenId` and `memberId`, or `system`), `action` from the closed `AUDIT_ACTIONS`, `target { kind, id, name }` from `AUDIT_TARGET_KINDS`, `outcome` (`success`, `denied`, `failed`), `client { ip, userAgent }`, `details` and the hash chain `hash` and `prevHash`.
- Since API 1.4.0, `target.name` is the target's name as it was when the action happened (agent, folder, secret, API token, passkey, file, trigger or integration name, chat title, member display name), at most `MAX_AUDIT_TARGET_NAME_LENGTH` (256) characters, or `null` for a target without a name. Record the snapshot, not a lookup at read time, so a rename or delete leaves the entry readable. It is untrusted text: members type these names, and the UI renders them as text only.
- Since API 1.4.0, `details` is a JSON object with what the engine adds about the action, or `null`: for example the names of the fields a request set, or the problem `code` and `requiredPermission` of a refusal. Never put secret values, tokens, message content or file content in it. At most `MAX_AUDIT_DETAILS_BYTES` (16 KiB) as JSON and `MAX_AUDIT_DETAILS_DEPTH` (8) levels deep, the object itself being level 1; the strict schema refuses anything larger. Clients treat it as untrusted text too.
- Both fields are optional, so 1.3 engines still parse. A client reads an `action` it does not know (a newer engine's, matching `AUDIT_ACTION_PATTERN`) as its raw name instead of failing the page; the engine's schema stays closed to the list.
- `actor.memberId` is the member of the acting session, the same `memberId` that `GET /me` returns for it. `client.ip` is the address from the tunnel's `OPEN` frame; `userAgent` is truncated to `MAX_USER_AGENT_LENGTH`. `client` is `null` for system actions.
- The log is append-only and hash-chained: `prevHash` of entry n equals `hash` of entry n − 1 and is `null` only for the first. How `hash` is computed is the engine's choice; the in-memory engine's rule is in [audit-chain.ts](../../packages/engine-api/src/in-memory/audit-chain.ts). Whatever the rule, `hash` must cover `target.name` and `details` as well as every other field, or an edit to them would pass `GET /audit/verify`. The in-memory rule changed in 1.4.0 for that: `target` is hashed with its `name`, and `details` (`null` when absent) is appended last to the hashed array.
- `GET /audit/verify` re-walks the whole chain and reports `{ status, checkedEntries, lastSeq, firstBrokenSeq, checkedAt }`.
- **Engine requirement, not yet in the contract:** the hash chain must be complemented by engine-signed checkpoints, `signingInput('ptbk-audit-checkpoint-v1', …)` over the latest `seq` and its hash, so that truncating the chain's tail is detectable. C-04 will add a `checkpoint` field to `GET /audit/verify` that reports the latest checkpoint. The checkpoint payload, cadence and where checkpoints are published are an engine design point ([README, open points](README.md#open-points)). `ptbk-audit-checkpoint-v1` is not in `SIGNING_CONTEXT` yet.

## Security panel

`GET /security` (`SecurityOverview`) is what the owner uses to check the engine without trusting us. It reports the engine's own values verbatim; the UI does not reformat or recompute them.

- **Engine and UI bundle:** the engine version with its release's Rekor log index and entry UUID, update status and policy; the UI version, bundle SHA-256, log index and entry UUID, and the loader's last update check (`ui.lastUpdateCheck`: outcome, version, and for a refusal the reason from `UI_REFUSAL_REASONS` with the revocation reason for `revocations-unverifiable`). Report every check, so a refused or unverifiable release shows in the panel and not only in the logs.
- **TLS:** the certificate's SHA-256 (to compare with the browser's padlock), and the last Certificate Transparency check; for `unexpected-certificate`, list what was found in `unexpectedCertificates` (SHA-256, issuer, validity; at most 16).
- **Relays and hostnames:** every relay's status, since when, and the last tunnel ping's round trip (`lastPingRttMs`); every hostname with its kind, its certificate status and, for a custom domain, whether the dashboard holds its signed claim (`claimRegistered`; `null` for the default hostname).
- **Heartbeat:** the last body **verbatim** with the exact `Ptbk-Signature` header value sent with it ([heartbeat.md](heartbeat.md)), and `clockSkew`: the engine's clock minus the dashboard's `serverTime` from the last `stale-timestamp` refusal, `null` while unknown or once a beat is accepted again.
- **Outbound destinations:** every destination the engine contacts.

The fields added in API 1.3.0 default to `null` or `[]`, so a client reads a 1.2 engine's answer; an engine on 1.3 sends them all. Since API 1.10.0, `ui.lastUpdateCheck.eligibleAt` is when a delayed release becomes eligible, set exactly when `reason` is `delay-not-elapsed` (`null` otherwise and from older engines), so the owner sees when it installs. The client reads an update outcome, refusal reason, revocation reason or certificate status it does not know as `unknown`.

## Onboarding

Capability `onboarding@1` (2026-11-05, [onboarding.ts](../../packages/engine-api/src/capabilities/onboarding.ts)): the engine's own initializer (Reborn `ptbk init`, `specs/cli/initialization.md`) drives setup after pairing, one prompt at a time, the way the engine's desktop client presents it through `src/ui/prompt-transport.ts`. The UI renders the prompt and returns the answer; the engine validates it, decides what comes next and when setup is done. Choice values, drafts and login state stay in the engine.

- `GET /onboarding` (`settings.manage`): `{ status: pending | working | completed, deferred, progress: { step, of } | null, prompt | null }`. A prompt is present exactly while `pending`. Poll while `working` or a harness login is `waiting` or `verifying`.
- Prompt kinds, each with `id` (new per presentation), `title`, `question`, `hint`, `error` (why the last answer was refused) and `canGoBack`: `text` (single line or the long intent field; `attachments` means files may go with it), `choice` (one or many; opaque choice IDs, `initial` preselects), `confirm`, `upload` (files uploaded first through `files@1` with purpose `upload`, then named by ID), `harness-login` (the harness's native sign-in as it offers it: `device-code` shows `url` and `userCode` to type at the provider; `return-code` shows `url` and takes the code the provider hands back; `status` is `waiting`, `verifying`, `succeeded`, `failed`, `expired`, `denied` or `unsupported`, with the engine's `diagnostic`).
- `POST /onboarding/answer` `{ promptId, action: answer, answer }` or `{ promptId, action: back }`: answers the current prompt and returns the new state. A `promptId` that is not current is 409 `onboarding-prompt-stale`; an answer of another kind 400 `validation-failed`; an answer the engine cannot accept comes back as the same prompt with `error`. `{ kind: harness-login, returnCode: null }` starts the sign-in again.
- `POST /onboarding/defer` ("Skip for now"): setup stays pending and reachable from home; the engine may set itself up through its built-in agents, and the UI goes to a chat with Chatter.
- Login codes and returned codes are transient: never logged, audited, stored, put in a Book or sent as a chat message. Wallet setup and recovery words are not part of this flow.

## Agent origin

Every `Agent` carries `origin` (2026-11-05), as the Reborn engine models agents ([core agents](../../packages/engine-api/src/agents.ts), Reborn `specs/agents/core-agents.md` and `system-agents.md`): `content` for the project's own agents, `core` for the roles the engine prepares as ordinary project Books (Chatter, Adam, Tasker, Router, Fixer, Teacher), `system` for agents the engine defines itself with no project Book (Expert). Origin grants nothing. `GET /agents?origin=` takes one origin or a comma-separated set; the UI lists `content` agents first and `core,system` in a quiet "Built-in" section, each with `profile.description` as its one-line role. Agents created through `POST /agents` are `content`. A `system` agent belongs to the engine: `PATCH`, `DELETE`, `restore` and `PUT .../source` on it are 409 `agent-engine-owned` and change nothing. The UI lists Chatter first, then the other core agents, then the system ones.

## Capabilities

- `GET /engine` (`EngineInfo`) returns `capabilities: [{ id, version }]` (`CapabilityRef`) and `engineId`. `KNOWN_CAPABILITIES` lists `runs@1`, `tasks@1`, `files@1`, `triggers@1`, `integrations@1`, `test-chat@1`, `access-requests@1`, `file-scanning@1`, `members@1`, `api-tokens@1`, `audit@1`, `book-editor@1` and `agent-management@1` ([capability.ts](../../packages/engine-api/src/capabilities/capability.ts)).
- **The engine is the source.** The UI shows a screen only when the engine reports it, so features the Reborn engine does not have are capabilities too, not core (2026-11-05):
  - `members@1`: roles, invites, role changes and removals (`PATCH`/`DELETE /members/{memberId}`, `/invites`). `GET /members`, `GET /members/{memberId}` and `/me` stay core. Without it, access is binary: whoever can sign in is the one level of member.
  - `api-tokens@1`: every `/api-tokens` route.
  - `audit@1`: `/audit` and `/audit/verify`.
  - `book-editor@1`: editing Books in the UI: `PUT /agents/{agentId}/source`, `POST /agents/validate` and the revisions. Reading the current source stays core. `test-chat@1` assumes it.
  - `agent-management@1`: agent forms: `PATCH /agents/{agentId}` (visibility, folder) and `POST /agents/{agentId}/restore`. Without it the UI offers no wizard, no Settings tab and no visibility or delete actions; agents come and change through chat with the engine's own agents. `POST /agents`, `DELETE /agents/{agentId}` and folders stay core for now, because the conformance suite uses them to set up its fixtures.
- `GET /activity` lists no item of a capability the engine does not advertise (`ACTIVITY_CAPABILITIES`: `run.*`, `file.*`, `trigger.*`, `integration.*`, `member.*`); engine activity is core.
- An engine advertises only what it serves, and may ship capabilities one at a time. Every route of a capability it does not advertise answers 404 `capability-not-supported`; the in-memory engine checks this before the permission.
- A breaking change is a new version (`runs@2`) served next to the old one; an engine may advertise both.
- Runs (`runs@1`, [runs.ts](../../packages/engine-api/src/capabilities/runs.ts)) since API 1.5.0 carry what the UI shows without a lookup per row. `Run.agentName` is the agent's name when you answer (the name it had when deleted, `null` if you no longer know it). `Run.preview` is the text that started the run: the user's message for a chat run, the subject of an inbound email, a schedule's message, an API or member request; whitespace runs collapsed to one space, cut to `MAX_RUN_PREVIEW_LENGTH` (200), `null` when nothing textual started it; a retry keeps the failed run's preview. `RunDetail.outputs.fileNames` names each entry of `outputs.files` in the same order, as the file was named when the run produced it, so outputs read without `files@1`; the schema refuses a different length. `RunStats.lastFinished` is `{ status, at }` of the run that finished last (by `completedAt`), or `null`. All three texts are untrusted: members and senders write them, and the UI renders them as text only. The client reads a `status` or `source` it does not know as `unknown`, in run responses and `run.changed` events; your schemas stay closed.
- Tasks (`tasks@1`, [tasks.ts](../../packages/engine-api/src/capabilities/tasks.ts)) report the engine's task inventory as the engine models it, read-only: work changes through chat with Chatter, never through a task route. One inventory holds ordinary (source-backed) and engine-owned tasks (`kind: 'engine'`, e.g. the self-update, with `executor` and no `sourcePath`). `GET /tasks` answers every task in your smart default order (current decisions, then upcoming, recent, distant and old work) and filters by `state` (a set), `kind`, `agentId`, `parentId` and `q` (name). `state` is your readiness projection verbatim (`active`, `awaiting-user`, `ready`, `needs-assignment`, `assigning`, `needs-recovery`, `failed`, `incompatible`, `blocked`, `waiting-until`, `waiting-dependency`, `not-ready`, `placeholder`, `done`, `cancelled`, `retired`), with `stateReason`, `next` and `conditions`. `Task.id` is your opaque transport form of the task's identity (its normalized Book name, or the engine-owned definition); a rename is a new task. `parent` is `TASK PARENT`, `dependsOn` is `TASK DEPENDS ON` with each prerequisite's standing (`met` only for a successful one; `missing` when the name does not resolve), `origin` is `TASK ORIGIN`, `doneCount`/`lastDoneAt`/`reopened` follow `TASK DONE` and `TASK REOPEN`. `GET /tasks/{taskId}` adds `children`, `blocks` (tasks whose `TASK DEPENDS ON` names this one), the directed `links` around the task (`outgoing` from its Book, `incoming` from the other Book; chats, agents and tasks) and `notes`. `GET /tasks/{taskId}/occurrences` pages the task's occurrences newest first: each work cycle, recurring slot, catch-up, reopening and retry, with its own outcome and the `runIds` that worked on it; `Run.taskId` and `Run.occurrenceId` link back. `allowedActions` lists the task-control operations you would accept for this task (`amend`, `accept`, `cancel`, `retire`, `reopen`, `notify`); report none (`[]`) until you decide to. `task.changed` events carry the ID and new state, gated by `tasks.read`.
- Files (since API 1.6.0): `GET /files` takes one `purpose` or `scan` or a comma-separated set (`scan=infected,failed`), like `GET /runs`'s `status`. `GET /files/stats?agentId` counts files by purpose and by scan status (`files.read`). `GET /files/upload-policy?purpose=` (`files.write`) answers that purpose's `maxBytes` (at most `MAX_FILE_BYTES`) and `accept`, a list in the grammar of HTML's `accept` attribute (`.pdf`, `text/plain`, `image/*`; empty takes any type). The upload route enforces the same policy: larger is 413 `payload-too-large`, a name and declared type that match no entry (`acceptsFile`) is 415 `unsupported-media-type`. The UI checks a file against the policy before uploading, so a refusal there is a contract mismatch, not the usual path.
- File scanning (`file-scanning@1`, since API 1.13.0) is optional: advertise it only if the engine scans every new file for malware. Without it, every `FileMetadata.scan` is `null`, a `scan` filter matches nothing, `byScan` counts zero, no download is refused as `file-infected`, no `file.scan-failed` activity is written, and the UI shows nothing about scanning. With it, `scan` is always `{ status, checkedAt }` and an infected file is never served (409 `file-infected`). The platform has no scanning service, so engines start without it.
- Triggers (since API 1.7.0): `Trigger.agentName` is the agent's name when you answer (the name it had when deleted, `null` if you no longer know it), like `Run.agentName`; untrusted text. A 422 `invalid-schedule` carries `errors` naming the request field at fault (`body.recurrence.expression`, `body.recurrence.timeZone`, `body.recurrence.at`, `body.endsAt`), like `validation-failed`, so the UI can show it on that field. `GET /triggers/stats?agentId` (`triggers.read`) counts triggers by lifecycle (`active`, `paused`, `failed`, `ended`) and answers the soonest `nextFireAt` among the active ones, or `null`. The client reads a trigger `kind` it does not know as `{ kind: 'unknown', rawKind }` without `config`, an unknown recurrence as `{ kind: 'unknown', rawKind }`, an unknown `lifecycle` as `unknown` next to `rawLifecycle`, and an unknown `endedReason` or fire `outcome` as `unknown` (`TriggerReader`, `TriggerFireReader`); your schemas stay closed.
- Integrations (since API 1.8.0): `GET /integrations` takes one `status` or a comma-separated set (`status=needs-attention,error`), like `GET /runs`'s `status`. With `agentId`, `includeEngineWide=true` also lists the engine-wide integrations (`agentId: null`) that agent may use, in the same order and paging; without it, `agentId` lists only the agent's own. `GET /integrations/stats?agentId` (`integrations.read`) counts integrations by status (`connected`, `needsAttention`, `disconnected`, `error`), engine-wide or of that agent alone. The client reads an integration `status` or secret reference `state` it does not know as `unknown` (`IntegrationReader`); your schemas stay closed.
- Activity (`GET /activity`, `activity` events) is a union discriminated on `kind` and `v` ([activity.ts](../../packages/engine-api/src/capabilities/activity.ts)). Each kind is visible only with its read permission (`ACTIVITY_PERMISSIONS`). Activity carries IDs and short names, never message or file content.
- Test chat (`test-chat@1`, since API 1.11.0, [test-chat.ts](../../packages/engine-api/src/capabilities/test-chat.ts)): the book editor's live test chat. `POST /agents/{agentId}/test-chat` (`agents.write`: only someone who may edit the book tests drafts of it) takes `{ book, messages }`: the unsaved book as typed and the whole conversation so far, oldest first, `{ role: 'user' | 'agent', content }` each, ending with the member's new message; at most `MAX_TEST_CHAT_MESSAGES` (50) turns of at most `MAX_MESSAGE_LENGTH` each and `MAX_TEST_CHAT_TRANSCRIPT_LENGTH` (256 Ki UTF-16 units) together, on top of a book of at most `MAX_BOOK_SOURCE_LENGTH`. Answer the agent's reply as it would be with that book, as SSE `TestChatEvent`s: `delta { seq, text }` with `seq` as the SSE id, then exactly one `completed { content }` (the whole reply) or `failed { problem }`. A book with an error diagnostic is 422 `invalid-book` with `diagnostics` before anything streams; a deleted agent is 409 `agent-deleted`.
  - **Store nothing.** No chat, message, revision, run, activity item, event or agent memory comes of a test, and nothing of it reaches another member. The request carries all the context, so the engine is stateless between turns. Closing the stream stops the reply; there is no cancel route and no `Last-Event-ID` resume, since nothing is kept to resume from: the UI sends the turn again.
  - **Audit the start, not every turn.** A test changes nothing, but it is the only trace of a model run against a book nobody saved, so record `agent.test-chat.start` (target the agent) once per conversation: on the request whose `messages` holds exactly one message. Follow-up turns write no entry; refusals are audited as `denied` like any other route. Never put the book or the messages in `details`.
  - **Rate-limit it per member or client**, tighter than the rest of the API (each request is a model call), answering 429 `rate-limited` with `Retry-After`. The mock engine allows 60 a minute.
  - Whether a test run may call the agent's tools and integrations is engine policy (see the [open points](README.md#open-points)); the UI labels it "Test · not saved", not a sandbox. An engine that does not advertise `test-chat@1` simply has no live test chat in the editor.
- Activity (since API 1.9.0): every item carries `agentName`, the agent's name when you answer (the name it had when deleted, `null` if the item has no agent or you no longer know it), like `Run.agentName`; untrusted text. The client reads a missing or malformed `agentName` on a kind it does not know as `null`, so the generic card still shows; on a known kind it is required.

## Reference implementation

Merged (M-04). The mock engine serves this API over the tunnel with seeded data, roles and faults, with no route written by hand: [api-routes.ts](../../apps/mock-engine/src/adapters/http/api-routes.ts) declares one route per `ENGINE_API_ROUTE_LIST` entry and hands each to `serveEngineApiRoute` with the request's `Actor`. Its role policy and ownership rule are in [policy.ts](../../apps/mock-engine/src/domain/authorization/policy.ts) (a guess to align with you, see the [open points](README.md#open-points)), and seeded scenarios in [seed.ts](../../apps/mock-engine/src/domain/state/seed.ts). Since M-07 it advertises every capability (`MOCK_CAPABILITIES` narrows them), with seeded data and a live simulation of runs and schedules driven only through the in-memory core's controller levers.

The mock builds on two parts of `@ptbk/engine-api`, which are the behavioural reference. They are meant for tests and UI development, not as an engine to ship:

- **`@ptbk/engine-api/in-memory`** ([in-memory.ts](../../packages/engine-api/src/in-memory.ts)): the in-memory engine, which implements every route with the contract's observable rules (strict input, permission checks, cursor paging, soft delete, revision conflicts, Wallet logins without passwords, the audit chain, events filtered by permission with a bounded buffer, capability gating, streamed replies). `createInMemoryEngineCore(options)` serves one shared state per request `Actor` (member, session, client, permissions, step-up freshness) through `transport(actor)`, with an optional `Authorizer`. Handlers are in [in-memory/handlers.ts](../../packages/engine-api/src/in-memory/handlers.ts).
- **`@ptbk/engine-api/http`** ([http.ts](../../packages/engine-api/src/http.ts)): the framework-agnostic HTTP binding. `serveEngineApiRoute(transport, route, params, request)` parses the query (a repeated parameter is 400), the body by media type and `Last-Event-ID`, and writes JSON, empty, attachment, SSE and problem+json answers; `createEngineApiHttpHandler(transport)` adds route matching under `ENGINE_API_PREFIX`, with literal segments before parameters. Source: [http/serve.ts](../../packages/engine-api/src/http/serve.ts).
- **`@ptbk/engine-api/testing`**: `engineApiClientSuite`, the shared client behaviour suite that the in-memory and fetch clients run, and that the mock engine runs over real HTTP through a relay.
