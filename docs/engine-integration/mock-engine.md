# The mock engine as reference implementation

`apps/mock-engine` is a real Node 24 process that speaks the real contracts with fake data, so the relay, the dashboard and the UI work end to end before the real engine exists ([ADR 0004](../adr/0004-mock-engine-and-conformance.md)). It has no shortcuts the real engine would not have: everything goes through `@ptbk/protocol` and `@ptbk/engine-api`. That makes it the executable reference for the engine team. Read its code next to this guide; its [README](../../apps/mock-engine/README.md) describes what runs today.

It is not a template for the real engine's internals: its data is fake, its sign-in is a stand-in, and it holds dev-only tooling that must never ship.

## Running it locally

From the repository root, with Node 24 and Bun installed (`bun install` once):

```sh
export PTBK_DATA_DIR="$(mktemp -d)"         # must be mode 0700, owned by you
export PTBK_ENGINE_DOMAIN=engine.localhost
export PTBK_RELAYS=wss://relay.localhost:8443
bun run --filter @ptbk/mock-engine identity # prints { engineId, enginePublicKey, hostname }
bun run --filter @ptbk/mock-engine dev      # or: build, then start
```

- It needs a relay to dial; without one it keeps reconnecting with backoff, which is enough to watch the tunnel state machine in its logs. The `identity` command prints what the relay's static registry needs.
- Certificates inside the tunnel come from a local dev CA, generated into `PTBK_DATA_DIR/dev-ca/`. The CA is name-constrained to the configured engine domain and excludes every IP address, so it is harmless if it leaks. To reach the engine from a browser or curl, trust `PTBK_DATA_DIR/dev-ca/ca-cert.pem` for the session and remove it afterwards.
- Every setting is in the README's configuration table. The spec's variables (`PTBK_MODE`, `PTBK_DATA_DIR`, `HTTPS_PROXY`, `NO_PROXY`) mean the same as for the real engine. `PTBK_ENGINE_DOMAIN`, `PTBK_DASHBOARD_URL`, `PTBK_LINK_CODE`, `PTBK_RELAYS`, `PTBK_UI_RELEASE_URL`, `PTBK_ENGINE_VERSION`, `PTBK_ACME_DIRECTORY_URL` and `PTBK_ACME_EMAIL` are the mock's own names; our test harnesses configure engines with them, so reusing them saves you a harness change ([testing-against-the-platform.md](testing-against-the-platform.md#engine-settings-the-harness-uses)). The `MOCK_*` variables are mock levers with no counterpart in a real engine. The mock refuses unknown `PTBK_*` and `MOCK_*` names at startup.
- The spike routes under `/__spike/` (whoami, SSE, WebSocket echo, screencast, download) exist to measure the relay. They are not part of the engine contract.

## Dev-only control endpoint

M-04 adds a control listener for tests ([control-server.ts](../../apps/mock-engine/src/adapters/control-server.ts)): scenarios, fault injection and session hand-out under `/__mock/`, enabled only with `MOCK_CONTROL=enabled`, on a separate plain-HTTP listener bound to loopback, never reachable through the tunnel, and refused at startup with `NODE_ENV=production`. Its dev login is likewise test-only.

**Never copy the control endpoint, the dev login or fault injection into the real engine.** They exist so tests can drive the mock; a real engine answers only to passkey sessions. How conformance gets sessions on the real engine is an open point ([conformance.md](conformance.md#sessions-on-a-real-engine)).
