# 0004. A mock engine and a conformance suite

- **Status:** Accepted
- **Date:** 2026-10-19

## Context

The engine team builds the real engine in the public repo, and that integration comes last. We still need the relay, the dashboard and engine-ui to work end to end in this repo, and the real engine must later drop in without changes on our side.

## Decision

- `apps/mock-engine` is a real process that speaks the real contracts: it registers with the dashboard, dials every relay in its list, terminates TLS for its hostname inside the tunnel (local CA, or ACME TLS-ALPN-01 against Pebble), sends signed heartbeats, runs the UI loader, and serves the engine API.
- Its data is fake but believable: generated by seeded faker, so the same seed gives the same agents, chats and members. State is in memory and reacts to mutations (create an agent, it appears in the list). Scenarios and fault injection (latency, errors, dropped streams, slow tunnel) are switchable at startup and at runtime through a dev-only control endpoint.
- `packages/conformance` is one test suite that any engine implementation must pass: tunnel handshake and framing, heartbeat, registration, engine API behaviour, UI loader checks. It runs against the mock engine in CI from day one and against the real engine when it exists.
- The mock engine has no shortcuts the real engine would not have: if the mock needs a capability, it goes through the contract.

## Consequences

- Swapping in the real engine means pointing the e2e and conformance runs at it. Nothing else changes.
- The mock engine doubles as the reference implementation and the executable spec for the engine team.
- Contract changes show up as conformance failures, which keeps the mock honest.
