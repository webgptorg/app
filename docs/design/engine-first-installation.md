# Engine-first installation, 18 November 2026

The existing Reborn engine owns durable onboarding, identity, private drafts, the passkey gateway, prompts, files and harness sign-in. This change completes Dashboard's installation presentation without replacing those mechanisms, adding heartbeat fields or billing, or sending project content to Dashboard.

## Configuration and response

`ENGINE_INSTALLATION` is optional reviewed fallback metadata: `version`, `windowsSha256`, `bootstrapRevision` (an immutable commit) and `bootstrapSha256`. Supported semantic versions start at `0.119.0-117`, including later prereleases and release lines. The pinned Ubuntu installer accepts versions without build metadata. Invalid or older versions fail startup. URLs derive from official release naming and the immutable bootstrap path. HTTPS Dashboard origin is required. A requester cannot supply an installer URL or shell fragment.

On each personal or team link-code issuance and each install-script request outside development, Dashboard reads `https://registry.npmjs.org/ptbk/latest`. A newer supported version is selected only when its exact `v<version>` GitHub release is published, is not a draft, and has exactly one uploaded `Promptbook-Setup-<version>-windows-x64.exe` with a GitHub SHA-256 digest. The served scripts (npm package, Ubuntu's `--version`, the Windows URL/checksum) and the Windows EXE tab with its continuation each use one exact selected version. Future releases need no Dashboard redeploy. A copied command gets the release that is current when it runs, not when it was copied.

Both metadata requests share a ten-second deadline and each response is capped at 512 KiB. The Worker requests a five-minute edge cache for successful public metadata to bound registry/GitHub traffic; error responses are not cached. URLs are fixed official endpoints, redirects are not followed, and no pairing code, cookie, credential or project content is sent. Missing assets during publication, malformed metadata, upstream errors/timeouts, or a version no newer than the fallback preserve the complete configured version/checksum pair. This means an upstream outage can temporarily offer the reviewed fallback instead of the newest release. Caller cancellation propagates. Development and tests use an in-memory configured source; legacy command-only configuration makes no metadata requests.

At link-code issuance, optional `installationOptions` separates these payloads:

| Kind       | UI                 | Payload                                                             |
| ---------- | ------------------ | ------------------------------------------------------------------- |
| `command`  | Terminal (default) | One line each for Bash/zsh, Windows PowerShell and an Ubuntu VPS    |
| `ai`       | Install with AI    | CS/EN prompts for this computer or an existing VPS over SSH         |
| `download` | Windows EXE        | Exact release URL, SHA-256, checked PowerShell pairing continuation |

Legacy configurations keep their original tabs. `INSTALL_COMMANDS` still validates its 512-character shell templates and one placeholder; long prompts/downloads never enter it. With new metadata, the generated local block is also retained as the legacy `installer` command, and each configured connect or Compose command has its own tab.

Each command is one line: `curl -fsSL <origin>/install.sh | PTBK_LINK=<code> bash`, `curl -fsSL <origin>/install-server.sh | PTBK_LINK=<code> bash`, or `$env:PTBK_LINK='<code>'; irm <origin>/install.ps1 | iex`. The code travels in the environment, never in argv, and each script removes it from its environment before starting anything. The scripts are public Worker routes (`auth: public`, `public-read-ip` rate limit, no input) that render the selected release into templates kept as real files under `src/domain/registration/install-scripts/`. They carry no pairing data.

The page that shows a command and the script it fetches come from the same origin over TLS, so a checksum that origin embedded in the command (as the first version did) adds no protection against that origin. Its only job was integrity against a stale cache or the SPA fallback page reaching a shell. That is kept another way: the scripts are answered by the Worker at exact paths, never by static assets or the SPA fallback (an unconfigured environment answers a 404 problem), as `text/plain` with `no-store` and `nosniff`. Each script does nothing before the call on its last line, so a download cut short at most defines functions; PowerShell parses the whole script block before running it. The scripts still verify the downloaded Node.js archive, Ubuntu bootstrap and Windows EXE by SHA-256 before running them.

The macOS/Linux script validates the code and builds the link URL. In an attended terminal it restores terminal input for `ptbk init --prepare-only --link` so the engine can show the first-access link. With redirected input and output it passes the link on stdin. It reuses compatible Git, Node.js and npm, and reuses a CLI only from its own prefix under `~/.local/share/promptbook`: another `ptbk` on PATH, even with the right version, may be a wrapper that runs as a different user with other credentials. When required, it installs Git with Homebrew, Apple Command Line Tools or, after the person at the terminal approves the shown command, the host package manager (unattended runs stop instead) and downloads an official Node.js 24 archive for x64/arm64, verified against its SHA-256. Alpine uses its native packages. Engine installations use an ordinary user prefix and Promptbook's shell installation marker. The launcher is available immediately and added to future Bash/zsh sessions. On Linux, when logind reports that linger is off for an ordinary user, the script explains why and asks before running `loginctl enable-linger` as administrator, so the engine's systemd user service comes back after a reboot without a login; unattended runs and declines skip it with a hint, root and hosts without systemd are not asked.

The Windows script downloads the exact published x64 EXE, checks its SHA-256 and waits for the native setup wizard with `/PrepareOnly=yes`. It refreshes PATH in the current PowerShell session, checks the installed CLI version and hands the pairing link to the CLI. An interactive console retains the engine’s first-access flow. Redirected sessions pass the link on stdin. Closing or failing setup stops pairing. The manual EXE tab offers just the version check and pairing after installation.

The Ubuntu VPS script uses the upstream installer. It verifies the immutable script before elevation, passes the link on stdin and runs the engine as the dedicated `promptbook` user. All paths leave project placement and first access to the engine.

The installation page opens the terminal command for the browser’s platform. The macOS/Linux, Windows PowerShell and Ubuntu VPS commands sit together at the start of one tab list, followed by the AI prompts, the Windows EXE and configured commands. Each command can be copied directly. The running-project tab also offers the pairing address when available. The Ubuntu VPS command carries one muted line naming its requirements (Ubuntu 24.04 x64 with systemd, run as root or with sudo). Under the tabs, next to the expiry line, a muted note says agents act with the host’s permissions, files and signed-in services, and that sharing a project can give colleagues indirect access to them. Both are available in Czech and English.

AI prompts carry the same one-line commands, preserve data/sign-ins and native approvals, and leave agenda/harness choices to the engine UI. No engine name is represented as a known project path. Dashboard and its payloads never know an owner setup secret.

## Reviewed artifacts and limits

Staging's reviewed fallback is npm `ptbk@0.119.0-131` (git `d35a811b`) and `Promptbook-Setup-0.119.0-131-windows-x64.exe` (SHA-256 `1bb46215441c35edaf8012935d245603c382f268de9bef979f5d062288ce938f`, hashed locally and matching GitHub's digest and the `.sha256` asset), published on 22 November 2026. Bootstrap commit `eda1a109787d164046d1f73732705e8a9afa76ec` and its checksum remain independently pinned; its verified script accepts the selected exact `--version`. This is a prerelease. Matching macOS DMGs remain in the public catalogue. Production's remaining placeholders are not credentials or a deployment instruction.

Source-checkout versions are never used for release selection. A verified command/asset is not proof that every provider flow succeeds. Update fallback version and Windows digest together after checking the published npm package and asset. Bootstrap bytes/revision remain a separate manual review; automatic version discovery does not replace the pinned script or weaken signed UI verification.

## Review and release gates

- Related draft #256 covers the older Ubuntu-only path. Coordinate this broader follow-up; do not land duplicate default flows.
- Preserve issuance-only handling, expiry/copy feedback, CZ/EN and mobile tabs. No pairing secret enters URL queries, persistent client storage, project files or logs.
- Owner setup happens on the engine origin. Continue through `onboarding@1`/`files@1`; stale `promptId` submissions remain the engine's responsibility.
- Full UI needs approved `PTBK_UI_RELEASE_URL` and `PTBK_UI_TRUST_POLICY_FILE`. Check signatures, manifest/API range, delay, revocations and `/api/v1/security` UI facts. Relay reachability is insufficient.
- Before release, complete one real engine walkthrough from a new pairing through passkey, brief/file, native harness login and usable project, including deferral. Record Windows 5.1, native EXE/DMG and real VPS runs separately from portable PowerShell and fixtures.

Targeted tests execute the copied one-liners against the served scripts in Bash 3.2/5, zsh and PowerShell with inert commands, cover failed installs/version mismatches, invalid codes, truncated downloads, valid/corrupt bootstrap and stdin handoff, check that the routes never fall back to the SPA shell, validate typed configuration/responses, and render/copy both locales. They do not install system software, buy hosting or authenticate a real provider.
