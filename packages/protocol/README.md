# @ptbk/protocol

Wire contracts between the engine, the relay and the dashboard (spec, Interfaces 1 to 5): engine IDs and hostname claims, engine registration, registry lookup, tunnel handshake and frame codec, heartbeat, and the release log with its verification. zod schemas, strict and versioned.

It also holds the TLS ClientHello parser (`parseClientHello`, `createClientHelloBuffer`) that the relay routes on and engines use to spot `acme-tls/1`. It is total over untrusted bytes, bounded by `maxBytes`, and fuzzed with fast-check. Its fixtures in `src/tls/fixtures/` are real ClientHellos captured with `scripts/capture-client-hello.ts`, which documents how each was made.

MIT, Web APIs only (`crypto.subtle`, streams), no imports from `@ptbk/*`, so it runs in Node, Workers and browsers and can move to the public repo unchanged ([ADR 0002](../../docs/adr/0002-public-private-split.md)). Plan: tasks C-01, C-02, C-03, C-06, R-01.

## Wire formats under review

These freeze at publication (E-02) after review by the engine team and Pavol ([ADR 0010](../../docs/adr/0010-protocol-design-principles.md), [ADR 0014](../../docs/adr/0014-cryptography.md)). This is the one place to review them.

- **Byte strings** are base64url (RFC 4648 §5) without padding. The decoder rejects padding, `+`, `/`, whitespace, a length ≡ 1 (mod 4) and non-zero trailing bits, so each byte string has exactly one accepted encoding.
- **Keys and signatures** carry no algorithm prefix: Ed25519 is fixed in v1. `Ed25519PublicKey` is base64url of exactly 32 bytes, `Ed25519Signature` of exactly 64.
- **Engine ID**: SHA-256 over the raw 32-byte public key (not its base64url text), base32 (RFC 4648 alphabet) lowercase, first 26 characters (130 bits), `/^[a-z2-7]{26}$/`. The default hostname is `<engineId>.<engine domain>`; any other name inside the engine domain, including the domain itself, is invalid, never custom.
- **Hostname**: ASCII only (IDN as A-labels), lowercased, at most 253 characters, at least two labels of 1–63 `[a-z0-9-]` without leading or trailing hyphen, no trailing dot. A last label that is a number (decimal or `0x` hex) is refused, because browsers parse such a host as IPv4. `RelayId` is a `Hostname` branded separately.
- **Signing input**: `signingInput(context, ...parts)` = `"ptbk-sig\0" ‖ u8 len(context) ‖ context ‖ (u32be len(part) ‖ part)…`. Strings are UTF-8; binary values (nonces, hashes, keys) are raw bytes. Contexts: `ptbk-tunnel-v1`, `ptbk-hostname-v1`, `ptbk-register-v1`, `ptbk-heartbeat-v1`. A hostname claim is Ed25519 over `signingInput('ptbk-hostname-v1', hostname, engineId)`.
- **Verification**: `@noble/curves` 2.4.0, `ed25519.verify(sig, msg, pub, { zip215: false })`: canonical A and R (y < p, no negative zero), S < L, A not of small order, then the cofactored equation. Small- or mixed-order R and mixed-order A are accepted when the equation holds (libsodium rejects them). [`src/ed25519-vectors.json`](src/ed25519-vectors.json) records the result for each edge case and is the reference other implementations must match; `bun run --filter @ptbk/protocol generate-vectors` regenerates it and refuses if noble disagrees with this rule. WebCrypto only generates keys and signs (non-extractable at runtime); it never verifies.
- **Link code**: 128 random bits from the `Random` port as lowercase RFC 4648 base32 without padding: 26 characters of `[a-z2-7]`, the last one of `a e i m q u y 4` (its 2 trailing bits are zero), so each code has one spelling. No separators. A secret: the dashboard stores only its SHA-256.
- **Registration** (`POST /v1/engines/register`, body at most 4 KiB): `{ v: 1, linkCode, enginePublicKey, engineVersion, mode: 'tunnel' | 'direct', sig }`, where `sig` is Ed25519 by the engine key over `signingInput('ptbk-register-v1', "1", linkCode, raw 32-byte public key, engineVersion, mode)`. The response `{ engineId, hostname, relays }` (1–16 unique relay hostnames) is checked by the engine with `checkRegistrationResponse`: `engineId` must derive from its own key and `hostname` must be `<engineId>.<engine domain>`. Errors are RFC 9457 problem+json with a stable `code` (`REGISTRATION_ERROR_CODE`).
- **Registry entry** (`GET /internal/v1/engines/{engineId}`): `{ enginePublicKey, hostnames (≤ 32), claims: [{ hostname, sig }] (≤ 32), status: 'active' | 'suspended' }`. `resolveRoutableHostnames` is the one claim check: the default hostname needs no claim; a custom hostname is routable only if it lies outside the engine domain, is listed once, and has exactly one claim that verifies. A routable claim is still subject to the relay's CNAME check against `expectedCnameTarget` (`<engineId>.<engine domain>`).
- **Heartbeat** (`POST /v1/engines/{engineId}/heartbeat`, body at most 4 KiB): `{ v: 1, engineId, seq, ts, version, uptimeS, diskPct, ramPct, cpuLoad, update, agents, members }`, numbers and closed enums only. `Ptbk-Signature: ed25519=<base64url>` signs `signingInput('ptbk-heartbeat-v1', SHA-256 of the exact body bytes)`, the digest as 32 raw bytes. `verifyHeartbeat` checks, in order: size, header, signature over the raw bytes, then parse and strict schema, path engine ID, `seq > lastSeq`, and `|now − ts| ≤ 120 s`; a stale timestamp returns the server time. `seq` only has to increase strictly: engines send `max(lastSeq + 1, Date.now())`, so an engine that loses its state but keeps its key is not locked out.
- **Strict and tolerant schemas**: receivers parse strictly and reject unknown fields (`RegisterEngineRequest`, `Heartbeat`, and `RegisterEngineResponse`, `RegistryEntry`, `ProblemDetails` where the dashboard checks what it sends). Clients reading a response use the `Tolerant*` variants, which validate every known field and strip unknown ones, so a newer dashboard can add optional fields (ADR 0010 §3): the engine reads `TolerantRegisterEngineResponse` and `TolerantProblemDetails`, the relay reads `TolerantRegistryEntry`. Byte caps for each are exported (`*_MAX_BYTES`).
- **Golden vectors**: [`src/signed-message-vectors.json`](src/signed-message-vectors.json) holds a signed registration request and a signed heartbeat body and header for the RFC 8032 test key, with the signing inputs in hex. They were computed independently (Python's standard library for encodings and SHA-256, OpenSSL for Ed25519); the tests check that this package reproduces them byte for byte.
- **Tunnel handshake** (`src/tunnel/handshake.ts`): JSON text messages, each with `v: 1` and at most `MAX_HANDSHAKE_MESSAGE_BYTES` UTF-8 bytes, strict (unknown fields rejected). The relay sends `challenge` (32-byte nonce, `relayId`, its protocol versions and features), the engine `auth`, the relay `ready` or `reject`. Protocol versions are 1–8 unique integers in 1..`MAX_PROTOCOL_VERSION` (65 535); features 0–32 unique `[a-z0-9-]{1,32}`. `ready` carries the highest common version and exactly the feature intersection, sorted by byte; the engine recomputes it with `checkTunnelReady` and closes with `PROTOCOL_ERROR` on any difference.
- **Tunnel signature**: Ed25519 over `signingInput('ptbk-tunnel-v1', relayId, nonce (raw 32 bytes), engineId, version, relayVersions, relayFeatures, engineVersions, engineFeatures)`. Each list is one part: versions sorted numerically in decimal, features sorted by byte, comma-joined (`[2, 10, 1]` → `"1,2,10"`; empty list → empty part). Every field of `auth` except `sig` is signed, so the negotiation cannot be downgraded (ADR 0014).
- **Tunnel frames** (`src/tunnel/frame.ts`): `[u8 type][u32 streamId, big-endian][payload]`, one per binary WebSocket message, whose length is the frame length. Bit 7 of the type byte marks a frame ignorable; bits 0–6 are the code: 0 is always invalid, 1–4 are `OPEN`, `DATA`, `CLOSE`, `WINDOW`, 5–127 are reserved for a new version or a negotiated feature. An unknown code is skipped with the flag and a protocol error without it. Stream IDs are non-zero u32; payloads at most `MAX_FRAME_PAYLOAD_BYTES`. `OPEN` = `[u8 family 4|6][4 or 16 address bytes][u16 port]`, `DATA` = 1+ raw bytes, `CLOSE` = `[u8 code 0–4]`, `WINDOW` = `[u32 increment 1..2^31−1]`. Flow control: `INITIAL_WINDOW_BYTES` of DATA credit per stream and direction, never above 2^31−1. [`src/tunnel/vectors.json`](src/tunnel/vectors.json) holds golden frames and a signed handshake; `bun run --filter @ptbk/protocol generate-vectors` regenerates it from an implementation independent of `src/`.
